# `dspy.LocalSandbox`

**`dspy.LocalSandbox`** is the **user-facing Python-execution primitive** underlying [[DSPyProgramOfThought|`dspy.ProgramOfThought`]]. From [[dspy-tutorial-program-of-thought|the ProgramOfThought tutorial]]:

> "`ProgramOfThought` integrates an adapted Python sandbox to execute code generated by LMs."

> "We'll create an instance of `dspy.LocalSandbox` and demonstrate the underlying execution of `ProgramOfThought`."

It is reachable as a top-level `dspy.LocalSandbox` symbol — the tutorial walks an explicit `sandbox = dspy.LocalSandbox(); sandbox.execute(expr)` invocation **before** introducing `dspy.ProgramOfThought`, framing the sandbox as the *engine the Module calls into*.

## Surface

```python
import dspy
sandbox = dspy.LocalSandbox()
expr = "value = 2*5 + 4\nvalue"
answer = sandbox.execute(expr)
answer   # 14
```

- **`dspy.LocalSandbox()`** — zero-argument constructor.
- **`sandbox.execute(expr: str)`** — runs `expr` as Python code; returns the value of the last expression in the snippet.

That is the entire user-facing API the tutorial discloses. Whatever internal mechanism `dspy.ProgramOfThought` uses to fold execution results back into the [[DSPyPrediction|Prediction]] is wrapped by this same `execute(...)` call.

## Why it exists as a public primitive

For most users, `dspy.ProgramOfThought` is the right entry point — the sandbox is invoked transparently. The tutorial's decision to *also* expose `dspy.LocalSandbox` directly serves three purposes:

1. **Pedagogical** — walking the sandbox first lets the tutorial *show* what the Module is doing rather than describe it.
2. **Composability** — users who want code execution **without** PoT's signature-expansion behaviour can call `sandbox.execute(...)` directly inside a custom [[DSPyModules|`dspy.Module`]].
3. **Inspectability** — a user debugging a PoT failure can manually `execute(...)` the LM's generated code to isolate whether the bug is in the Module's expansion logic or in the runtime.

This is consistent with [[DSPyProgrammingModel|the Programming Model's]] *every wrapper is a thin layer over a public primitive* posture — like `dspy.ChainOfThought` is a thin wrapper over [[DSPyPredict|`dspy.Predict`]], `dspy.ProgramOfThought` is a thin wrapper over `dspy.LocalSandbox`.

## Position relative to other DSPy execution surfaces

| Surface | What it executes | Where the code comes from |
|---|---|---|
| **`dspy.LocalSandbox.execute(expr)`** | **Arbitrary Python string** | **User-supplied** |
| [[DSPyProgramOfThought\|`dspy.ProgramOfThought`]] | Python code (via `LocalSandbox`) | LM-generated, framework-orchestrated |
| [[DSPyTools\|`dspy.Tool`]] | Python callables | User-registered functions; LM selects which |
| [[react\|`dspy.ReAct`]] | Tool calls in a loop | LM-chosen from a tool inventory |
| [[DSPyMCP\|`dspy.MCP`]] | MCP server tools (child process isolation) | Remote MCP server |

`dspy.LocalSandbox` is the **most permissive** of these — it executes whatever Python string is passed in, with no Signature constraint, no tool inventory, no MCP isolation boundary.

## Safety boundary (undisclosed)

The tutorial calls it an *"adapted Python sandbox"* but does **not** describe what it actually isolates — no documentation of file-system access, network access, or process isolation in the tutorial. Treat as **untrusted-code-adjacent until the safety boundary is explicitly characterized**. Compare:

- [[dspy-tool-use-tutorial|Tool-use tutorial]] uses [[func_timeout|`@func_set_timeout(10)`]] + try/except — *isolation by timeout only*.
- [[dspy-mcp-tutorial|MCP tutorial]] uses **child-process MCP isolation** — strong boundary.
- `dspy.LocalSandbox` — boundary **undisclosed** by the receipt the wiki has.

Mark as an **open question**: gap to fill if a follow-up tutorial or the source code discloses the actual isolation mechanism.

## Why this matters

- **First exposed public primitive for code execution in DSPy.** Prior to this tutorial, the wiki documented `dspy.ProgramOfThought` as a black-box code-execution Module; users could not invoke the underlying runtime directly. This receipt promotes the engine to first-class API status.
- **Enables `dspy.ProgramOfThought`'s sound-critic claim to be inspected.** Users debugging a PoT misclassification can manually `sandbox.execute(...)` the captured code from [[InspectHistory|`dspy.inspect_history()`]] to isolate the failure layer.
- **Composability lever for custom Modules** that need code execution outside the PoT signature-expansion contract — e.g., a Module that generates code conditioned on retrieval context but wants to control the post-execution synthesis manually rather than via the PoT-injected slots.
