# API Fuzzing

**API fuzzing** (a.k.a. *function-level* or *unit-level* fuzzing) targets a program's individual **functions / library API** directly with generated arguments, rather than feeding bytes to the whole program through its system input channels. The payoff is **flexibility and speed**: a single function can be exercised millions of times without the overhead of process startup, file/stdin plumbing, or driving the input all the way through the program. The trade-off is the **risk of false alarms** — calling a function with arguments it would never legitimately receive (violating *implicit preconditions*) can surface "bugs" that no real execution would trigger.

## The technique (The Fuzzing Book Ch 24)
*The Fuzzing Book* implements API fuzzing with **grammars that synthesize code for function calls**. Instead of generating a value and immediately calling the function (a *scaffold*), the recommended route is to **synthesize a callable string** and run it later:

```python
call = "urlparse('http://www.cispa.de/')"   # generated by a grammar
eval(call)                                  # executed whenever you like
```

A [[Grammar|grammar]] whose terminals are code snippets does the generating:

```python
URLPARSE_GRAMMAR = { "<call>": ['urlparse("<url>")'] }
URLPARSE_GRAMMAR.update(URL_GRAMMAR)        # import <url> from Ch 9's URL grammar
URLPARSE_GRAMMAR["<start>"] = ["<call>"]
```

A plain [[GrammarFuzzer|`GrammarFuzzer`]] then produces executable test strings; the `do_call(s)` helper `eval`s them and reports the result.

### Why synthesize *code* rather than call inline?
Code synthesis **decouples test generation from test execution**: tests can be saved, re-run, or emitted for a *different language*. The chapter shows `URLPARSE_C_GRAMMAR`, which wraps the same calls in a generated C `void test() { ... }` with `#include "urlparse.h"` — the recursive rule `"<calls>": ["<call>", "<calls><call>"]` emits whole *sequences* of calls (see [[CallSequenceFuzzing]]).

## Generating arguments: data-type grammar constructors
API fuzzing needs argument *values*, so the chapter provides reusable grammar constructors:

- `INT_GRAMMAR`, `FLOAT_GRAMMAR`, `ASCII_STRING_GRAMMAR` — basic types (the float grammar gives `inf`/`NaN` a probability; the string grammar quotes ASCII chars).
- `int_grammar_with_range(start, end)` / `float_grammar_with_range(start, end)` — attach a [[GeneratorGrammar|generator]] `pre` function (`random.randint` / `random.random`) via `set_opts(...)` so the expansion is overridden by an in-range value. Produce with a `ProbabilisticGeneratorGrammarFuzzer`.
- `list_grammar(object_grammar)` — composite data: instantiate a list grammar with any element grammar to get `[obj, obj, ...]` (e.g. a list of ranged floats). Dicts/sets follow the same pattern, so arbitrary argument structures can be composed.

## Oracles
Generic execution only catches crashes/exceptions. To synthesize a real [[TestOracle|oracle]], the chapter uses a [[GeneratorGrammar|generator-grammar]] `post` function to enforce equalities a context-free grammar cannot express — e.g. `assert urlparse('<url>').geturl() == '<url>'`, where both `<url>`s are forced equal. A richer variant asserts the parsed `scheme`/`netloc`/`path`/`query` against the generated components.

## From The Fuzzing Book — Carving Unit Tests
[[fuzzingbook-25-carver|Ch 25]] removes the need to hand-write the call grammars above: instead of authoring `URLPARSE_GRAMMAR` by hand, it *records* real calls (the [[Carver|`CallCarver`]]) during a system run and *mines* an API grammar from them ([[APIGrammarMining|`CallGrammarMiner`]]) — one rule per argument, with the observed values as alternatives. Fuzzing that mined grammar with a [[GrammarCoverageFuzzer|`GrammarCoverageFuzzer`]] *recombines* recorded arguments (e.g. carving `power(1,2)`/`power(3,4)` lets it emit `power(1,4)`), so API tests can be synthesized "without having to write a grammar at all." Ch 25 inherits Ch 24's exact false-alarm caveat: recombination can violate the API's *implicit preconditions*.
