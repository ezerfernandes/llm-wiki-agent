# Fuzzing

**Fuzzing** (fuzz testing) is an automated testing technique that feeds large volumes of generated or mutated inputs into a program to provoke crashes, hangs, assertion failures, or other undefined behavior. The dominant modern variant is **coverage-guided fuzzing**: the fuzzer instruments the target to observe which code branches each input exercises, keeps inputs that reach *new* coverage, and mutates them to explore deeper — a feedback loop that efficiently finds edge cases (especially in native C/C++ extensions) without an explicit input model.

Representative tools named in the [[Hypothesis]] cluster:
- **libFuzzer** — LLVM's in-process, coverage-guided fuzzing engine.
- **Atheris** — Google's coverage-guided fuzzer for Python, built on top of libFuzzer (`atheris.Setup(...)` / `atheris.Fuzz()`, with `atheris.instrument_all` / `atheris.instrument_imports` for instrumentation).
- **python-afl** — Python bindings for the AFL (American Fuzzy Lop) fuzzer.
- **HypoFuzz** — a purpose-built product that fuzzes an existing Hypothesis test suite directly; recommended for pure-Python targets or when you already have Hypothesis tests.

## Fuzzing vs property-based testing
Fuzzing and [[PropertyBasedTesting|property-based testing]] are **complementary input-generation strategies**:
- A fuzzer mutates raw byte sequences and uses runtime coverage feedback to steer toward unexplored code paths — strong at exploration, weak at producing *structured* valid inputs.
- Property-based testing uses declarative [[SearchStrategy|strategies]] to generate *structured, valid* inputs (e.g. well-formed JSON) and checks declared properties, but generation is driven by the strategy rather than live coverage feedback.

[[Hypothesis]] bridges the two via `fuzz_one_input` (see [[hypothesis-howto-external-fuzzers]]): an external coverage-guided fuzzer supplies the bytestrings and coverage feedback, while a Hypothesis strategy decodes each bytestring into a structured test case. This combines coverage-guided exploration of native extensions with strategy-driven structure plus Hypothesis' [[Shrinking|shrinking]], observability, and [[ExampleDatabase|example database]] for triage. Notably, `fuzz_one_input` does *not* shrink inline — failures are written to the database and minimised/deduplicated when the normal test suite is re-run ("fuzzer taming").

## From The Fuzzing Book — Tours through the Book
[[fuzzingbook-01-tours|*The Fuzzing Book*]] (Zeller, Gopinath, Böhme, Fraser & Holler, CISPA 2024) is a large, code-first treatment of fuzzing built around runnable Python notebooks. Its opening chapter frames the whole field as a prerequisite graph organized into six parts — lexical (byte-by-byte), syntactic (grammar-based), semantic (constraint/symbolic), domain-specific, and management — and offers role-based reading tours for programmers, students, and researchers. The book treats coverage-guided/greybox fuzzing (AFL-style) and mutation-based fuzzing as the modern mainstays, consistent with the coverage-feedback loop described above, while extending the picture toward grammar-based, generator-based, and constraint-based input generation. See the source page for the full chapter map.

## From The Fuzzing Book — Introduction to Software Testing
[[fuzzingbook-02-intro-testing|Ch 2]] supplies the testing groundwork fuzzing rests on. It defines a [[TestCase|test case]] (input + check), the [[TestOracle|test oracle]] problem (generating inputs is easy; deciding correctness for *arbitrary* generated inputs needs a property oracle like √x·√x = x), and escalates from manual tests to [[RandomTesting|random testing]] over thousands of generated values — the direct precursor to a fuzzer, whose "Next Steps" point straight at [[fuzzingbook-03-fuzzer|Ch 3]]'s random `Fuzzer`. Two ideas it establishes are load-bearing for the rest of the book: (1) random generation is *unbiased* but blind to rare special values (e.g. exactly 0), with Exercise 3 quantifying ~584 years to hit a 1/2⁶⁴ corner case — the motivation for coverage-guided and structured generation; and (2) the robustness/fuzzability duality — code that gracefully handles any *system input* can be *sent* any input, while internal functions can only be fuzzed if their [[Precondition|preconditions]] are known.

## From The Fuzzing Book — Fuzzing: Breaking Things with Random Inputs
[[fuzzingbook-03-fuzzer|Ch 3]] is the wiki's canonical treatment of **basic blackbox random fuzzing** — the historical and conceptual root of everything above. It defines fuzzing as feeding *random characters* into a program and traces the field to [[BartonMiller|Barton Miller]]'s 1989 experiment, which crashed/hung about a third of UNIX utilities. The chapter mints the book's two reusable class hierarchies: [[RandomFuzzer|`Fuzzer`/`RandomFuzzer`]] (generators overriding `fuzz()`) and [[Runner|`Runner`/`PrintRunner`/`ProgramRunner`]] (the harness returning `(result, PASS|FAIL|UNRESOLVED)`) — the architecture later chapters subclass. It catalogs the bug classes fuzzing exposes ([[BufferOverflow|buffer overflows]], missing error checks, rogue numbers) and the checkers that catch them: [[AddressSanitizer]] (the [[Heartbleed]] discovery), [[RepresentationInvariant|`repOK()`]] assertions, and [[StaticAnalysis|static typing]] via [[MyPy]] — establishing the "enable as many automatic checkers as possible" doctrine. This is the *unguided* baseline the modern coverage-guided/structured fuzzing described above improves upon.

## From The Fuzzing Book — Code Coverage
[[fuzzingbook-04-coverage|Ch 4]] supplies the **feedback signal** that turns blackbox random fuzzing into the coverage-guided fuzzing described above. It builds a `Coverage` class on [[TraceFunction|`sys.settrace`]] to record executed lines, distinguishes [[LineCoverage|statement]] from [[BranchCoverage|branch coverage]], and uses coverage to *compare* fuzzers — quantifying that the Ch 3 random [[RandomFuzzer|`fuzzer()`]] reaches full statement coverage of `cgi_decode()` in ~40–60 inputs. Its thesis that coverage can *guide* generation toward uncovered code (not merely *measure* it) is the conceptual root of [[CoverageGuidedFuzzing|coverage-guided fuzzing]] and is picked up by the book's [[fuzzingbook-05-mutation-fuzzer|mutation]] and [[fuzzingbook-06-greybox-fuzzer|greybox]] fuzzers. See [[Coverage]] for the full operational treatment.

## From The Fuzzing Book — Mutation-Based Fuzzing
[[fuzzingbook-05-mutation-fuzzer|Ch 5]] introduces the **mutation** family of fuzzing as the answer to blackbox random fuzzing's core weakness — random strings are almost always invalid and bounce off the parser. [[MutationBasedFuzzing|Mutation-based fuzzing]] starts from valid [[SeedInput|seed inputs]] and applies small [[Mutator|mutations]] (delete/insert/flip a character) that tend to stay valid; the chapter packages this as `MutationFuzzer` and then guides it by [[Coverage|coverage]] in [[MutationCoverageFuzzer|`MutationCoverageFuzzer`]], which keeps only mutants reaching new coverage. This is the book's first concrete [[CoverageGuidedFuzzing|coverage-guided]] fuzzer and an explicit miniature of [[AFL|AFL]]'s "keep inputs that find new paths" heuristic — the bridge from the random baseline to the greybox/power-scheduled fuzzing of [[fuzzingbook-06-greybox-fuzzer|Ch 6]].

## From The Fuzzing Book — Greybox Fuzzing
[[fuzzingbook-06-greybox-fuzzer|Ch 6]] mints the wiki's [[GreyboxFuzzing|greybox fuzzing]] concept — the dominant modern form named throughout this page — by reconstructing [[AFL]]. It positions greybox between blackbox and whitebox (lightweight coverage instrumentation, no heavyweight analysis) and adds the steering layer mutation fuzzing lacked: a [[PowerSchedule|power schedule]] that assigns each seed an [[SeedEnergy|energy]] (selection probability). It builds three escalating fuzzers — `GreyboxFuzzer` (keep new coverage), the [[BoostedGreyboxFuzzing|boosted]] `CountingGreyboxFuzzer` + [[AFLFast|`AFLFastSchedule`]] (energy `1/f(p)^a` for rare [[PathCoverage|paths]], a [[MarkovChain|Markov-chain]] model), and the [[DirectedGreyboxFuzzing|directed]] `AFLGoSchedule` (energy by [[CallGraph|call-graph]] distance to a target) — crediting co-author [[MarcelBohme|Marcel Böhme]] for AFLFast/AFLGo. It forwards to [[fuzzingbook-07-search-based-fuzzer|Ch 7]] (search-based) and [[fuzzingbook-15-greybox-grammar-fuzzer|Ch 15]] (grammar-aware greybox).

## From The Fuzzing Book — Search-Based Fuzzing
[[fuzzingbook-07-search-based-fuzzer|Ch 7]] adds the *directed*, objective-driven member of the family: [[SearchBasedTesting|search-based software testing (SBST)]], which treats finding an input that reaches a **specific** target branch as an optimization problem. Rather than maximizing coverage broadly (the greybox loop above), it defines a [[FitnessFunction|fitness function]] — typically the [[BranchDistance|branch distance]], obtained by automatic AST [[CodeInstrumentation|instrumentation]] — and follows its gradient with [[MetaheuristicSearch|meta-heuristics]]: [[HillClimbing|hill climbing]] for small neighborhoods, and global [[EvolutionaryTesting|evolutionary]]/[[GeneticAlgorithm|genetic-algorithm]] search for large spaces. It is the conceptual basis of [[EvoSuite]], the search-based test generator by co-author [[GordonFraser|Gordon Fraser]], and generalizes the directed-fuzzing-as-optimization view already hinted at by AFLGo in [[fuzzingbook-06-greybox-fuzzer|Ch 6]].

## From The Fuzzing Book — Fuzzing with Grammars
[[fuzzingbook-09-grammars|Ch 9]] opens **Part III (syntactic fuzzing)** and pivots from byte-level generation to **structured** generation. The core weakness of the random/mutation fuzzers above is that their inputs are mostly *invalid* and bounce off the parser; [[GrammarBasedFuzzing|grammar-based fuzzing]] fixes this by expanding a [[ContextFreeGrammar|context-free grammar]] — encoded as the reusable [[Grammar|`Grammar`]] data structure (a `dict` of [[Nonterminal|nonterminal]] → expansion lists) — so every input is syntactically valid by construction. The chapter mints `simple_grammar_fuzzer()` (a naive string-rewriting producer capped by `max_nonterminals`), the running `EXPR_GRAMMAR`/`CGI_GRAMMAR`/`URL_GRAMMAR` examples, [[EBNF]]→[[BNF]] desugaring via `convert_ebnf_grammar()`, and `is_valid_grammar()`. It also unifies the two strategies: grammar-produced inputs make excellent **seeds** for the Ch 5 [[MutationBasedFuzzing|`MutationFuzzer`]], probing the valid/invalid boundary where parser bugs live. The naive producer's inefficiency and unbounded growth are fixed by the [[DerivationTree|derivation-tree]] `GrammarFuzzer` of [[fuzzingbook-10-grammar-fuzzer|Ch 10]].

## From The Fuzzing Book — Testing Web Applications
[[fuzzingbook-27-web-fuzzer|Ch 27]] aims the family at a *running system over a network protocol* (HTTP), opening Part V's user-interface arc ([[WebApplicationFuzzing|Web-application fuzzing]]). It composes earlier techniques rather than minting a new engine: a hand-written [[Grammar|grammar]] of order URLs feeds a [[GrammarFuzzer|`GrammarFuzzer`]]; a [[MutationBasedFuzzing|`MutationFuzzer`]] perturbs valid orders until a `WebRunner` (a `Runner` whose oracle is the HTTP status code) sees a 500, then [[fuzzingbook-16-reducer|Ch 16]] delta debugging minimizes the failing path. Its central move is to *mine* the fuzzing grammar from the served HTML form ([[WebFormFuzzer|`WebFormFuzzer`]] / [[GrammarMining|grammar mining]] from a UI), so any form can be fuzzed from just a URL — and then to turn this into a fully automatic attack platform for [[SQLInjection|SQL]]/[[CrossSiteScripting|XSS]]/[[HTMLInjection|HTML]] injection ([[CodeInjection|code injection]]), defended by [[InputSanitization|input sanitization]]. It leads into generic [[fuzzingbook-28-gui-fuzzer|GUI fuzzing (Ch 28)]].

## From The Fuzzing Book — Fuzzing in the Large
[[fuzzingbook-29-fuzzing-in-the-large|Ch 29]] opens **Part VI (Managing Fuzzing)** and zooms out from all the engines above to the *operational* problem of [[FuzzingAtScale|running them at scale]]: dozens to thousands of machines, many programs, for weeks. It introduces a central **crash server** + database (demonstrated with Mozilla's [[FuzzManager]], authored by co-author [[ChristianHoller|Christian Holler]]) that collects failures from a whole fleet, and two scale techniques: [[CrashDeduplication|crash bucketing]] (grouping thousands of duplicate crashes by a stack-trace/program-counter *signature* into a few distinct bugs) and central per-fuzzer [[Coverage|coverage]] collection (to see where fuzzers stall). This is the management layer wrapped around the [[GreyboxFuzzing|greybox]]/[[MutationBasedFuzzing|mutation]] engines and is the counterpart to [[fuzzingbook-30-when-to-stop-fuzzing|Ch 30]]'s statistical "when to stop" question.

## From The Fuzzing Book — When To Stop Fuzzing
[[fuzzingbook-30-when-to-stop-fuzzing|Ch 30]], the book's *final* chapter, answers the dual of every preceding "how to fuzz" with a statistical "**when to stop**." It reframes fuzzing as [[SpeciesDiscovery|species discovery (STADS)]] — each input belongs to a species (e.g. its execution trace) — and applies the [[GoodTuringEstimator|Good-Turing estimator]] ([[AlanTuring|Turing]] & [[IJGood|I.J. Good]], from [[BletchleyPark]]'s [[EnigmaMachine|Enigma]] codebreaking) to estimate the [[DiscoveryProbability|probability of discovering a new path]]. Per [[MarcelBohme|Böhme]], that probability is an upper bound on **[[ResidualRisk|residual risk]]** (the chance of an unfound bug); Anne [[AnneChao|Chao]]'s [[Chao1Estimator|Chao1 estimator]] adds a *total*-species estimate and extrapolation. The campaign should stop when discovery probability / residual risk falls below threshold. The book closes: *"go and create great fuzzers and test generators!"*
