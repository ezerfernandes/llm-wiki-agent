# Critical Section

A region of code that "we cannot allow more than one thread to execute … at the same time" ([[parproc-ch01-intro-parallel-processing]]). The standard term in shared-memory parallel programming for code that must execute *atomically* with respect to peer threads. In embedded contexts the related but narrower sense is *"a context where interrupts are disabled"* ([[rust-embedded-book-concurrency-index]]) — same goal, different racing peer (interrupt handler instead of another thread).

## Shared-memory / threading sense

[[parproc-ch01-intro-parallel-processing]] introduces the term via a Sieve-of-Eratosthenes prime finder that uses [[Pthreads]] mutexes to serialize access to a shared `nextbase` counter. Matloff's framing: "a common term used for this is that we wish the actions in the critical section to collectively be **atomic**, meaning not divisible among threads. The calls to `pthread_mutex_lock()` and `pthread_mutex_unlock()` ensure this. If thread A is currently executing inside the critical section and thread B tries to lock the lock by calling `pthread_mutex_lock()`, the call will block until thread B executes `pthread_mutex_unlock()`."

The chapter's worked race: if two threads both read `nextbase = 11`, both will then redundantly cross out multiples of 11, and the subsequent increment will skip 13 entirely — the lock prevents this interleaving.

Crucially: **"a critical section is always a potential bottleneck in a parallel program, because its code is serial instead of parallel."** Matloff's running optimization is to *coarsen* the critical section — process five sieve multipliers per lock acquisition instead of one — reducing lock overhead by 5×. The cost is load imbalance near the end of the run.

[[OpenMP]] exposes this pattern as `#pragma omp critical { ... }` — the OpenMP runtime sets up and releases the locks automatically. Matloff: "alleviating you of work and alleviating your code of clutter."

## Embedded / interrupt-free sense

*"A context where interrupts are disabled"* ([[rust-embedded-book-concurrency-index]]). The simplest synchronization primitive for embedded concurrency between `main` and [[Interrupt|interrupt handlers]]: wrap a region of code so that no interrupt can fire inside it, then run the (otherwise racing) shared-state access inside.

On [[ARMCortexM|Cortex-M]], realized as `cortex_m::interrupt::free(|cs| …)` (from the [[CortexMCrate|`cortex-m`]] crate): *"this is also the same as disabling interrupts, running some code, and then re-enabling interrupts."* Underlying `CriticalSection` token type lives in the [[BareMetalCrate|`bare-metal`]] crate, re-exported by `cortex-m`.

## The `CriticalSection` token trick

The closure's `cs: &CriticalSection` argument is the chapter's central **zero-cost-abstraction trick**: by accepting `&CriticalSection` on methods that need critical-section protection, you force the caller to *prove at compile time* that it's inside `interrupt::free`, with no runtime overhead. *"These tokens are only safely generated by `interrupt::free`, so by requiring one be passed in, we ensure we are operating inside a critical section, without having to actually do the lock ourselves. This guarantee is provided statically by the compiler: there won't be any runtime overhead associated with `cs`."*

Consequence: **one token serves many resources**. If you have multiple counters / [[Mutex|mutexes]], they can all be borrowed under the same `cs` without nested critical sections.

```rust,ignore
cortex_m::interrupt::free(|cs| {
    COUNTER_A.borrow(cs).set(1);
    COUNTER_B.borrow(cs).set(2);
    // both protected by the same cs, no nesting
});
```

## Costs and limits

- **Latency / jitter cost**: *"each critical section temporarily pauses interrupt processing, there is an associated cost of some extra code size and higher interrupt latency and jitter (interrupts may take longer to be processed, and the time until they are processed will be more variable)."*
- **Single-core only**: *"while a critical section guarantees no interrupts will fire, it does not provide an exclusivity guarantee on multi-core systems! The other core could be happily accessing the same memory as your core, even without interrupts. You will need stronger synchronisation primitives if you are using multiple cores"* — typically [[Atomic|atomics]].
- **Asymmetry**: code that *only writes a value the racing thread never reads*, or *cannot be preempted* by the racing thread, doesn't need the critical section. The chapter's running example puts the critical section on the `main`-side increment but not on the `#[interrupt] fn timer()` reset.
