# Google ADK (Agent Development Kit)

**Google ADK** — the **Agent Development Kit** (also written "Agent Developer Kit") — is [[google|Google]]'s framework for building, evaluating, and deploying AI agents, integrated with Google's AI infrastructure ([[GoogleCloudVertexAI|Vertex AI]], [[gemini|Gemini]]). It is one of the agentic frameworks used for the hands-on code examples in [[AgenticDesignPatterns|*Agentic Design Patterns*]] (Gulli).

## Role in the book
[[agentic-design-patterns-ch01-prompt-chaining|Chapter 1]] names Google ADK alongside [[LangChain]]/[[LangGraph]] and [[CrewAI|Crew AI]] as frameworks that *"offer structured environments for constructing and executing multi-step processes, which is particularly advantageous for complex architectures."* The [[AgenticDesignPatterns|book hub]] lists ADK among the three framework families it draws on, used to build, evaluate, and deploy agents on Google's AI stack. (Ch 1's runnable example itself uses LangChain/LangGraph LCEL; ADK is named as an alternative.)

## In Agentic Design Patterns — Appendix C (frameworks overview)
[[agentic-design-patterns-appendices-bg|Appendix C]] (Gulli) profiles ADK as a **high-level, opinionated, production-oriented** framework for multi-agent applications. It contrasts with [[LangChain]]/[[langgraph|LangGraph]] by offering orchestration of agent collaboration rather than the fundamental building blocks of an agent's internal logic: it **abstracts away low-level graph construction** with pre-built architectural patterns and agent types like **`SequentialAgent`** and **`ParallelAgent`** that manage control flow automatically. It is architected around a **"team" of agents** — a primary agent delegating to specialized sub-agents — with state and session handled more implicitly. The appendix's analogy: "LangGraph gives you the detailed tools to design the intricate wiring of a single robot or a team; Google's ADK gives you a factory assembly line designed to build and manage a fleet of robots that already know how to work together." Example: `LlmAgent(model="gemini-2.0-flash-exp", ..., tools=[google_search])` — a search-augmented agent. (The appendix renders the import as `from google.adk.agents import LlmAgent`.)

## Routing via Auto-Flow ([[agentic-design-patterns-ch02-routing|Ch 2]])
[[agentic-design-patterns-ch02-routing|Chapter 2 (Routing)]] gives ADK its own hands-on example: a `Coordinator` `Agent` defined with `sub_agents=[booking_agent, info_agent]`. *"The presence of sub_agents enables LLM-driven delegation (Auto-Flow) by default"* — so ADK implements [[Routing|routing]] declaratively, by **defining a discrete set of capabilities/[[ToolUse|tools]]** and letting the framework's internal logic match user intent to the correct functional handler ([[AgentHandoff|agent delegation]]). This contrasts with [[LangGraph]]'s explicit computational-graph routing: ADK *"focuses on defining distinct capabilities (Tools) and relies on the framework's ability to route user requests to the appropriate tool handler, which can be simpler for agents with a well-defined set of discrete actions."* The example uses `gemini-2.0-flash`, `FunctionTool`, and `InMemoryRunner`.

## Parallel execution via `ParallelAgent` ([[agentic-design-patterns-ch03-parallelization|Ch 3]])
[[agentic-design-patterns-ch03-parallelization|Chapter 3 (Parallelization)]] gives ADK its most elaborate example, exercising the `LlmAgent` / `ParallelAgent` / `SequentialAgent` primitives together. Three `LlmAgent` researchers (renewable energy, EVs, carbon capture — each `gemini-2.0-flash` with the `google_search` [[ToolUse|tool]]) each write their summary to shared **session state** via `output_key`. A `ParallelAgent(name="ParallelWebResearchAgent", sub_agents=[...])` *"orchestrates the concurrent execution of the researchers"* and **finishes only once all sub-agents have completed and stored their results in state**. A downstream merger `LlmAgent` then reads those state keys and synthesizes a structured, source-attributed report (strictly grounded on the provided summaries). The whole flow is wrapped in a `SequentialAgent(sub_agents=[parallel_research_agent, merger_agent])` set as the `root_agent` — run parallel research first, then merge. The book notes ADK can *also* achieve parallelism through **LLM-Driven Delegation**, where a coordinator agent's LLM identifies independent sub-tasks and triggers their concurrent handling by specialized sub-agents. This is ADK's native answer to [[LangChain]]'s `RunnableParallel` and [[LangGraph]]'s parallel branches; *"this inherent capability... allows developers to design and implement solutions where multiple agents can operate concurrently, rather than sequentially."*

## Reflection via Generator-Critic `SequentialAgent` ([[agentic-design-patterns-ch04-reflection|Ch 4]])
[[agentic-design-patterns-ch04-reflection|Chapter 4 (Reflection)]] uses ADK to implement the [[Reflection|Producer-Critic / Generator-Critic]] model directly. `from google.adk.agents import SequentialAgent, LlmAgent`. A `generator` `LlmAgent` (`name="DraftWriter"`) writes an initial draft and saves it to shared **session state** via `output_key="draft_text"`. A `reviewer` `LlmAgent` (`name="FactChecker"`) is instructed to read `state['draft_text']`, verify factual accuracy of all claims, and emit a **structured dictionary** — `{"status": "ACCURATE"|"INACCURATE", "reasoning": "..."}` — to `output_key="review_output"`. A `SequentialAgent(name="WriteAndReview_Pipeline", sub_agents=[generator, reviewer])` enforces the execution order (generator → reviewer), realizing the [[Reflection|reflection]] feedback loop as a stateful two-agent pipeline. The chapter adds a note that **ADK's `LoopAgent`** is the alternative for *true iterative* reflection (repeated generate→critique→refine cycles). This is the [[GoogleADK|ADK]] counterpart to [[LangChain]]'s single-file `run_reflection_loop`.

## Tool use & built-in tools ([[agentic-design-patterns-ch05-tool-use|Ch 5]])
[[agentic-design-patterns-ch05-tool-use|Chapter 5 (Tool Use)]] highlights ADK's **library of natively integrated, pre-built tools** that drop directly into an agent's capabilities — the framework's distinguishing feature for [[ToolUse|tool use]]:
- **`google_search`** — a pre-built tool wrapping the Google Search engine; gives an agent web-search/external-information retrieval (`tools=[google_search]`). Already used by the Ch 3 researchers.
- **`built_in_code_execution`** / **`BuiltInCodeExecutor`** (from `google.adk.code_executors`) — a **sandboxed Python interpreter** attached to an `LlmAgent` via `code_executor=BuiltInCodeExecutor()`. Used for deterministic logic and precise calculations beyond probabilistic generation (e.g., a `calculator_agent` evaluating `(5 + 7) * 3`). See [[CodeInterpreter]].
- **`VSearchAgent`** (`google.adk.agents.VSearchAgent`) — answers questions by searching a specified **[[GoogleCloudVertexAI|Vertex AI Search]]** datastore (`datastore_id`), streaming the response and surfacing **grounding metadata** / source attributions. The enterprise-search realization of tool-augmented RAG.
- **`FunctionTool`** — the wrapper for custom callables (also used in Ch 2's routing example).

These ADK tools map onto [[GoogleCloudVertexAI|Vertex AI]]'s prebuilt [[VertexAIExtensions|extensions]] (Code Interpreter, Vertex AI Search) — auto-executed by the platform, in contrast to manually-executed [[FunctionCalling|function calls]]. ADK agents run via a `Runner` + `InMemorySessionService`, processing the agent's streamed events to extract the final response.

## Multi-agent coordination primitives ([[agentic-design-patterns-ch07-multi-agent|Ch 7]])
[[agentic-design-patterns-ch07-multi-agent|Chapter 7 (Multi-Agent Collaboration)]] is ADK's most primitive-dense chapter, exercising the full coordination toolkit:
- **Hierarchical `sub_agents`** — a coordinator `LlmAgent` (`model="gemini-2.0-flash-exp"`) given `sub_agents=[greeter, task_doer]`; ADK **automatically establishes the parent-child relationship** (`assert greeter.parent_agent == coordinator`), and delegation is driven by the coordinator's `description`/`instruction` ("When asked to greet, delegate to the Greeter…"). The supervisor/orchestrator-worker topology of [[MultiAgentCollaboration]].
- **Custom non-LLM agent** — `class TaskExecutor(BaseAgent)` (from `google.adk.agents`) overriding `async def _run_async_impl(self, context: InvocationContext)` to `yield Event(author=self.name, content=...)`. Shows agents need not be LLM-backed.
- **`LoopAgent`** — `LoopAgent(name="StatusPoller", max_iterations=10, sub_agents=[process_step, ConditionChecker()])` runs its sub-agents sequentially for up to N iterations; a `ConditionChecker(BaseAgent)` reads `context.session.state.get("status")` and **escalates to stop the loop** via `yield Event(actions=EventActions(escalate=True))` when complete. ADK's mechanism for *iterative* workflows (the same primitive Ch 4 cited for true iterative [[Reflection|reflection]]).
- **`SequentialAgent`** — `SequentialAgent(name="MyPipeline", sub_agents=[step1, step2])`; `step1=Agent(name="Step1_Fetch", output_key="data")` writes to `session.state["data"]` and `step2` reads `state['data']` — linear workflows where one agent's output becomes the next's input.
- **`ParallelAgent`** — `ParallelAgent(name="data_gatherer", sub_agents=[weather_fetcher, news_fetcher])` runs sub-agents concurrently, each writing to its own `output_key` (`weather_data`, `news_data`) in shared state (see [[Parallelization]] / Ch 3).
- **Agent-as-a-Tool (`AgentTool`)** — `from google.adk.tools import agent_tool`; `image_tool = agent_tool.AgentTool(agent=image_generator_agent, description=...)` wraps a sub-agent so a parent `artist_agent` can invoke it via `tools=[image_tool]` exactly like a function. "The AgentTool acts as a bridge, allowing one agent to use another agent as a tool" — a layered system where a higher-level agent orchestrates a lower-level specialist. Bridges [[MultiAgentCollaboration]] with [[ToolUse]].

## Memory: Session / State / MemoryService ([[agentic-design-patterns-ch08-memory-management|Ch 8]])
[[agentic-design-patterns-ch08-memory-management|Chapter 8 (Memory Management)]] makes ADK the primary worked example of the [[MemoryManagement|memory-management]] pattern, mapping its primitives onto the memory taxonomy: a **`Session`** is one chat thread (its `events` log + `state` scratchpad) managed by `SessionService`; **`session.state`** is a key-value dictionary for [[ShortTermMemory|short-term]] / temporary chat data, with prefixes scoping persistence (`user:` per-user across sessions, `app:` shared across all users, `temp:` current-turn-only, no-prefix session-specific); and **`MemoryService`** is the searchable [[LongTermMemory|long-term]] store (`BaseMemoryService` interface: `add_session_to_memory`, `search_memory`; impls `InMemoryMemoryService` for testing and `VertexAiRagMemoryService` for production, backed by Vertex AI [[rag|RAG]]). The chapter's discipline: **update state through the event pipeline** — `output_key` (auto-saves the agent's final text reply) or `EventActions.state_delta` appended via `session_service.append_event()` — never by direct `session.state` mutation, so changes are logged, timestamped, and persisted. ADK also integrates [[VertexAiMemoryBank|Vertex AI Memory Bank]] out-of-the-box via `VertexAiMemoryBankService` (`google.adk.memory`). See [[MemoryManagement]].

## MCP integration via `MCPToolset` ([[agentic-design-patterns-ch10-mcp|Ch 10]])
[[agentic-design-patterns-ch10-mcp|Chapter 10 (MCP)]] makes ADK the hands-on vehicle for both sides of the [[ModelContextProtocol|MCP]] client-server model, via `MCPToolset` (from `google.adk.tools.mcp_tool.mcp_toolset`):
- **Consuming an existing MCP server.** An `LlmAgent` (`gemini-2.0-flash`) gets an `MCPToolset` whose `connection_params=StdioServerParameters(command='npx', args=['-y', '@modelcontextprotocol/server-filesystem', TARGET_FOLDER_PATH])` — connecting over STDIO to the Node.js-distributed community filesystem MCP server (`npx` runs it without global install). The chapter also shows `StdioConnectionParams` driving `python3 ./agent/mcp_server.py` and `uvx mcp-google-sheets@latest` (the `uv`-based isolated-env Python runner), each passing `env` (e.g. `SERVICE_ACCOUNT_PATH`, `DRIVE_FOLDER_ID`).
- **Consuming a remote/HTTP MCP server.** `MCPToolset(connection_params=HttpServerParameters(url="http://localhost:8000"))` connects to a running [[FastMCP]] server (the chapter's `greet`-tool example).
- **Tool filtering.** An optional `tool_filter=['list_directory', 'read_file']` / `tool_filter=['greet']` restricts which of a server's tools the agent may use.
- **Exposing ADK tools as an MCP server** is also supported (the reverse direction) — ADK "supports both utilizing existing MCP servers and exposing ADK tools via an MCP server."

Agents are discoverable as Python packages (an `__init__.py` with `from . import agent`), then run via `adk web` from the parent directory. This is ADK's realization of MCP's **dynamic discovery** — the agent queries the server's manifest at connect time rather than having tools hard-coded.

## Goals as instructions, monitoring via state ([[agentic-design-patterns-ch11-goal-setting|Ch 11]])
[[agentic-design-patterns-ch11-goal-setting|Chapter 11 (Goal Setting and Monitoring)]] notes ADK's idiomatic realization of the [[GoalSettingAndMonitoring|Goal Setting and Monitoring]] pattern: *"In Google's ADK, goals are often conveyed through agent instructions, with monitoring accomplished through state management and tool interactions."* I.e. an agent's objective lives in its `instruction` prompt, and progress toward it is tracked through the shared session `state` (the same `output_key` / `state_delta` substrate Ch 8 describes) plus the outputs of the tools the agent calls — exactly the loop ADK's `LoopAgent` + `ConditionChecker` (which `escalate`s to stop when `state['status']` is complete, per Ch 7) already mechanizes.

## Fault tolerance via layered `SequentialAgent` ([[agentic-design-patterns-ch12-exception-handling|Ch 12]])
[[agentic-design-patterns-ch12-exception-handling|Chapter 12 (Exception Handling and Recovery)]] uses ADK to make an agent fault-tolerant against a failed [[ToolUse|tool call]]. A `robust_location_agent = SequentialAgent(sub_agents=[primary_handler, fallback_handler, response_agent])` runs three `Agent`s (all `gemini-2.0-flash-exp`) in guaranteed order: `primary_handler` tries the precise `get_precise_location_info` tool; `fallback_handler` checks shared `state["primary_location_failed"]` and — only if `True` — extracts the city from the user's query and calls the coarser `get_general_area_info` (otherwise does nothing); `response_agent` reads `state["location_result"]` and presents it, apologizing if it's empty. The `SequentialAgent`'s deterministic ordering is what makes the fallback fire *after* the primary records its failure in session state — ADK's idiomatic expression of the **fallback + [[GracefulDegradation|graceful-degradation]]** strategy of the [[ExceptionHandlingAndRecovery|Exception Handling and Recovery]] pattern. (Ch 7's `LoopAgent` + `ConditionChecker` `escalate` mechanism is ADK's complementary recovery/escalation primitive.)

## RAG: `google_search` grounding + `VertexAiRagMemoryService` ([[agentic-design-patterns-ch14-rag|Ch 14]])
[[agentic-design-patterns-ch14-rag|Chapter 14 (Knowledge Retrieval / RAG)]] uses ADK for two of its three hands-on [[rag|RAG]] examples. First, **grounding via built-in search**: an `Agent(model="gemini-2.0-flash-exp", tools=[google_search])` (from `google.adk.tools import google_search`) — "the Google Search tool is a direct example of a built-in retrieval mechanism that can augment an LLM's knowledge." Second, **persistent semantic retrieval over a Vertex AI RAG Corpus**: `VertexAiRagMemoryService` (from `google.adk.memory`) is initialized with a `rag_corpus=RAG_CORPUS_RESOURCE_NAME` (`projects/.../ragCorpora/your-corpus-id`), `similarity_top_k=SIMILARITY_TOP_K` (=5, how many relevant chunks to return), and `vector_distance_threshold=VECTOR_DISTANCE_THRESHOLD` (=0.7, the max semantic distance for retrieved results). This is the same `VertexAiRagMemoryService` Ch 8 named as the production [[MemoryManagement|long-term-memory]] backend — Ch 14 shows it as the retrieval engine over a [[GoogleCloudVertexAI|Vertex AI]] **RAG Corpus**, making RAG and long-term memory the same primitive in ADK. (Ch 14's third example uses [[LangChain]]/[[langgraph|LangGraph]] + [[Weaviate]], not ADK.)

## Cost-aware multi-agent routing ([[agentic-design-patterns-ch16-resource-aware|Ch 16]])
[[agentic-design-patterns-ch16-resource-aware|Chapter 16 (Resource-Aware Optimization)]] makes ADK the lead hands-on vehicle for the [[ResourceAwareOptimization|Resource-Aware Optimization]] pattern. ADK's multi-agent architecture enables modular, scalable cost-aware apps; **model flexibility** lets it use various Gemini models directly (the example defines a `gemini_pro_agent` on `gemini-2.5-pro` and a `gemini_flash_agent` on `gemini-2.5-flash`) or integrate other models through **[[LiteLLM]]** (`from google.adk.models.lite_llm import LiteLlm`). A `QueryRouterAgent(BaseAgent)` overrides `_run_async_impl` to route on `query_length` (a simple `< 20` words threshold) — short queries to the Flash agent, long ones to the Pro agent — the cost/complexity specialization of Ch 2's [[Routing|routing]]. ADK's orchestration supports **dynamic, LLM-driven routing** for adaptive behavior, and its **built-in evaluation features** allow systematic assessment of agent performance for system refinement (the [[CritiqueAgent|Critique Agent]] / [[EvaluationAndMonitoring]] loop). The worked travel-planner example assigns the high-level planner to Gemini Pro and the simple repetitive sub-tasks to Gemini Flash. See [[DynamicModelSelection]].

## Tool-call guardrail via `before_tool_callback` ([[agentic-design-patterns-ch18-guardrails|Ch 18]])
[[agentic-design-patterns-ch18-guardrails|Chapter 18 (Guardrails/Safety Patterns)]] uses ADK's **callback** mechanism as a **technical guardrail** that validates tool invocations before they run. A `validate_tool_params(tool: BaseTool, args: Dict[str, Any], tool_context: ToolContext) -> Optional[Dict]` function (imports `from google.adk.agents import Agent`, `from google.adk.tools.base_tool import BaseTool`, `from google.adk.tools.tool_context import ToolContext`) reads `tool_context.state.get("session_user_id")`, compares it against the call's `args.get("user_id_param")`, and on mismatch **blocks execution** by returning an error dict (`{"status": "error", "error_message": "Tool call blocked: User ID validation failed for security reasons."}`); returning `None` lets the tool proceed. It is wired onto a `root_agent = Agent(model='gemini-2.0-flash-exp', name='root_agent', instruction="...", before_tool_callback=validate_tool_params, tools=[...])`. This is the [[Guardrail|guardrails]] pattern's **tool-use-restriction / [[PrincipleOfLeastPrivilege|least-privilege]]** layer realized in ADK — *"validating model and tool invocations through callbacks,"* alongside [[gemini|Gemini]]'s built-in content filters and system instructions, isolated code execution ([[LocalSandbox]]/[[CodeInterpreter]]), and VPC Service Controls network boundaries (the chapter's [[GoogleCloudVertexAI|Vertex AI]] safety practices). Distinct from Ch 13's `before_model` `personalization_callback` and Ch 12's `SequentialAgent` fallback — here the callback is `before_tool` and its job is **authorization/blocking**. See [[Guardrail]] / [[ToolUse]].

## Evaluation support: `adk web` / `pytest` / `adk eval` ([[agentic-design-patterns-ch19-evaluation|Ch 19]])
[[agentic-design-patterns-ch19-evaluation|Chapter 19 (Evaluation and Monitoring)]] presents ADK as the concrete framework that supports the [[EvaluationAndMonitoring|Evaluation and Monitoring]] pattern, offering **three evaluation methods**:
- **Web-based UI** (`adk web`) — interactive evaluation and **dataset generation**; enables creating/saving sessions into existing or new eval sets and displays evaluation status. The eval UI renders an agent session as a list of **Events** and a **Trace** view (e.g. `text → functionCall:get_current_time → functionResponse → text`), with a Sessions/Eval tab (Fig. 3).
- **Programmatic `pytest` integration** — runs test files as part of integration tests by calling **`AgentEvaluator.evaluate(...)`**, specifying the agent module and test-file path; suited for [[CICD|CI/CD]] pipelines.
- **Command-line `adk eval`** — automated evaluation given the agent module path and eval-set file, with options to specify a config file or print detailed results; specific evals within a larger eval set can be selected by listing them after the filename, comma-separated. Suited for regular build generation/verification.

Two artifact types underpin all three: **test files** (one session, multiple turns — unit testing during dev, optionally with a `test_config.json` defining criteria) and **evalset files** (an "evalset" dataset of multiple multi-turn "evals" — complex integration testing). Each turn records the user query, **expected tool-use [[AgentTrajectoryEvaluation|trajectory]]**, intermediate responses, and reference final response. References: ADK Web (`github.com/google/adk-web`), ADK Evaluate (`google.github.io/adk-docs/evaluate/`).

## Exposing an A2A server ([[agentic-design-patterns-ch15-a2a|Ch 15]])
[[agentic-design-patterns-ch15-a2a|Chapter 15 (Inter-Agent Communication / A2A)]] makes ADK the hands-on vehicle for serving an agent over the [[A2AProtocol|A2A protocol]] — a "Calendar Agent" exposed as an A2A-compliant HTTP service. An `async create_agent(client_id, client_secret)` builds an `LlmAgent` (`gemini-2.0-flash-001`) whose `tools=await CalendarToolset(...).get_tools()` come from `google.adk.tools.google_api_tool` (Google Calendar API). The agent's interface is declared in an `AgentCard(name='Calendar Agent', url=f'http://{host}:{port}/', version='1.0.0', defaultInputModes=['text'], defaultOutputModes=['text'], capabilities=AgentCapabilities(streaming=True), skills=[AgentSkill(id='check_availability', ...)])` — i.e. ADK produces the [[AgentCard|Agent Card]] discovery file directly. A `Runner` wires `InMemoryArtifactService` / `InMemorySessionService` / `InMemoryMemoryService`; an **`ADKAgentExecutor(runner, agent_card)`** + `DefaultRequestHandler(agent_executor, task_store=InMemoryTaskStore())` feed an **`A2AStarletteApplication(agent_card, http_handler=request_handler)`**, whose `.routes()` are mounted on a Starlette app (with an extra OAuth `/authenticate` route via `agent_executor.on_auth_callback(...)`) and served by [[Uvicorn|uvicorn]]. This complements Ch 10's `MCPToolset` story: Ch 10 shows ADK on the agent↔tool ([[ModelContextProtocol|MCP]]) axis; Ch 15 shows ADK on the agent↔agent (A2A) axis. Reference samples (LangGraph, CrewAI, Azure AI Foundry, AG2) live in Google's `a2a-samples` repo.
