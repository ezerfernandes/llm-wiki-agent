# DSPy

**DSPy** is an open-source framework for **programming — not just prompting — language model systems** ([dspy.ai](https://dspy.ai/), [github.com/stanfordnlp/dspy](https://github.com/stanfordnlp/dspy)). Originated in the [[StanfordUniversity|Stanford NLP]] group (Omar Khattab and collaborators) as the successor to the *DSP* (Demonstrate-Search-Predict) line of work. The framework provides a small, learnable API in which an LLM pipeline is built from typed **[[DSPySignatures|Signatures]]** (declarative input → output specs), composed into **[[DSPyModules|Modules]]** (predictors, [[ChainOfThought|chain-of-thought]], [[react|ReAct]], retrieval-augmented, multi-hop, etc.), and **automatically optimized** by **[[DSPyOptimizers|Optimizers]]** that tune the prompts and / or weights of the underlying [[LanguageModel|LM]] against a metric and a development set.

## Framework-level thesis: "writing code instead of strings"

The [[dspy-programming-overview|Programming Overview]] (page 2 of 13 of the *Learn* section) is the canonical statement of DSPy's design philosophy: ***"DSPy is a bet on writing code instead of strings. In other words, building the right control flow is crucial."*** An LLM pipeline is a **program** — typed inputs, typed outputs, composed control flow — not a string template; the string is an implementation detail the framework generates from the program. This is the framework-level claim that justifies every concrete design choice below.

The full philosophy is captured on the [[DSPyProgrammingModel]] concept page, which records DSPy's **separation-of-concerns** decomposition: a conventional prompt entangles four orthogonal concerns into one non-portable string, and DSPy factors them out as four named, separable artifacts:

| Conventional-prompt concern | What it does | DSPy artifact |
|---|---|---|
| **Signature** | "asks the LM to take some inputs and produce some outputs of certain types" | [[DSPySignatures\|Signatures]] |
| **Adapter** | "formats the inputs in certain ways and requests outputs in a form it can parse accurately" | [[DSPyAdapters\|Adapters]] |
| **Module logic** | "asks the LM to apply certain strategies like 'thinking step by step' or using tools" | [[DSPyModules\|Modules]] |
| **Manual optimization** | "relies on substantial trial-and-error to discover the right way to ask each LM to do this" | [[DSPyOptimizers\|Optimizers]] |

The decomposition underwrites three concrete portability claims the Programming Overview commits to:

- **Swap the LM (or its adapter)** without changing the rest of the program.
- **Swap one module for another** (e.g. `dspy.ChainOfThought` ↔ `dspy.ProgramOfThought`) without modifying the Signature — the Signature is the **stable interface**; the Module is the **swappable strategy**.
- **Run prompt-optimization *or* weight fine-tuning** against the same program.

The Programming Overview also commits the framework to a "**start simple, then grow**" discipline: the recommended starting point for any new task is a single `dspy.ChainOfThought` module, with complexity added incrementally based on observation rather than designed up-front.

## The three-stage development model

The framework's *Learn* documentation ([[dspy-learn-index]]) frames the developer journey as three sequential stages with a **strict precedence**:

| Stage | What you do | Output |
|---|---|---|
| **1. Programming** | "defining your task, its constraints, exploring a few examples, and using that to inform your initial pipeline design" | A runnable DSPy program (signatures + modules + LM wiring) |
| **2. Evaluation** | "collect an initial development set, define your DSPy metric, and use these to iterate on your system more systematically" | A measurable dev-set score the program currently achieves |
| **3. Optimization** | "use DSPy optimizers to tune the prompts or weights in your program" | A program whose dev-set metric is higher than the hand-written baseline |

> "It's unproductive to launch optimization runs using a poorly designed program or a bad metric." — [[dspy-learn-index|DSPy Learn index]]

The wiki notes one important consequence: DSPy is **not** an optimizer-only library, and the framework's documentation explicitly warns against treating it as one. The Programming and Evaluation stages are load-bearing prerequisites.

## Evaluation: the measurement stage between Programming and Optimization

[[dspy-evaluation-overview|The Evaluation Overview]] (page 9 of 13) opens the **Evaluation** stage of the three-stage model and operationalizes it as a **four-step iterative loop** the wiki captures on the [[DSPyEvaluation]] concept page:

1. **Collect a development set of 20–200 examples.** *"Even 20 input examples of your task can be useful, though 200 goes a long way."* The dev set is **small by design** — Evaluation is diagnostic, not training. Sourcing options (ranked): adjacent public datasets ([[HuggingFace]] / StackExchange) → permissive-license re-use → manual labeling → deployed-demo collection.
2. **Define a DSPy metric.** *"A metric is a function that takes examples from your data and takes the output of your system, and returns a score."* Two regimes: scalar `accuracy` for simple tasks; a **small DSPy program** for long-form tasks (the [[llmasjudge|LLM-as-judge]] pattern, made disciplined by DSPy's typed-[[DSPySignatures|Signature]] / [[DSPyAdapters|Adapter]]-managed prompt machinery).
3. **Run development evaluations on the pipeline.** Produces two outputs — a **numerical baseline** the [[DSPyOptimizers|Optimizer]] must beat, and a **qualitative diagnostic** that may force a return to the Programming stage rather than proceed forward.
4. **Optimize the metric itself** (recursive — applies only when the metric is a DSPy program). *"If your metric is itself a DSPy program, a powerful way to iterate is to optimize your metric itself."* The metric's output is bounded and scalar, so the "metric of the metric" is easy to define and a few labeled examples suffice. This makes the Evaluation stage **recursively self-improving**.

Three load-bearing commitments distinguish DSPy Evaluation from generic ML evaluation:

- **Small dev sets are sufficient** — the 20-example floor lowers start-up cost; the 200-example ceiling marks the *"goes a long way"* point of diminishing returns for dev-set-scale work.
- **Intermediate-step labels are almost never needed** — *"You almost never need labels for the intermediate steps in your program in DSPy."* The metric scores **final outputs only**; intermediate-step quality (the `reasoning` from [[ChainOfThought|`dspy.ChainOfThought`]], the `trajectory` from [[react|`dspy.ReAct`]]) is the [[DSPyOptimizers|Optimizer's]] job to discover, not the developer's job to label. This is DSPy's structural answer to the *intermediate-supervision problem* in chain-of-thought training.
- **The metric is itself iterative** — *"Invest in defining metrics and improving them incrementally over time; it's hard to consistently improve what you aren't able to define."* The metric has versions over the project's lifetime; a change in metric definition may invalidate prior baselines. This is the [[DSPyProgrammingModel|"start simple, then grow"]] discipline from page 2 restated at the metric layer.

The Evaluation Overview is the **entry point** of the stage; it motivates two sibling pages: **Data Handling** (page 10, [[dspy-data|ingested 2026-05-17]]) which expanded Step 1 into [[DSPyExample|`dspy.Example`]] mechanics (typed Python dict-with-utilities, `with_inputs(...)` input-tagging, `inputs()` / `labels()` partition, and the structurally important [[DSPyPrediction|`Prediction`]]-is-a-subclass-of-[[DSPyExample|`Example`]] inheritance that makes the [[DSPyMetrics|metric's]] `(example, prediction) -> score` contract type-symmetric), and **[[DSPyMetrics|Metrics]]** (page 11, forward reference) which will expand Step 2 into the full `(example, prediction) -> score` contract.

[[dspy-data|The Data Handling page]] (page 10 of 13) **resolves** both long-standing forward references [[DSPyData]] and [[DSPyExample]] carried by [[DSPyEvaluation]] / [[dspy-evaluation-overview]] since the Evaluation stage opened. Three load-bearing commitments distinguish DSPy's data layer from generic ML data handling:

- **DSPy is a machine learning framework.** *"DSPy is a machine learning framework, so working in it involves training sets, development sets, and test sets."* DSPy locates itself inside the supervised-ML tradition; a [[DSPyOptimizers|DSPy Optimizer]] is **trained** on a training set the way an ML model is trained, the dev set selects the winning candidate, the test set is held out for final assessment.
- **Datasets are plain Python lists.** Unlike PyTorch (`torch.utils.data.Dataset`), TensorFlow (`tf.data.Dataset`), or HuggingFace (`datasets.Dataset`), DSPy does **not** introduce a `Dataset` class. A training set is a `list[dspy.Example]`. The framework adds **exactly one** class on the data layer ([[DSPyExample|`dspy.Example`]]); train/dev/test splits are Python slicing; no `train_test_split(...)` helper, no built-in loaders. The small-API discipline consistent with [[dspy-modules|*"DSPy is just Python code"*]].
- **Inputs-only sufficiency.** *"You can use DSPy effectively without any intermediate or final labels, but you will need at least a few example inputs."* The data-side mirror of [[dspy-evaluation-overview|the Evaluation Overview's]] *intermediate-step labels are almost never needed* commitment — together, the two commitments authorize a minimal-data development style (collect 20–200 inputs, write a reference-free [[llmasjudge|LLM-as-judge]] rubric, evaluate).

The [[DSPyExample|`dspy.Example`]] primitive itself is a typed Python dict-with-utilities — arbitrary field names and value types (no enforced schema; the [[DSPySignatures|Signature]] supplies schema separately); dot-notation field access (`ex.field_name`); `with_inputs("field", ...)` input-tagging that returns a **new** `Example` whose attached `input_keys` set tags the named fields (non-mutating; warn-not-fail discipline); and non-destructive `inputs()` / `labels()` partition accessors. The structurally important fact the page records: **[[DSPyPrediction|`dspy.Prediction`]] is a subclass of `dspy.Example`** — which makes the [[DSPyMetrics|metric]]'s `(example, prediction) -> score` contract **type-symmetric**: both arguments share the same dot-access / partition surface, so the metric author writes `example.answer == prediction.answer` with no class-aware branching. [[DSPyExample]] is the data-side primitive paired with [[DSPyPredict]] (the strategy-side minimal primitive); [[DSPyData]] is the dataset-layer discipline paired with [[DSPyModules]] (the strategy-layer composition discipline).

## Optimization: the automated-search stage and the fourth artifact

[[dspy-optimization-overview|The Optimization Overview]] (page 12 of 13) **opens the Optimization stage** of the three-stage model and operationalizes the *fourth* of [[DSPyProgrammingModel|the Programming Model's]] four orthogonal artifacts at the workflow level. The canonical one-sentence definition: *"Once you have a system and a way to evaluate it, you can use DSPy optimizers to tune the prompts or weights in your program."* The page commits the framework to a **three-input, one-output contract** the wiki captures on the [[DSPyOptimization]] concept page:

| Slot | What it is | Source |
|---|---|---|
| **Program** (input) | A [[DSPyModules\|`dspy.Module`]] subclass — typed [[DSPySignatures\|Signatures]] + composed sub-Modules + LM wiring | [[DSPyProgrammingModel\|Programming stage]] |
| **Metric** (input) | A `(example, pred, trace=None) -> float \| int \| bool` callable | [[DSPyEvaluation\|Evaluation stage]] ([[DSPyMetrics]]) |
| **Training set** (input) | A `list[dspy.Example]` of 30–300+ examples | [[DSPyEvaluation\|Evaluation stage]] ([[DSPyData]] / [[DSPyExample]]) |
| **Optimized program** (output) | Same [[DSPyModules\|`dspy.Module`]] subclass — refined instructions / demonstrations / weight references | The optimizer |

Four load-bearing commitments distinguish DSPy Optimization from generic ML hyperparameter optimization:

- **The optimizer's three inputs compose the prior two stages.** Programming produces the program; Evaluation produces the metric and training set; Optimization consumes all three. This is the **interface contract** that makes the three-stage model composable — each stage's *output* is the next stage's *input*.

- **Training-set size scales from 30 to 300+.** *"You can often get substantial value out of 30 examples, but aim for at least 300 examples."* The training-set regime is explicitly **larger** than [[DSPyEvaluation|the Evaluation stage's]] 20–200-example dev-set regime — the optimizer's search benefits from more examples than diagnostic measurement does. The 30-example floor lets the developer try optimization early; the 300-example target marks the *"goes a long way"* point for serious optimization work. The order-of-magnitude gap between 30 and 300 mirrors the *"start simple, then grow"* discipline at the training-set layer.

- **The conventional ML train/val split is inverted to 20/80 for most prompt optimizers.** *"For most prompt optimizers, we recommend allocating 20% of your data for training and 80% for validation, contrary to typical deep learning conventions. This is because prompt optimizers tend to overfit on small training sets."* This is the page's **most consequential single claim** — it tells the developer to **use less training data** than they would in conventional ML, because the prompt-optimization search space (instructions + demonstrations) is small enough that an optimizer can **memorize** a small training set and **generalize poorly**. A large validation set is the **overfitting defense**.

- **[[GEPA]] is the named carve-out.** *"However, the GEPA optimizer follows standard ML practice — maximizing the training set size while keeping the validation set sufficiently sized to represent the downstream task distribution."* The page names exactly **one** specific optimizer ([[GEPA]]) and only to disclose that it **violates** the framework-level 20/80 recommendation — implying GEPA is more robust to overfitting on small training sets than the other prompt optimizers. The mechanism is deferred to page 13 ([[DSPyOptimizers|Optimizers]]).

- **Iteration spans four axes, not just optimizer-choice.** *"Iterative development is key. DSPy gives you the pieces to do that incrementally."* The page names four iteration axes — **data, program structure, metric, and optimizer** — via six diagnostic questions, **three of which point back into the Programming and Evaluation stages** rather than forward into the optimizer catalog. The Optimization stage is therefore **not a black-box terminus** — when results disappoint, the developer is expected to return to earlier stages along any of the four axes. The three-stage model is a **closed feedback loop**, not a strictly forward sequence.

With the Optimization Overview ingested, the **four-artifact picture is structurally complete at the workflow level**: every concern named on [[DSPyProgrammingModel|the Programming Model]] now has a corresponding source page and concept anchor — **Signatures** ([[dspy-signatures]] → [[DSPySignatures]]), **Adapters** ([[dspy-adapters]] → [[DSPyAdapters]]), **Modules** ([[dspy-modules]] → [[DSPyModules]]), and **Optimizers** ([[dspy-optimization-overview]] → [[DSPyOptimization]] at the workflow level, with [[DSPyOptimizers]] at the catalog level resolved by page 13). [[DSPyEvaluation|Evaluation]] sits as the connective stage between Programming and Optimization — the metric and training set the Optimization stage consumes are produced by the Evaluation stage. The Optimization Overview deliberately **defers the per-optimizer catalog** ([[BootstrapFewShot]], [[BootstrapFewShotWithRandomSearch]], [[MIPROv2]], [[BootstrapFinetune]], [[GEPA]], and others) to page 13, mirroring the [[dspy-evaluation-overview|Evaluation Overview]] → [[dspy-metrics|Metrics]] split — one page anchors the workflow, the sibling page anchors the per-algorithm machinery. The split between [[DSPyOptimization]] (workflow / minted by this ingest) and [[DSPyOptimizers]] (catalog / forward reference) mirrors the [[DSPyEvaluation]] / [[DSPyMetrics]] precedent.

## Core abstractions (forward references)

DSPy's surface area is small and the *Learn* section enumerates it. Each item below has (or will have) its own concept page once the corresponding Learn sub-page is ingested:

- **[[DSPySignatures|Signatures]]** — declarative, typed input → output specifications, *"a declarative specification of input/output behavior of a DSPy module"* ([[dspy-signatures]], page 4 of 13). Two surface forms: **inline** (`"question -> answer"`, `"context: list[str], question: str -> answer: str"`) and **class-based** (`class Emotion(dspy.Signature)` with `dspy.InputField` / `dspy.OutputField` typed attributes, docstring as task description, and `desc=` per-field hints). Five-tier type system: basic Python / `typing` composites / pydantic models / dot-notation nested types / DSPy-special types (`dspy.Image`, `dspy.History`). Modules can **expand signatures under the hood** (`dspy.ChainOfThought` adds a `reasoning` field). DSPy uses Signatures to *generate* prompts rather than asking the user to write them.
- **[[DSPyModules|Modules]]** — composable *prompting-technique-as-building-block* primitives ([[dspy-modules]], page 5 of 13). Generalized over any Signature; each carries learnable parameters (instructions, demonstrations, optional LM-weight references); compose into bigger programs via `class MyProgram(dspy.Module)` with `__init__` + `forward(...)`. Seven built-ins: [[DSPyPredict|`dspy.Predict`]] (minimal primitive — *"all other DSPy modules are built using `dspy.Predict`"*), [[ChainOfThought|`dspy.ChainOfThought`]] (adds `reasoning`), [[DSPyProgramOfThought|`dspy.ProgramOfThought`]] (output-code-then-execute), [[react|`dspy.ReAct`]] (tool-using agent via `tools=[...]`), [[DSPyMultiChainComparison|`dspy.MultiChainComparison`]] (N-CoT + LM comparison), [[DSPyRecursiveLanguageModel|`dspy.RLM`]] (Recursive Language Model — sandboxed Python REPL + recursive sub-LLM calls for over-context cases), and function-style [[DSPyMajority|`dspy.majority`]] (vote over a set of [[DSPyPrediction|`Prediction`]]s). Returns [[DSPyPrediction|`dspy.Prediction(...)`]] which exposes output fields as attributes and (from DSPy 2.6.16) carries `get_lm_usage()` cost-accounting telemetry under `dspy.configure(track_usage=True)`.
- **[[DSPyAdapters|Adapters]]** — translation layer between Signatures and the concrete LM API call (handles formatting, parsing, few-shot demo injection).
- **[[DSPyTools|Tools]]** — external function / API invocation primitive used by tool-using modules ([[react|ReAct]], agents). [[dspy-tools]] (page 7 of 13) defines the abstraction: `dspy.Tool` wraps a Python callable (exposing `.name` / `.desc` / `.args` / `str(tool)` from the function's `__name__` / docstring / type hints), and `dspy.ToolCalls` is the model-output type carrying the LM's requested invocations back into Python (`call.execute()` runs each; **DSPy 3.0.4b2+** required). Two equal-status approaches: **fully-managed** via [[react|`dspy.ReAct`]] (framework owns the think-act-observe loop, returns a `trajectory`-bearing [[DSPyPrediction|`Prediction`]]) and **manual handling** via [[DSPyPredict|`dspy.Predict`]] with a [[DSPySignatures|Signature]] whose input is `tools: list[dspy.Tool]` and whose output is `dspy.ToolCalls` (user owns the loop; void-return tools are first-class). Native function calling is configured at the [[DSPyAdapters|Adapter]] layer via `use_native_function_calling=` (defaults: [[DSPyAdapters|`ChatAdapter`]]=`False`, [[DSPyAdapters|`JSONAdapter`]]=`True`; automatic fallback to text-parsing for models that don't support it — the **second model-capability scoping** in the *Learn* corpus). Async tools via `tool.acall(...)` plus the `dspy.context(allow_tool_async_sync_conversion=True)` sync-from-async opt-in.
- **[[ModelContextProtocol|MCP]]** — DSPy integrates with the [Model Context Protocol](https://modelcontextprotocol.io/) for tool and context plumbing ([[dspy-mcp]], page 8 of 13). DSPy doesn't manage MCP server connections — the user opens an `mcp.ClientSession` via the `mcp` Python SDK (over `stdio_client` or `streamablehttp_client` transport) and uses [[DSPyMCP|`dspy.Tool.from_mcp_tool(session, tool)`]] to convert each MCP-side tool descriptor into a [[DSPyTools|`dspy.Tool`]] instance. Converted tools then compose through every existing DSPy pathway — [[react|`dspy.ReAct`]] as the canonical entry point — without any further MCP-aware code. All MCP execution is async, so [[react|`dspy.ReAct`]] must be invoked via `.acall(...)` and the agent invocation must live *inside* the `async with` session block. Installation: `pip install -U "dspy[mcp]"`. [[anthropic|Anthropic]] is the protocol originator; MCP is **framework-agnostic** — the same server serves DSPy, [[ClaudeCode|Claude Code]], and any other MCP client. This is the first concrete demonstration in the Learn corpus that DSPy's [[DSPyTools|`dspy.Tool`]] abstraction is **portable across tool origin** (local function vs MCP server).
- **[[DSPyMetrics|Metrics]]** — scoring functions over `(prediction, example)` pairs; the contract between the Evaluation and Optimization stages.
- **[[DSPyOptimizers|Optimizers]]** — the prompt / weight tuners (formerly "Teleprompters"); search over few-shot demonstrations, instructions, and / or LM weights to maximize the metric on a training set.

The list of optimizers and the full taxonomy of modules will be filled in by sibling ingests of the 12 remaining Learn sub-pages.

## Position in the wiki's LLM-programming landscape

DSPy is the wiki's first dedicated **LLM-programming framework** entity, and it occupies a distinctive position relative to the corpus's existing AI/LLM research papers:

- **vs. hand-written prompt engineering ([[PromptEngineering]]).** DSPy automates the search over prompts that prompt engineering performs manually. Optimizers like `BootstrapFewShotWithRandomSearch`, `MIPROv2`, and `BootstrapFinetune` (full enumeration deferred to the *Optimizers* sub-page ingest) replace human prompt-iteration with program-level metric-driven search.

- **vs. agentic harnesses ([[2604.25850-agentic-harness-engineering]]).** The harness-engineering paper explicitly counterposes itself against "DSPy-style instruction tuning" — its argument is that the system prompt alone is **not** the load-bearing component, tools / middleware / long-term memory are. DSPy and AHE are not strictly contradictory: DSPy is the prompt-and-demonstration-tuning layer, AHE is the surrounding harness machinery. They could in principle be composed.

- **vs. [[LLMModuloFramework|LLM-Modulo]] ([[2402.01817-llm-modulo]]).** Kambhampati et al.'s framework keeps the LLM as candidate-generator and routes correctness through external sound critics. DSPy's Modules are precisely the candidate-generator layer of an LLM-Modulo system; DSPy's Metrics are precisely the *critic* layer. Their relationship is complementary — DSPy could be the substrate on which an LLM-Modulo pipeline is built.

- **vs. [[AgenticAI]] DAGs ([[2605.12966-agentic-ai-to-agi]]).** Liao et al.'s DAG framework $\Psi = (\mathcal{G}, \mathcal{F}, \Lambda)$ is more general than DSPy's typical pipeline graph, but a DSPy program *is* an instance of the Agentic AI DAG — Modules are nodes, the inter-module dataflow is the edge structure, and DSPy's [[CompositionalCapacity|compositional]] story sits inside the bounded-$C(\mathcal{G})$ regime the paper argues for.

## LM-agnosticism in practice: the `dspy.LM` client

The [[dspy-language-models|Language Models]] page (3 of 13) operationalizes the *"swap the LM (or its adapter)"* portability claim into a **two-line code change**. The mechanism is a single class — [[DSPyLM|`dspy.LM`]] — that wraps every supported provider behind one initializer signature using a `provider/model-name` model string. The page's most consequential disclosure is the **upstream dependency**: `dspy.LM` routes provider plumbing through **[[LiteLLM]]**:

> *"DSPy supports dozens of LLM providers via LiteLLM."*

LiteLLM is therefore the substrate that makes DSPy's LM-agnostic claim true — DSPy's `provider/model-name` convention *is* LiteLLM's, and the per-provider authentication / request-shaping / response-parsing is LiteLLM's responsibility. The provider matrix the page demonstrates spans three deployment regimes with the same API:

| Regime | Example | Backing service |
|---|---|---|
| **Managed API** | `dspy.LM('openai/gpt-4o-mini')`, `dspy.LM('anthropic/claude-sonnet-4-5-20250929')`, `dspy.LM('gemini/gemini-2.5-pro-preview-03-25')`, `dspy.LM('vertex_ai/gemini-2.0-flash')`, `dspy.LM('databricks/...')`, `dspy.LM('anyscale/...')`, `dspy.LM('together_ai/...')`, `dspy.LM('azure/<deployment>')` | [[openai\|OpenAI]] / [[anthropic\|Anthropic]] / [[gemini\|Gemini]] / [[google\|GCP]] / [[Databricks]] / [[Anyscale]] / [[TogetherAI\|Together AI]] / [[microsoft\|Azure]] |
| **Self-hosted GPU** | `dspy.LM('openai/meta-llama/Meta-Llama-3-8B-Instruct', api_base='http://localhost:7501/v1')` | [[SGLang]] OpenAI-compatible server |
| **Local laptop** | `dspy.LM('ollama_chat/llama3.2', api_base='http://localhost:11434')` | [[Ollama]] local runtime |

Two **bind modes** wire an `dspy.LM` into the rest of the program, both thread-safe — `dspy.configure(lm=...)` (global default) and `with dspy.context(lm=...):` (block-local override, the multi-LM pattern). On top of LiteLLM, `dspy.LM` adds four framework-level capabilities: default-on **caching**, **`rollout_id`**-based deterministic cache-busting (OpenAI / Databricks), per-call **`lm.history`** telemetry (`prompt / messages / kwargs / response / outputs / usage / cost / timestamp / uuid / model / response_model / model_type`) which [[DSPyOptimizers|Optimizers]] later replay against, and **`model_type="responses"`** as an opt-in for OpenAI's Responses API surface. Full detail on the [[DSPyLM]] concept page.

## Modules: the *swappable-strategy* layer over a stable Signature

[[dspy-modules|The Modules page]] (page 5 of 13) **defines** the *module-logic* concern named on [[DSPyProgrammingModel|the Programming Model]] and operationalizes it as the [[DSPyModules|`dspy.Module`]] class plus a built-in taxonomy. The page's most consequential structural claim is the **`dspy.Predict` primitive**: *"Internally, all other DSPy modules are built using `dspy.Predict`."* The framework has *one* prompting primitive — every strategy ([[ChainOfThought|CoT]], [[DSPyProgramOfThought|PoT]], [[react|ReAct]], [[DSPyMultiChainComparison|MultiChainComparison]], [[DSPyRecursiveLanguageModel|RLM]]) decomposes to a [[DSPyPredict|`dspy.Predict`]] plus a **signature expansion**:

| Module | Signature expansion | Use case |
|---|---|---|
| [[DSPyPredict\|`dspy.Predict`]] | None — identity. | Bare-bones LM call. |
| [[ChainOfThought\|`dspy.ChainOfThought`]] | Adds `reasoning` before output. | Default; *"start simple, then grow."* |
| [[DSPyProgramOfThought\|`dspy.ProgramOfThought`]] | Code-and-execution slots. | Computable answers; sound-critic adjudication. |
| [[react\|`dspy.ReAct`]] | Tool-call slots; `tools=[...]` kwarg. | Tool-using agent. |
| [[DSPyMultiChainComparison\|`dspy.MultiChainComparison`]] | N CoT + final comparison Predict. | LM-adjudicated ensembling. |
| [[DSPyRecursiveLanguageModel\|`dspy.RLM`]] | Sandboxed REPL + recursive sub-LLM calls. | Over-context exploration. |
| [[DSPyMajority\|`dspy.majority`]] | N/A — function-style aggregator. | Vote-based ensembling (zero LM cost). |

Composition is **plain Python** — *"DSPy is just Python code that uses modules in any control flow you like, with a little magic internally at `compile` time to trace your LM calls"*. A multi-module program is a `dspy.Module` subclass:

```python
class Hop(dspy.Module):
    def __init__(self, num_docs=10, num_hops=4):
        self.num_docs, self.num_hops = num_docs, num_hops
        self.generate_query = dspy.ChainOfThought('claim, notes -> query')
        self.append_notes  = dspy.ChainOfThought(
            'claim, notes, context -> new_notes: list[str], titles: list[str]'
        )

    def forward(self, claim: str) -> list[str]:
        notes, titles = [], []
        for _ in range(self.num_hops):
            query = self.generate_query(claim=claim, notes=notes).query
            context = search(query, k=self.num_docs)
            prediction = self.append_notes(claim=claim, notes=notes, context=context)
            notes.extend(prediction.new_notes)
            titles.extend(prediction.titles)
        return dspy.Prediction(notes=notes, titles=list(set(titles)))
```

Three structural commitments: sub-modules live as `self.*` attributes (so the framework can enumerate them via `named_predictors()` / `named_parameters()` for [[DSPyOptimizers|Optimizer]] consumption — the same PyTorch convention `dspy.Module` *"is inspired directly by"*); `forward(...)` is the entry point; the return value is always a [[DSPyPrediction|`dspy.Prediction(...)`]] so the bigger Module composes the same way its sub-Modules do.

**LM-usage tracking** is framework-level: `dspy.configure(track_usage=True)` enables per-`Prediction` `get_lm_usage()` returning `{provider/model: {prompt_tokens, completion_tokens, total_tokens, ...details}}` aggregated across **every** LM call inside `forward()`. Cached responses don't count — the cache discipline propagates from [[LiteLLM]] through [[DSPyLM]] into the Prediction's telemetry. Requires DSPy 2.6.16+.

## Adapters: the *wire-format* layer between Signatures and the LM

[[dspy-adapters|The Adapters page]] (page 6 of 13) **defines** the third of [[DSPyProgrammingModel|the Programming Model's]] four orthogonal artifacts. The page's opening line is the canonical definition: *"Adapters function as the bridge between `dspy.Predict` and the actual Language Model (LM)."* The [[DSPyAdapters|Adapter]] sits between the typed [[DSPySignatures|Signature]] and [[DSPyLM|`dspy.LM`]] in the call stack, performing three responsibilities the rest of the framework cannot do generically:

1. Convert a Signature into a system message defining the task.
2. Format input data (multi-turn messages, demo injection, conversation history, function calls, and DSPy-special types — [[DSPyTools|`Tool`]] / `dspy.Image` / `dspy.History`) into the LM's request shape.
3. Parse the LM's textual response into a typed [[DSPyPrediction|`dspy.Prediction`]].

The framework ships **four** built-in adapters:

| Adapter | Wire format | Compatibility |
|---|---|---|
| [[DSPyAdapters\|`dspy.ChatAdapter`]] (default) | Field delimiters `[[ ## field_name ## ]]`; JSON schemas inlined for non-primitive types; **automatic `JSONAdapter` fallback on parse failure** | **Universal** — *"works with all language models"* |
| [[DSPyAdapters\|`dspy.JSONAdapter`]] | Native LM `response_format` parameter | Models supporting `response_format`; *incompatible with smaller open-source models lacking this capability* |
| [[DSPyAdapters\|`dspy.XMLAdapter`]] | XML-formatted I/O | Named only on the *Learn* page |
| [[DSPyAdapters\|`dspy.TwoStepAdapter`]] | Two-step extract-then-format workflow | Named only on the *Learn* page |

Custom adapters are supported via `Adapter`-subclass + `format()`/`parse()` override. Two configuration channels — `dspy.configure(adapter=...)` (global) and `with dspy.context(adapter=...):` (block-local) — mirror the [[DSPyLM|LM]] bind modes, and two introspection hooks — `adapter.format(signature, demos, inputs)` and `adapter.format_system_message(signature)` — make the wire format visible.

`JSONAdapter`'s `response_format` requirement is the **first explicit model-capability boundary** in the [[dspy-learn-index|Learn corpus]] — a reminder that the *"swap the LM"* portability the [[dspy-language-models|Language Models page]] operationalizes is not unconditional at the wire-format layer. The Adapter is also the **single funnel** through which every DSPy-typed value crosses into the LM's wire format: [[DSPyTools|Tools]] (the page-7 forward reference) and the multi-modal `dspy.Image` primitive (introduced on [[dspy-signatures]]) both compose through the Adapter, not through separate sub-systems inside `dspy.ReAct` or `dspy.Predict`. Full detail on the [[DSPyAdapters]] concept page.

## MedVAL: clinical text validation via `dspy.BootstrapFinetune` + QLoRA

**[[2507.03152-medval|MedVAL (Aali et al., arXiv 2026)]]** is the **first wiki-corpus paper to apply [[BootstrapFinetune|`dspy.BootstrapFinetune`]] to a clinical-safety task** and the source of the **[[QLoRA]] integration** added to DSPy's local PEFT pipeline. The paper extends DSPy in two directions:

1. **A QLoRA-enabled local PEFT path** — 4-bit weight quantization via `BitsAndBytesConfig` + LoRA adapters, lets < 8B-parameter students fine-tune on a single NVIDIA A6000. Lands in `stanfordnlp/dspy` via the paper's GitHub PR.
2. **A domain-specific bootstrap filter** — replaces the metric-pass-fail filter with **[[GeneratorValidatorConsistency|$\mathcal{M}_\mathrm{MedVAL}$]]**, a continuous absolute-+-relative-consistency metric over synthetic perturbations. Filtering at $\tau = 0.9$ retains 57% of synthetic data and outperforms unfiltered 100% on every tested student.

The output is **[[MedVAL4B|MedVAL-4B]]** (Qwen3-4B base, F1 = 0.527 on [[MedVALBench]]) — the best open-source clinical validator in the benchmark. Together with the GPT-4o-MedVAL non-inferiority-to-a-physician result ($p < 0.001$), this establishes DSPy as the canonical framework for distilling deployable clinical safety models, alongside the optimizer-line uses of [[MIPROv2|MIPRO]] / [[BetterTogether]] / [[GEPA|GEPA]] in compound-AI systems and the [[DSPyGuardrails|guardrails-line]] uses for safety pipelines.

## LM Assertions: runtime self-refinement as a programming-language construct

**[[2312.13382-dspy-assertions|DSPy Assertions (Singhvi, Shetty, Tan, Potts, Sen, Zaharia, Khattab — arXiv 2023/2024)]]** adds a *runtime self-refinement* layer that sits **orthogonal** to the four Programming-Model artifacts. Rather than tuning prompts ([[DSPyOptimizers]]), tuning weights ([[BootstrapFinetune]]), or expanding a [[DSPySignatures|Signature]], LM Assertions intercept the **module-execution layer** with retry-with-feedback semantics:

| Construct | Severity | On persistent failure after $R$ retries |
|---|---|---|
| **[[DSPyAssert\|`dspy.Assert`]]** | Hard — non-negotiable | Raises `AssertionError`; halts pipeline |
| **[[DSPySuggest\|`dspy.Suggest`]]** | Soft — heuristic guidance | Logs `SuggestionError`; continues to next module |

The paper introduces three assertion-driven optimizations:

- **[[AssertionDrivenBacktracking|Assertion-driven backtracking]]** (inference-time) — failing module is re-invoked with its prior erring output + the user error message injected into the prompt; the LM sees its own failure and the rule it broke.
- **[[AssertionDrivenExampleBootstrapping|Assertion-driven example bootstrapping]]** (compile-time) — wraps backtracking around the **teacher** in [[BootstrapFewShotWithRandomSearch]] so bootstrapped few-shots satisfy every assertion at every intermediate module, not only the final-answer metric.
- **[[CounterexampleBootstrapping|Counterexample bootstrapping]]** (compile-time) — captures the failure → fix traces from backtracking and uses them as negative few-shot demonstrations.

The five-strategy comparison matrix (Table 1 of the paper) shows `C+Infer w/ Assert` (compile-time + inference-time) dominating on intrinsic metrics across four [[hotpotqa|HotPotQA]]-derived tasks ([[MultiHopQA]], [[LongFormQA]], [[QuizGen]], [[TweetGen]]); headline result: [[QuizGen]] valid-JSON output rises from **37.6% → 100%**, and the composite Validity metric from **30.5% → 87.2%**.

Position in the DSPy-adjacent research arc:

- **Predates** [[2406.11695-mipro|MIPRO]] / [[2407.10930-better-together|BetterTogether]] / [[2507.19457-gepa|GEPA]] (arXiv Dec 2023 v1, Feb 2024 v2).
- **Supplies the *self-refinement primitive*** the later optimization papers' demonstration-quality assumptions tacitly rely on.
- **Compatible with [[GEPA]]'s reflective prompt mutation** — different layers ($\Pi$-update vs runtime control-flow); LM Assertions could host a GEPA-optimized prompt and vice versa. The paper's `msg: Optional[str]` argument is the textual-feedback ancestor of GEPA's [[FeedbackFunction|feedback function $\mu_f$]].
- **Sidesteps the [[2402.01817-llm-modulo|LLM-Modulo]] self-verification critique** — the constraint check is external Python (possibly invoking a sub-DSPy program); the LM is only the *generator* + *refiner*, never the *verifier*.

## Conversation history: the chatbot-shaped application slice

**[[dspy-conversation-history|Managing Conversation History (DSPy tutorial)]]** scopes [[DSPy]] at the **multi-turn chatbot** application layer — the first wiki-corpus DSPy page anchored to a *tutorial* rather than a *Learn* reference or paper. Two load-bearing disclosures:

1. **[[DSPy]] does not automate conversation-history management.** [[DSPyModules|`dspy.Module`]] has no built-in inter-turn state capture. Per the tutorial: *"DSPy does not provide such functionality out of the box, meaning users are required to manage the conversation history on their own."* The developer owns the [[DSPyHistory|`dspy.History`]] instance lifecycle — construction, per-turn append, re-injection.
2. **[[DSPyHistory|`dspy.History`]] is the [[DSPySignatures|Signature]] field type** — a DSPy-special type (tier five, alongside [[DSPyImage|`dspy.Image`]]) with a `messages: list[dict[str, Any]]` attribute. Each entry carries all input + output field values for one prior turn. Declared as `history: dspy.History = dspy.InputField()` on the Signature; instantiated as `dspy.History(messages=[])` at session start; appended via `history.messages.append({"question": question, **outputs})` after each turn.

The tutorial also discloses a structural property of [[DSPyHistory|`dspy.History`]] under [[BootstrapFewShot|few-shot]] demonstration: **history-bearing [[DSPyExample|`dspy.Example`]] demos render as a single turn with the messages serialized as JSON** rather than expanded into multiple conversational turns — *"DSPy renders the history as a single message in the few-shot examples to maintain compatibility with the OpenAI standard format."* The rendering choice keeps prompt envelopes bounded under [[BootstrapFewShot]] / [[BootstrapFewShotWithRandomSearch]] / [[MIPROv2]] demo budgets and preserves the OpenAI `messages=[...]` shape the [[LiteLLM]] layer beneath [[DSPyLM|`dspy.LM`]] expects.

## Customer service agent: the multi-tool ReAct application receipt

**[[dspy-customer-service-agent|Building AI Agents — Customer Service Agent (DSPy tutorial)]]** is the wiki's canonical **end-to-end production-shaped [[react|`dspy.ReAct`]] receipt** — a seven-tool airline customer-service agent over a five-class [[Pydantic]] domain (`Date`, `UserProfile`, `Flight`, `Itinerary`, `Ticket`), driven by a two-field [[DSPySignatures|Signature]] (`user_request: str` → `process_result: str`). The tool list is split into the three production-agent categories:

| Category | Tools | Discipline |
|---|---|---|
| **Lookup** | `fetch_flight_info`, `fetch_itinerary`, `get_user_info`, `pick_flight` | Read-only; safe to retry |
| **Mutation** | `book_flight`, `cancel_itinerary` | State-changing; should be gated with [[DSPyAssert|`dspy.Assert`]] preconditions |
| **Escalation** | `file_ticket` | Hand off to human when no other tool resolves the request |

Three structural properties the tutorial makes explicit beyond the [[dspy-modules|Modules page]]'s two-tool calculator-plus-Wikipedia example:

1. **Tools are plain Python functions with docstrings + type hints** — no `dspy.Tool(...)` wrapping required when passed directly into `dspy.ReAct(..., tools=[...])`. The framework auto-wraps each callable.
2. **The user-facing Signature is independent of the tool list.** Two fields scope the user-facing interface; seven tools scope the action surface. The same Signature could host a different tool list, and vice versa.
3. **[[Pydantic]] models compose at any depth.** Tools take and return nested Pydantic objects; the [[DSPyAdapters|Adapter]] handles the serialization-and-parsing translation between LM-emitted JSON and typed Python objects. Tier three (*pydantic models*) of [[DSPySignatures|the Signatures type system]] is the central mechanism for typed agent domains.

The returned [[DSPyPrediction|`Prediction`]] carries **three fields**: `trajectory` (full think-act-observe log), `reasoning` (final-decision explanation, the same field [[ChainOfThought|`dspy.ChainOfThought`]] adds), and the user-declared `process_result`. Only the last was declared on the Signature; the first two are added by [[react|`dspy.ReAct`]]'s under-the-hood signature expansion. `dspy.inspect_history()` is the canonical debugging surface — same as the [[dspy-conversation-history]] tutorial. **Scope-limit gap**: the tutorial does **not** add [[DSPyAssertions|LM Assertions]] / hard-constraint checks inside mutation tools — a production deployment needs the [[LLMModuloFramework|LLM-Modulo]] sound-critic layer (e.g., `dspy.Assert(flight.date_time > now())` inside `book_flight`) to prevent the agent from silently creating invalid records.

Position update to the DSPy application stack (rung 4 added):

| Rung | State shape | Wiki anchor |
|---|---|---|
| 1. Single LM call | Stateless | [[DSPyPredict]] |
| 2. Single LM-program call | Module-local | [[DSPyModules]] |
| 3. Multi-turn conversation | Flat append-only `dspy.History` | [[dspy-conversation-history]] / [[DSPyHistory]] |
| 4. **Single-agent multi-tool task** | **`dspy.ReAct` + typed tool list** | **[[dspy-customer-service-agent]] / [[CustomerServiceAgent]]** |
| 5. Multi-agent collaborative discourse | Graph (mind map) | [[CoSTORM]] |
| 6. Long-horizon compound system | $\langle \Pi, \Theta \rangle$ | [[2407.10930-better-together]] / [[2507.19457-gepa]] |

Rung 4 is the **natural composition** of rungs 1–3 — a [[DSPyModules|Module]] with [[DSPyTools|tools]] (action surface) and optionally [[DSPyHistory|history]] (rung 3 composition) — and the **building block** for rung 5: a Co-STORM expert agent is internally a rung-4 single-agent multi-tool system before contributing to the cross-agent mind map.

## Custom modules: the canonical starting template

**[[dspy-custom-module|Building AI Applications by Customizing DSPy Modules (DSPy tutorial)]]** is the wiki's canonical **how-to** for the minimum-viable `class MyProgram(dspy.Module)` shape — the same composition pattern [[dspy-modules|the Modules *Learn* page]] showcases via the multi-hop `Hop` example, restated here for the non-iterative case (three sub-modules called once each). Four positions:

1. **Subclass `dspy.Module` and implement `__init__` + `forward`** — the two-method contract that mirrors PyTorch's `nn.Module`. `__init__` declares sub-modules as `self.*` attributes; `forward` runs them.
2. **`forward()` is unconstrained Python** — *"you are not limited to calling only other DSPy modules; you can also integrate any standard Python functions, such as those for interacting with Langchain/Agno agents, MCP tools, database handlers, and more."* Arbitrary Python (loops, conditionals, recursion, external API calls, retrieval, side effects) is supported.
3. **Call the module instance directly, not `forward()` explicitly** — *"the `__call__` method handles necessary internal processing before executing the `forward` logic."* The internal processing is the **trace point** for [[DSPyOptimizers|optimizer]] replay, [[MLflow]] auto-logging, [[DSPyHistory|history]] threading, and the LM-usage accounting `dspy.Prediction.get_lm_usage()` exposes.
4. **Custom modules unlock framework features** — *"putting your logic with a custom module so that you can use other DSPy features, like DSPy optimizer or MLflow DSPy tracing."* Plain-function pipelines (or inline sub-module use outside any `dspy.Module`) get **neither** — they are invisible to `named_predictors()` / `named_parameters()` introspection and to the `mlflow.dspy.autolog()` trace hook.

The worked receipt is a **three-stage [[rag|RAG]] program** — `dspy.Predict(QueryGenerator)` → `dspy.ColBERTv2(...)` Wikipedia retrieval → [[chainofthought|`dspy.ChainOfThought("question,context->answer")`]]:

```python
class RAG(dspy.Module):
    def __init__(self):
        self.query_generator = dspy.Predict(QueryGenerator)
        self.answer_generator = dspy.ChainOfThought("question,context->answer")

    def forward(self, question, **kwargs):
        query = self.query_generator(question=question).query
        context = search_wikipedia(query)[0]
        return self.answer_generator(question=question, context=context).answer
```

Five load-bearing details: (i) one sub-module uses a **class-based** [[DSPySignatures|Signature]] (`QueryGenerator`), the other an **inline string** signature — confirming both styles compose freely in the same `dspy.Module`; (ii) retrieval is a **plain Python function** wrapping `dspy.ColBERTv2(url=...)(query, k=1)`, not a sub-module — so [[DSPyOptimizers|optimizers]] do not see retrieval as a tunable parameter; (iii) the canonical public [[ColBERTv2]] endpoint is `http://20.102.90.50:2017/wiki17_abstracts` (Wikipedia 2017 abstracts, same corpus as [[hotpotqa|HotPotQA]]); (iv) `forward` **unwraps** sub-module outputs by attribute access (`.query`, `.answer`); (v) `**kwargs` in `forward(self, question, **kwargs)` is the defensive default that absorbs any metadata kwargs `dspy.Module` may inject. **First wiki-corpus DSPy tutorial to spell out the `wiki17_abstracts` endpoint URL** — every prior DSPy retrieval example assumed it.

The tutorial closes with the **string-in-string-out → structured-input-to-structured-output** operational summary of [[dspy-programming-overview|the Programming Overview's]] *writing code instead of strings* thesis, and the **bidirectional portability** claim — *"DSPy is easy to migrate to from other frameworks or vanilla SDK usage, and easy to migrate off because essentially it's just python code."* The framework boundary is unusually thin precisely because there is no DSL, no DAG, no orchestration layer.

**Position in the application stack**: this is the **template-level** anchor for **rung 2** of the stack — the canonical worked starting receipt every other rung composes from. The [[dspy-conversation-history]] tutorial adds [[DSPyHistory|history]] (rung 3); the [[dspy-customer-service-agent]] tutorial adds [[react|ReAct]] + typed [[Pydantic]] tools (rung 4); both extend rung 2's `__init__` + `forward` template.

| Tutorial | Stack rung | What it adds beyond rung 2 |
|---|---|---|
| [[dspy-custom-module]] | **2 (template)** | The minimum-viable `__init__` + `forward` shape; the canonical [[ColBERTv2]] endpoint; the [[MLflow]] tracing recipe |
| [[dspy-rag-tutorial]] | **2 (measurable)** | Embedding retrieval ([[openai|OpenAI]] `text-embedding-3-small`) + a measurable benchmark ([[RAGQAArenaTech]]) + end-to-end [[MIPROv2|MIPROv2]] optimization (42→55.5→**61.1%** [[SemanticF1]]) — the wiki's first DSPy receipt combining all four [[DSPyProgrammingModel|Programming-Model artifacts]] |
| [[dspy-conversation-history]] | 3 | [[DSPyHistory|`dspy.History`]] field + per-turn append discipline |
| [[dspy-customer-service-agent]] | 4 | [[react|`dspy.ReAct`]] + typed [[Pydantic]] tool list (lookup / mutation / escalation) |
| [[dspy-tutorial-math]] | **2 (measurable)** | Single-signature [[chainofthought|`dspy.ChainOfThought("question -> answer")`]] over the [[MATH-benchmark|MATH]] algebra subset (350+350) + [[MIPROv2|MIPROv2]] `auto="medium"` with GPT-4o teacher (74.0% → **88.57%**, +14.6 pts) — **first wiki receipt where CoT is the entire program** (no retrieval, no tools, no history); **first DSPy receipt benchmarked on math reasoning** |

The five DSPy tutorials together cover the application stack from `dspy.Module` template (rung 2; shape-anchored, measurement-anchored RAG, and measurement-anchored single-step reasoning) through `dspy.History` (rung 3) and `dspy.ReAct` (rung 4) — the **multi-agent collaborative discourse** (rung 5) anchor remains [[CoSTORM]] (research paper, not tutorial) and the **long-horizon compound system** (rung 6) anchor remains the [[2407.10930-better-together|BetterTogether]] / [[2507.19457-gepa|GEPA]] optimizer line.

## RAG: the canonical end-to-end measurable receipt

**[[dspy-rag-tutorial|DSPy Tutorial — Retrieval-Augmented Generation]]** is the **fourth wiki-corpus DSPy tutorial** and the **first to combine all four [[DSPyProgrammingModel|Programming-Model artifacts]]** ([[DSPySignatures|Signatures]] / [[DSPyModules|Modules]] / [[DSPyMetrics|Metrics]] / [[DSPyOptimizers|Optimizers]]) on a single task with measurable per-stage gains. The tutorial walks a three-stage performance ladder on [[RAGQAArenaTech|RAG-QA Arena Tech]] (~1K technical QA pairs, 200/300/500 train/dev/test):

| Program | [[SemanticF1]] | Gain |
|---|---|---|
| Baseline [[chainofthought|`dspy.ChainOfThought`]] (no retrieval) | ~42% | — |
| [[rag|RAG]] module wrapping [[chainofthought|CoT]] over `k=5` embedding-retrieved docs | ~55.5% | **+13.5** |
| [[MIPROv2|`dspy.MIPROv2`]] `auto="medium"` over the RAG module | **~61.1%** | **+5.6** (cumulative **+19**) |

Three load-bearing details: (i) **the metric is [[SemanticF1]]** — a reference-based [[llmasjudge|LLM-as-judge]] DSPy program that decomposes both gold and predicted answers into atomic claims and grades coverage, instantiating the [[dspy-metrics|AI-feedback metric pattern]] from page 11; (ii) **retrieval uses [[openai|OpenAI]] `text-embedding-3-small`** over a 28K-document downsampled technical corpus, each doc truncated to 6K characters — the **first wiki-corpus DSPy RAG receipt to use dense embeddings** (the [[dspy-custom-module|Custom Module tutorial]] used [[ColBERTv2]] late interaction); (iii) **`auto="medium"` costs ~$1.50 and runs in ~20–30 min** on this dataset — the first concrete instance of [[dspy-optimizers|the Optimizers page's]] *$2 typical / cents-to-tens-of-dollars range* operating envelope on a multi-stage RAG program.

**Cross-receipt convergence**: this is the **second worked instance** of the [[MIPROv2|MIPROv2 Receipt 2 pattern]] (the first was the [[dspy-optimizers|Optimizers page's]] StackExchange subset, 53→61%). **Two independent benchmarks now converge on ~61% [[SemanticF1]] as the post-optimization ceiling** for a single-hop CoT-based RAG on gpt-4o-mini with `auto="medium"` — strong evidence that the operating envelope is a property of the optimizer × model × architecture × metric combination, not idiosyncratic to either dataset.

The tutorial's **further-improvement menu** names five axes for going beyond 61.1%: alternative system architectures ([[hotpotqa|multi-hop]] retrieval), different optimizer families ([[GEPA]] / [[BetterTogether]]), **inference-time scaling through ensembling** ([[DSPyMajority|`dspy.majority`]]), **model distillation** to reduce serving cost ([[BootstrapFinetune|`dspy.BootstrapFinetune`]]), and **iterative metric refinement** based on actual system outputs (the [[DSPyEvaluation|recursive-self-improvement claim]] at the metric layer). Each of these has a paper-anchored or tutorial-anchored sibling already in the wiki.

**Mints 2 concept pages** — [[SemanticF1]] (promoted from inline mention on [[MIPROv2]] / [[dspy-optimizers]] to a dedicated concept page) and [[RAGQAArenaTech]] (the dataset). Updates [[rag]] / [[MIPROv2]] / [[MLflow]] in place.

**[[MLflow]] integration**: the tutorial supplies the **first wiki-corpus DSPy-specific MLflow tracing recipe** — a four-step opt-in (`pip install mlflow>=3.0.0` → launch UI → `mlflow.set_tracking_uri(...)` + `set_experiment("DSPy")` → `mlflow.dspy.autolog()`). The fourth step is the bridge: every `__call__` on a [[DSPyModules|`dspy.Module`]] subclass after this point produces a trace span in the MLflow backend. [[Databricks]] owns [[MLflow]] — the tutorial is the second [[Databricks]]-touchpoint in the DSPy line, after [[MateiZaharia]]'s Databricks affiliation as senior author on [[2406.11695-mipro|MIPRO]] / [[2507.19457-gepa|GEPA]].

## From [[hands-on-llm-ch07-advanced-text-generation|*Hands-On LLMs* Ch 7]]

Ch 7 of *Hands-On LLMs* names DSPy explicitly as one of the *"newer frameworks of note"* alongside Haystack — *"LangChain is one of the earlier frameworks that simplify working with LLMs through useful abstractions. Newer frameworks of note are DSPy and Haystack."* The chapter does **not** compare them in depth — Ch 7 commits to [[LangChain]] for pedagogical continuity — but DSPy is named as the canonical alternative.

The Ch 7 [[LangChainAgent|`create_react_agent` + `AgentExecutor`]] receipt is the **LangChain-native counterpart** to DSPy's `dspy.ReAct`. Both operationalize Yao et al. 2022's [[react|ReAct]] framework, but with different ergonomics: `dspy.ReAct(Signature, tools=[...])` is **signature-parameterized** (typed I/O at the Signature level, `Prediction.trajectory` introspection); LangChain's `create_react_agent(llm, tools, prompt) + AgentExecutor` is **template-parameterized** (free-form text + a canonical ReAct prompt template, `verbose=True` prints the trajectory inline). See [[react]] for the detailed comparison and [[LangChainAgent]] for the LangChain-side receipt.
