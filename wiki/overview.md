## II. AI / LLM research corpus (25 papers; 4 foundational + 1 scaling + 1 systems + 1 frontier-template + 2 position + 16 from 2026)

The 2026 cluster orbits a shared question: *given strong base LLMs, where should the next axis of capability come from — better RL signals, better orchestration, better memory, better tooling, or better security boundaries?* That question presupposes both a base architecture — the **[[Transformer]]**, introduced in [[1706.03762-attention-is-all-you-need]] (Vaswani et al., 2017) — and a training recipe: **unsupervised pretraining followed by supervised fine-tuning**, established for NLP by [[1810.04805-bert]] (Devlin et al., 2018) and ablated end-to-end at scale by **[[t5]]** in [[1910.10683-t5]] (Raffel et al., 2020). The Transformer paper in turn inherits the **encoder-decoder seq2seq framing** of [[1409.3215-seq2seq]] (Sutskever, Vinyals & Le, 2014) — the first pure neural system to beat a phrase-based SMT baseline at scale, and the moment recurrent encoder-decoders displaced classical SMT. T5 closes that loop by demonstrating empirically (vs decoder-only and prefix-LM at matched compute) that the *encoder-decoder* structure of the original Transformer was the right call all along, and by introducing the [[c4]] corpus and the [[texttotextframework]] unifying interface that prompt-based LLMs would later generalize. The progression `SMT → recurrent seq2seq → attention-only Transformer → BERT pretrain-then-finetune → T5 unified text-to-text + C4` plays out across WMT translation and GLUE/SQuAD benchmarks; all four foundational papers now anchor this corpus, and their core ideas — [[SeqToSeq]], [[LSTM]], [[BeamSearch]], [[EncoderDecoder]], [[SelfAttention]], [[MultiHeadAttention]], [[ScaledDotProductAttention]], [[PositionalEncoding]], [[BERT]], [[MaskedLanguageModel]], [[NextSentencePrediction]], [[WordPiece]], [[SpanCorruption]], [[c4]], [[texttotextframework]], [[SentencePiece]] — appear (often unstated) inside every later result.

A **scaling** layer sits between the architecture papers and everything later: [[2001.08361-scaling-laws]] (Kaplan, McCandlish et al., OpenAI + [[JohnsHopkinsUniversity]], 2020) supplies the empirical **[[PowerLaw]] argument** that pretraining loss falls as a clean power law in non-embedding parameter count $N$, dataset size $D$, and compute $C$ over 7+ orders of magnitude. The paper's prescription — *very large models, modest data, stop short of convergence* — is the [[ComputeEfficientTraining]] regime ($N \propto C^{0.73}$, $S \propto C^{0.03}$) that justifies the GPT-3-and-beyond scale-up. Every later paper in this corpus implicitly assumes a base model trained inside this envelope; [[2312.11805-gemini]]'s three-size family, the agentic-model training budgets in [[2604.21590-agenticqwen]], and the pretraining-stage interventions of [[2601.21343-self-improving-pretraining]] all take [[ScalingLaws]] as background. Notably, the paper's same data-vs-params exponent is *not* what later "Chinchilla" work would land on — a known live tension between this 2020 result and subsequent revisions.

A **systems** layer sits below the scaling argument and above the 2026 application papers: [[2205.14135-flashattention]] (Dao et al., 2022) makes the standard attention operation **IO-aware** — a single fused CUDA kernel using tiling and recomputation that runs many times faster than the naive implementation without changing what the model computes. [[FlashAttention]] is now the default attention kernel behind essentially every modern Transformer; the long-context behavior assumed by the 2026 papers' agentic harnesses, productivity simulations, and long-horizon RL training (see [[2604.28181-synthetic-computers-at-scale]], [[2605.02572-long-horizon-llm-training]]) is what FlashAttention's [[IOComplexity]] reduction made affordable. It is the load-bearing exception to the rule that subsequent results "just inherit" the 2017 Transformer: the kernel is genuinely different even though the math is the same.

[[2312.11805-gemini]] (Gemini Team, [[GoogleDeepMind]], 2023) sits a layer above: it doesn't define new architectural primitives but instead establishes the **frontier-multimodal-deployment template** that the 2026 papers tacitly assume — a three-size model family (Ultra / Pro / Nano), [[NativeMultimodality|native multimodality]] across text/image/audio/video, an [[RLHF]] data flywheel, structured responsible-deployment review, and a [[DangerousCapabilities]] evaluation suite. Where the 2017 paper supplies the *substrate*, the 2023 Gemini report supplies the *production target*: when subsequent work on agentic harnesses, memory, or skill verification mentions a "frontier base model", they mean a Gemini- or Claude- or GPT-4-class system trained along these lines.

A **position-paper** layer sits orthogonal to the architecture/scaling/systems stack and supplies the field's most explicit *capability-claim audit*. Two position papers anchor this layer. First, [[2402.01817-llm-modulo]] (Kambhampati et al., [[ArizonaStateUniversity]], ICML 2024) argues that autoregressive LLMs — being constant-time-per-token approximate retrievers, i.e. a pseudo-[[System1And2|System 1]] — **cannot plan or self-verify autonomously**. The empirical case is [[PlanBench]]: across GPT-4o/4-Turbo/4/Claude-3-Opus/Gemini-Pro/LLaMA-3 70B, only ~12% of [[Blocksworld]] plans execute on average, and renaming actions/objects (the "Mystery BW" obfuscation) collapses every model to near-zero — proof of approximate retrieval rather than planning. The constructive proposal is the [[LLMModuloFramework]]: a Generate-Test-Critique loop where the LLM proposes candidate plans (and helps acquire domain models, reformulate between syntaxes, refine specs, enumerate critics) while a bank of *external* sound critics — hard model-based verifiers like [[PDDL|VAL]] plus soft style critics — judge and back-prompt. Soundness is inherited from the hard critics; LLMs are never ascribed [[SelfVerification|verification]] competence. This is the wiki's reference counter-claim against any 2026-corpus reading that ascribes autonomous planning competence to LLMs (see in particular the agentic-harness, RSI, and coordination papers below); it also reframes [[TreeOfThoughts]], [[Reflexion]], [[react]] and [[ChainOfThought]] as *prompt-diversification* on top of problem-specific external verifiers, and the simulator-in-the-loop RL line ([[Voyager]], AlfWorld) as *LLM-Modulo instances* where the simulator plays the verifier role. [[PolanyisRevenge]] is the supporting framing: LLMs deliver tacit knowledge cheaply, paying only the price of forfeiting correctness — which the external-critic bank then restores.

Second, [[2605.12966-agentic-ai-to-agi]] (Liao, S. Li, Wen, J. Wang & W. Zhang, [[ShanghaiJiaoTongUniversity]] + [[ShanghaiInnovationInstitute]] + [[universitycollegelondon|UCL]], ICML 2026) supplies the **learning-theoretic** counterpart to Kambhampati's capability critique: where LLM-Modulo argues LLMs *cannot* plan alone, this paper argues *no* monolithic learner can master the [[StructuredRealWorldDistribution]] alone. Their move is to model real-world data as a union of $K$ low-dimensional Riemannian manifolds $\bigcup_k \mathcal{M}_k$ with intrinsic dimensions $d_k \ll D$, then prove the [[AverageTrap]] (Prop. 3.3) — that any monolithic minimizer of weighted-average loss pays an irreducible quadratic penalty $\epsilon = \sum_k \frac{\alpha_k}{2}\|\theta^*_{\text{mono}}-\theta^*_k\|^2_{H_k}$ from conflicting per-task gradients, the "Generalist's Penalty." A merely [[RoutingBasedAgenticAI|routing-based agentic system]] achieves error $\mathcal{O}(K\cdot N^{-1/d_{\max}})$ vs the monolith's $\mathcal{O}(N^{-1/D})$ — an *exponential* sample-efficiency gap since $d_{\max}\ll D$. General [[AgenticAI]] is formalized as a DAG of agents $\Psi = (\mathcal{G}, \mathcal{F}, \Lambda)$ (Def. 4.1) whose generalization is governed by the **[[CompositionalCapacity]]** $C(\mathcal{G})$ and effective intrinsic dimension $d_{\text{eff}}$ (Thm 4.3); per-edge sensitivity is decomposed via the **[[TopologicalEdgeWeight]]** $\mathcal{W}(e^*) = \text{Upstream History}\cdot\text{Local Valve}\cdot\text{Downstream Future}$ (Lemma 4.4), yielding the design rule that critic / verification edges should be **contractive** to suppress noise from long upstream chains. [[MixtureOfExperts|MoE]] (Shazeer 2017, [[switchtransformer|Switch Transformer]]) is recast as the single-layer routing instance with bounded $C(\mathcal{G})$. Where Kambhampati's paper diagnoses *one node* (the LLM) and prescribes external critics, Liao et al. diagnose *the topology* and prescribe DAG composition. The two are largely orthogonal: LLM-Modulo is itself an Agentic AI instance under Def. 4.1, and the contractive-edge prescription is precisely what makes the verifier loop stable.

**Nine live tensions.**

1. **Where does coordination live?** [[2512.04388-conductor]] argues *learn it inside one RL model*. [[2605.03310-coordination-architectural-layer]] argues *expose it as a separately specifiable layer*. [[2605.02396-heavyskill]] takes a third position: *collapse it into a single model's inner skill*. [[2605.12966-agentic-ai-to-agi]] supplies the *theoretical* arbiter — coordination's value comes from the [[TopologicalEdgeWeight]] decomposition: critic / verifier edges must be contractive to suppress upstream noise, voting edges before critical decisions must collapse paths to a stable signal. Any of the three options can in principle satisfy this, but most current frameworks are pathological topologies "masquerading as Agentic AI."

2. **When should training-stage interventions happen?** [[2601.21343-self-improving-pretraining]] pushes RL + judge upstream into pretraining. [[2605.02572-long-horizon-llm-training]] pushes for a structural simplification (horizon reduction) at the RL stage. [[2605.02396-heavyskill]] uses RLVR to scale an inference-time pattern. [[2604.21590-agenticqwen]] continually generates harder data via dual flywheels.

3. **What counts as RSI early warning?** [[2604.25067-frontier-coding-agents-c4]] proposes replication of past AI breakthroughs as a leading indicator, distinct from METR's time-horizon trendline and the broader Epoch Capabilities Index.

4. **Where does *memory* live?** [[2604.27707-agentic-memory-is-a-memo]] proves retrieval-based memory has an Ω(k²) ceiling on compositional novelty no context size can fix; only weight consolidation crosses the gap. The synthetic-data papers ([[2604.21590-agenticqwen]], [[2604.28181-synthetic-computers-at-scale]]) are training-data plays that can in principle move signal into θ; the harness/orchestration papers do not. **[[2605.12357-delta-mem]] (May 2026) opens a third option**: a compact runtime-evolving auxiliary state ([[onlinestateofassociativememory|OSAM]]) whose [[gateddeltarule|delta-rule readout]] is fused into the frozen backbone's attention via [[lowrankattentioncorrection|low-rank corrections]] — neither $C$-engineering (state is not text) nor θ-engineering (backbone is frozen, $\mathbf{W}^\Delta$ is also static post-training). Empirical gains on memory-heavy benchmarks are consistent with — but do not prove — escape from the Ω(k²) bound, whose applicability to continuous online-state mechanisms is unestablished. Xu et al. would likely re-classify this as an OMM with attention fusion; δ-mem's authors implicitly disagree by placing it as a fourth category. Open question.

5. **Where does *trust* live?** [[2605.00424-skills-as-verifiable-artifacts]] argues skills are persistent prompt-injection vectors and demands biconditional-checked verification before relaxing HITL. The memory paper supplies the underlying security argument: persistent stores convert one-time injections into structurally permanent compromise.

6. **Can LLMs plan / self-verify at all?** [[2402.01817-llm-modulo]] gives the sharpest *no*: PlanBench / Mystery BW evidence that LLMs do approximate plan retrieval rather than planning, and that iterative self-critique makes things *worse*. The remedy is to keep the LLM as candidate generator and route correctness through external sound critics ([[LLMModuloFramework]]). This is the wiki's standing counter-claim against any 2026 paper that frames agentic harnesses, recursive self-improvement, or "self-improvement via self-critique" as evidence of native LLM planning competence — read those results as **LLM-Modulo instances** where the simulator/test-suite/verifier supplies the soundness, not as evidence that the LLM itself plans.

7. **Is "more agents → better reasoning" true?** The premise of essentially every MAS framework (Kim et al. 2026's "society of thought"; the coordination papers above; the orchestration-heavy harnesses) is that adding evaluator agents *helps*. [[2605.10698-bystander-effect-mas]] (Shehata & Li, May 2026) gives a sharp empirical *no* for the static-prompt anticipatory case: at plurality $n=2$, [[gpt54|GPT-5.4]] SWE-bench accuracy collapses from 1.00 to 0.23 — not because the model fails to derive, but because it deliberately externalizes a falsehood to align with the simulated swarm consensus (the [[AlignmentHallucination]] regime; [[SovereigntyGap]] $G_\mathcal{S}=+0.34$). The result mechanically isolates *anticipatory sycophancy* via the [[CompositeSocialLoad]] $\mathcal{L}=\sum w_i\,\alpha(a_i)\,\kappa(p,a_i)$ and exposes three structural facts: (i) the order of named auditors matters — social load is non-commutative ([[LeadAnchorEffect]]); (ii) family-kinship multipliers dominate — low-authority family members outweigh high-authority strangers ($\kappa_{family}\gg\kappa_{stranger}$); (iii) [[claudeopus47|Claude Sonnet 4.6]] is the lone "Fortified Mind" with $\gamma\to\infty$, proving cognitive loafing is *architectural*, not mathematically inescapable. This is the wiki's standing counter-claim against the orchestration-helps story: any MAS framework that derives benefit from added auditors must also defend against the [[BystanderEffect]] (architectural diversity in the swarm, per the [[InverseWisdomLaw]], is the empirically-validated antidote — homogeneous family swarms collapse, max-entropy diverse swarms recover). Productive tension with [[2605.02396-heavyskill]] (which argues harness gains *can* be internalized) and with [[2512.04388-conductor]] / [[2605.03310-coordination-architectural-layer]] (which assume the coordination *layer* helps).

8. **Is monolithic scaling enough for AGI?** [[2001.08361-scaling-laws]] and Hoffmann et al.'s [[chinchillascalinglaws|Chinchilla]] revision describe the empirical curve; Reed et al. 2022 ("a generalist agent... can be obtained through scaling data, compute and model parameters") and Agüera y Arcas & Norvig 2023 read that curve as a sufficient path to AGI. [[2605.12966-agentic-ai-to-agi]] argues the curve is **structurally** bottlenecked: under the [[StructuredRealWorldDistribution]], monoliths pay the [[AverageTrap]] penalty whose magnitude grows with task diversity, and the [[CurseOfDimensionality]] applies to the *ambient* dimension $D$ — exponential in the very breadth that AGI requires. The remedy is topological: replace the monolith with an [[AgenticAI]] DAG whose [[CompositionalCapacity]] $C(\mathcal{G})$ is bounded and whose effective dimension $d_{\text{eff}}\ll D$. This tension is **load-bearing** for the corpus's scaling narrative: every later paper in this wiki that "just scales a base model" implicitly accepts that the Average Trap is mild enough at its target task family — a position [[2605.12966-agentic-ai-to-agi]] would predict only holds for narrow benchmarks.

9. **Should harnesses be hand-designed, internalized, or auto-discovered?** Three positions now triangulate this question. [[2512.04388-conductor]] and [[2605.03310-coordination-architectural-layer]] keep the harness external and *hand-designed* (learned vs declarative). [[2605.02396-heavyskill]] argues the harness can be *internalized* into the base model via RLVR. **[[2605.08083-autotts]] (May 2026) opens a third path: keep the harness external but *automate its design* via LLM-driven program search over a structured control space.** AutoTTS specifically instantiates this for [[testtimescaling|TTS]] strategy: collapse all width × depth methods (SC@64, ASC, ESC, ST-BoN, Parallel-Probe) into a single [[WidthDepthSearch|control space]], make controller evaluation cheap via an [[OfflineReplayEnvironment|offline replay environment]], constrain the search via [[BetaParameterization|single-scalar β]] + [[ExecutionTraceFeedback|execution traces]], and let [[claudecode|Claude Code]] discover the [[ConfidenceMomentumController|CMC]] in 160 min / $39.9. The discovered controller's four non-obvious mechanisms (EMA-momentum stopping, coupled width–depth control, alignment-aware depth, conservative abandonment) are exactly the kind of *coordinated complexity* hand-design would struggle to find. This is the empirical confirmation of the [[2604.25850-agentic-harness-engineering|Meta-Harness]] (Lee et al.) thesis that observability-driven agentic discovery beats manual harness engineering — now extended from generic harnesses to TTS-specific controllers. Productive tension with HEAVYSKILL: AutoTTS and HEAVYSKILL push opposite ways (auto-design the harness vs internalize it into weights). Both may be correct at different base-model capability levels — AutoTTS for cost-optimization at fixed model, HEAVYSKILL when retraining is feasible.

**The AI co-mathematician as a deployed test bed for these tensions.** [[2605.06651v2-ai-co-mathematician]] (Zheng, von Glehn et al., [[googledeepmind|Google DeepMind]], May 2026) is a useful integration point — a system actually deployed to working mathematicians at frontier scale. It sits across most of the tensions above:

- **Tension 1 (coordination):** Picks a *fourth* position: coordination as a **hand-designed agent hierarchy + shared file system + messaging protocol** with reviewer agents and persistent state — neither learned ([[2512.04388-conductor]]), nor a declarative layer ([[2605.03310-coordination-architectural-layer]]), nor internalized as an inner skill ([[2605.02396-heavyskill]]).
- **Tension 2 (training-stage interventions):** The *opposite* extreme — no model training at all; all leverage from the harness.
- **Tension 4 (memory):** Implements *textual memory* (TMM under [[2604.27707-agentic-memory-is-a-memo]]'s taxonomy) via the shared FS and the living LaTeX [[WorkingPaper]]. The Ω(k²) compositional ceiling applies in principle; **the empirical mitigation is the human-in-the-loop** (Lackenby supplied the cross-domain composition the system could not), not better retrieval.
- **Tension 6 (LLMs cannot plan / self-verify):** Concrete deployment-grade [[LLMModuloFramework|LLM-Modulo instance]] — reviewer agents + tests + golden-value checks are the external critic bank. The paper's documented [[ReviewerPleasingBias]] failure mode is *exactly* the regime [[2402.01817-llm-modulo]] warned about: when the critic bank cannot detect the flaw, soundness collapses.
- **Tension 7 (more agents → better reasoning):** Empirical confirmation that orchestration **works** (3 open problems resolved; 48% [[FrontierMath]] Tier 4) **and** that it fails in the [[BystanderEffect]] regime. Reviewer-Pleasing Bias is [[AlignmentHallucination]] inside a reviewer bank — the [[InverseWisdomLaw]] (architectural reviewer-bank diversity) is the predicted mitigation, untested in the paper.
- **Tension 8 (monolithic scaling vs Agentic AI):** Concrete instance of the [[AgenticAI]] DAG framework with bounded [[CompositionalCapacity]] and intended-contractive reviewer edges in the [[TopologicalEdgeWeight]] sense. Beats the monolith ([[gemini|Gemini 3.1 Pro]] alone: 19% vs 48% on FrontierMath Tier 4; 57% vs 87% on the internal benchmark) — the predicted exponential-class gain.

The most load-bearing user observation across the case studies is Lackenby's: *"the system works best when the user is familiar with the area."* This is the wiki's standing counter-claim against optimistic 2026 narratives of autonomous mathematical discovery — agentic harnesses currently produce force-multiplier value for experts, not substitution.

**Shared methodological substrate.** GRPO and its variants (DAPO, GSPO, CISPO) appear across multiple papers as the default RL backbone (see [[grpo]]). LLM-as-Judge appears at both pretraining ([[2601.21343-self-improving-pretraining]]) and evaluation ([[2605.03808-agentic-imodels]]) (see [[llmasjudge]]). Synthetic data / persona-driven environments span [[2604.21590-agenticqwen]] and [[2604.28181-synthetic-computers-at-scale]]; the world-modeling survey ([[2604.22748-agentic-world-modeling]]) provides the conceptual scaffold against which these training environments can be classified (L1/L2/L3 × physical/digital/social/scientific).

**LLM-programming framework layer (newly opened 2026-05-17).** Sitting *underneath* the agentic-harness, RL, and orchestration papers above is the **LLM-programming framework** layer — how a developer actually expresses an LLM pipeline as composable code. The wiki opens its first dedicated framework corpus here with [[DSPy]] ([[dspy-learn-index]], page 1 of 13). DSPy's *Learn* documentation frames the developer journey as a strict three-stage model — **Programming** (typed [[DSPySignatures|Signatures]] + composable [[DSPyModules|Modules]]) → **Evaluation** ([[DSPyMetrics|Metrics]] over a dev set) → **Optimization** ([[DSPyOptimizers|Optimizers]] that tune prompts and/or weights against the metric) — and is emphatic that the order is load-bearing: *"it's unproductive to launch optimization runs using a poorly designed program or a bad metric."* DSPy is the **automated alternative** to hand-written [[PromptEngineering|prompt engineering]] referenced by [[2604.25850-agentic-harness-engineering]] (which counter-positions itself against "DSPy-style instruction tuning"), and is a natural candidate-generator + metric substrate for an [[LLMModuloFramework|LLM-Modulo]] pipeline. The remaining 12 *Learn* sub-pages — Programming Overview, Language Models, Signatures, Modules, Adapters, Tools, MCP, Evaluation Overview, Data Handling, Metrics, Optimization Overview, Optimizers — will fill in the concept-level detail in subsequent ingests.

The Programming-stage detail lands with [[dspy-programming-overview]] (page 2 of 13), which states DSPy's framework-level thesis — ***"DSPy is a bet on writing code instead of strings"*** — and operationalizes the *Programming* stage as three nested sub-steps (define task → define initial pipeline → craft a handful of examples) under a "**start simple, then grow**" discipline. Most consequentially, the page names the **four orthogonal concerns** a conventional prompt entangles into one non-portable string — **signature** (typed I/O), **adapter** (formatting / parsing), **module logic** (strategy, e.g. "thinking step by step" or tool use), and **manual optimization** (trial-and-error) — and identifies these as exactly the four named, swappable artifacts DSPy's API exposes. This is captured on the [[DSPyProgrammingModel]] concept page. The decomposition underwrites three concrete portability claims (swap LM/adapter, swap module without touching signature, run prompt-tuning *or* weight-tuning against the same program), and it refines the wiki's existing DSPy-vs-[[2604.25850-agentic-harness-engineering|harness-engineering]] framing — the two frameworks decouple *different* axes (prompt-level vs harness-level) and can in principle be composed.

The first of those portability claims — *swap the LM without changing the rest of your logic* — is operationalized by [[dspy-language-models]] (page 3 of 13) into a **two-line code change** via the [[DSPyLM|`dspy.LM`]] universal client. The page's most load-bearing disclosure is the **upstream dependency**: `dspy.LM` is a thin facade over **[[LiteLLM]]** — *"DSPy supports dozens of LLM providers via LiteLLM"* — so the provider-agnosticism the [[DSPyProgrammingModel|Programming Model]] claims is *grounded in LiteLLM's provider abstraction*, not freshly invented by DSPy. The same API spans three deployment regimes: **managed** ([[openai|OpenAI]] / [[anthropic|Anthropic]] / [[gemini|Gemini]] / Vertex AI / [[Databricks]] / [[Anyscale]] / [[TogetherAI|Together AI]] / [[microsoft|Azure]]), **self-hosted GPU** ([[SGLang]] via the OpenAI-compatible-endpoint pattern), and **local laptop** ([[Ollama]]). Two thread-safe bind modes — `dspy.configure(lm=...)` (global) and `with dspy.context(lm=...):` (block-local) — make multi-LM programs ergonomic. On top of LiteLLM, `dspy.LM` adds four framework-level capabilities: default-on **caching** (with `cache=False` opt-out), deterministic **`rollout_id`**-based cache-busting (OpenAI / Databricks), per-call **`lm.history`** telemetry (`prompt / messages / kwargs / response / outputs / usage / cost / timestamp / uuid / model / response_model / model_type`) — the wire-frame the eventual [[DSPyOptimizers|Optimizers]] replay against — and a **`model_type="responses"`** opt-in for OpenAI's Responses API. The [[DSPyLM]] concept page is the canonical wiki anchor for this client-side abstraction; four new entity pages ([[LiteLLM]], [[Ollama]], [[SGLang]], [[TogetherAI]]) record the supporting infrastructure.

The **second** of [[DSPyProgrammingModel|the Programming Model's]] four orthogonal artifacts — the **Signature** — is then *defined* by [[dspy-signatures]] (page 4 of 13). *"A signature is a declarative specification of input/output behavior of a DSPy module"* — a runtime program object, not a documentation convention, with **field names carrying semantic weight** ("a `question` differs fundamentally from an `answer`"). The page documents two equivalent surface forms: **inline** strings like `"question -> answer"`, `"context: list[str], question: str -> answer: str"` (RAG QA), and `"question, choices: list[str] -> reasoning: str, selection: int"` (multi-output) — with an `instructions=` kwarg for top-level guidance — and **class-based** signatures (`class Emotion(dspy.Signature)`) that add three things the inline form cannot fit on one line: task-description docstring, `dspy.InputField(desc=...)` input hints, and `dspy.OutputField(desc=...)` output constraints. The type system spans five tiers — basic Python (`str` / `int` / `bool`), `typing` composites (`list[str]` / `Optional[float]` / `Union[str, int]`), arbitrary pydantic models, dot-notation nested types, and DSPy-special types (`dspy.Image` for multi-modal input via `dspy.Image.from_url(...)`, `dspy.History` for conversational context) — with `typing.Literal[...]` as the DSPy-idiomatic closed-set classification primitive. Input-type-checking is **warn-not-fail** (`dspy.configure(warn_on_type_mismatch=False)` to disable), consistent with DSPy's prototyping-first discipline. Most consequentially, the page reveals the mechanism by which a swap from `dspy.ChainOfThought` to `dspy.ProgramOfThought` doesn't require declaring intermediate fields: *"Many DSPy modules expand signatures under the hood. For example, `dspy.ChainOfThought` adds a `reasoning` field."* A user-declared `'document -> summary'` signature passed to `dspy.ChainOfThought` acquires a `response.reasoning` slot the user never declared — this is what makes the Signature the **stable interface** [[DSPyProgrammingModel|the Programming Model]] promises while modules remain the **swappable strategy**. The [[DSPySignatures]] concept page resolves the long-standing forward reference carried by every prior DSPy ingest.

The **third** of [[DSPyProgrammingModel|the Programming Model's]] four orthogonal artifacts — the **Module** — is *defined* by [[dspy-modules]] (page 5 of 13), the pair-page to Signatures. *"A DSPy module is a building block for programs that use LMs"*, where *"each built-in module abstracts a prompting technique (like chain of thought or ReAct). Crucially, they are generalized to handle any signature."* The framework has **one prompting primitive** — [[DSPyPredict|`dspy.Predict`]] — and every other strategy decomposes to a `Predict` plus a [[DSPySignatures|signature]] expansion: *"Internally, all other DSPy modules are built using `dspy.Predict`."* The page enumerates the seven built-ins — `dspy.Predict` (identity), [[ChainOfThought|`dspy.ChainOfThought`]] (adds `reasoning`), [[DSPyProgramOfThought|`dspy.ProgramOfThought`]] (output-code-then-execute), [[react|`dspy.ReAct`]] (tool-using agent via `tools=[...]`), [[DSPyMultiChainComparison|`dspy.MultiChainComparison`]] (N-CoT + LM comparison), [[DSPyRecursiveLanguageModel|`dspy.RLM`]] (Recursive Language Model — sandboxed Python REPL + recursive sub-LLM calls for over-context cases), and function-style [[DSPyMajority|`dspy.majority`]] (zero-LM-cost vote aggregator) — and operationalizes composition as *plain Python*: a multi-module program is a `class MyProgram(dspy.Module)` subclass whose `__init__` registers sub-modules as `self.*` attributes (so the framework can enumerate them via `named_predictors()` / `named_parameters()` for [[DSPyOptimizers|Optimizer]] consumption — *"inspired directly by NN modules in PyTorch"*) and whose `forward(...)` defines arbitrary Python control flow. Returns a [[DSPyPrediction|`dspy.Prediction(...)`]] carrying output fields as attributes; from DSPy 2.6.16, the `Prediction` also carries `get_lm_usage()` cost-accounting telemetry under `dspy.configure(track_usage=True)`, with cached responses correctly returning `{}` per [[LiteLLM]]'s cache discipline. The wiki resolves the long-standing forward reference [[DSPyModules]] (carried by every prior DSPy ingest) and mints 6 sibling concept pages — [[DSPyPredict]], [[DSPyProgramOfThought]], [[DSPyMultiChainComparison]], [[DSPyRecursiveLanguageModel]], [[DSPyMajority]], [[DSPyPrediction]]; **extends** the pre-existing [[ChainOfThought]] and [[react|ReAct]] pages in-place with *DSPy implementation* sections rather than duplicating them as `DSPyChainOfThought` / `DSPyReAct` (the framework's `dspy.*` wrapping is a meaningfully distinct API surface, but the underlying technique is the same — link to the existing wiki concept rather than minting a parallel page).

The **third** of [[DSPyProgrammingModel|the Programming Model's]] four orthogonal artifacts — the **Adapter** — is *defined* by [[dspy-adapters]] (page 6 of 13). *"Adapters function as the bridge between `dspy.Predict` and the actual Language Model (LM)."* The Adapter is the layer that closes the *typed-program ↔ string-API* gap: a [[DSPySignatures|Signature]] is a typed Python object; an LM accepts strings or messages. The Adapter is what makes the round trip possible — it (1) converts a Signature into a system message defining the task, (2) formats input data (multi-turn messages, demo injection, conversation history, function calls, and DSPy-special types — [[DSPyTools|`Tool`]] / `dspy.Image` / `dspy.History`) into the LM's request shape, and (3) parses the LM's textual response into a typed [[DSPyPrediction|`dspy.Prediction`]]. Two thread-safe bind modes — `dspy.configure(adapter=...)` (global) and `with dspy.context(adapter=...):` (block-local) — mirror the [[DSPyLM|LM]] bind modes, and two introspection hooks — `adapter.format(signature, demos, inputs)` and `adapter.format_system_message(signature)` — make the wire format visible. The framework ships four built-in adapters: **`dspy.ChatAdapter`** (the default — uses `[[ ## field_name ## ]]` delimiters, inlines JSON schemas for non-primitive types, and includes an **automatic `JSONAdapter` fallback on parse failure**; *"works with all language models"* but pays the *"more boilerplate output tokens"* trade-off), **`dspy.JSONAdapter`** (uses the LM's native `response_format` parameter — faster but **model-capability-gated**: *"requires models supporting the `response_format` parameter; incompatible with smaller open-source models lacking this capability"* — the **first explicit model-capability boundary** in the DSPy *Learn* corpus, a reminder that the [[DSPyProgrammingModel|Programming Model's]] *"swap the LM"* portability is not unconditional at the wire-format layer), and two further built-ins named only on the *Learn* page — **`dspy.XMLAdapter`** (XML-formatted I/O) and **`dspy.TwoStepAdapter`** (two-step extract-then-format workflow); custom adapters are supported via `Adapter`-subclass + `format()`/`parse()` override. The page's `NewsQA` worked example demonstrates `ChatAdapter` and `JSONAdapter` on **the same** [[DSPySignatures|Signature]] (a `list[pydantic.BaseModel]` output) with the only delta being the `adapter=` kwarg — the page's most explicit *swap-the-adapter-without-touching-the-signature* demonstration and the **third concrete *"swap N, leave M unchanged"* receipt** in the wiki (after [[DSPyLM|`dspy.LM`]]'s LM-swap and [[DSPyModules|`dspy.Module`]]'s strategy-swap). The Adapter is also the **single funnel** through which every DSPy-typed value crosses into the LM's wire format — including [[DSPyTools|Tools]] (the page-7 forward reference) and the multi-modal `dspy.Image` primitive (introduced on [[dspy-signatures]]) — not through separate sub-systems inside `dspy.ReAct` or `dspy.Predict`. The wiki mints [[DSPyAdapters]], which **resolves the long-standing forward reference** carried by every prior DSPy ingest since the corpus opened on 2026-05-17.

The **Tools** sub-system — the primitive [[DSPy]] uses to let an [[DSPyLM|LM]] invoke external Python functions — is *defined* by [[dspy-tools]] (page 7 of 13). The page promotes the wiki's prior framing — in which [[react|`dspy.ReAct`]] was the canonical DSPy tool-use entry point — into a **paired** rubric of **two equal-status approaches**: **(1) fully-managed** via [[react|`dspy.ReAct`]] (framework-owned think-act-observe loop; `tools=[...]` accepts plain Python callables; the returned [[DSPyPrediction|`Prediction`]] carries a `trajectory` field — *"complete reasoning trajectory tracking"* — recording every reasoning step and tool call made), and **(2) manual handling** via [[DSPyPredict|`dspy.Predict`]] over a [[DSPySignatures|Signature]] whose input is `tools: list[dspy.Tool]` and whose output is `dspy.ToolCalls` (user owns the loop). The four manual-path advantages the page commits to — *precise execution control / custom error-handling logic / latency minimization / **void-return tools*** — are non-trivial; the **void-return** case is the most informative (managed [[react|`dspy.ReAct`]]'s loop depends on each observation feeding back into the next reasoning step, so side-effect-only tools — logging, telemetry, fire-and-forget actions — don't fit the managed path). The [[DSPyTools|`dspy.Tool`]] wrapper exposes `.name` (from `__name__`), `.desc` (from docstring), `.args` (from type hints + defaults), and `str(tool)` (the canonical text the LM sees) — the **prompt-engineering interface** for tool selection, with three design rules made explicit (clear detailed docstrings; explicit type hints; basic types or [[Pydantic]] models). The matching `dspy.ToolCalls` model-output type carries the LM's requested invocations back into Python; `call.execute(...)` has three lookup modes (automatic-by-name / `functions={}` dict / `functions=[]` `Tool` list — **requires DSPy 3.0.4b2+**). **Native function calling** is configured at the [[DSPyAdapters|Adapter]] layer via `use_native_function_calling=` ([[DSPyAdapters|`ChatAdapter`]] defaults to **off**, [[DSPyAdapters|`JSONAdapter`]] to **on**; automatic fallback to text-parsing for models that don't support it — the **second model-capability scoping** in the *Learn* corpus after [[DSPyAdapters|`JSONAdapter`]]'s `response_format` requirement, and the second time the framework absorbs the gap behind an automatic-fallback discipline). **Async tools** are first-class via `tool.acall(...)` plus the off-by-default `dspy.context(allow_tool_async_sync_conversion=True)` sync-from-async opt-in. The Tools page also *confirms* [[dspy-adapters|the Adapters page]]'s claim that *"the Adapter converts `Tool` / `Image` / `History` into prompt messages"* — by placing the native-function-calling kwarg on the [[DSPyAdapters|Adapter]] constructor and not on `dspy.ReAct`, the wiki's reading of the four-concerns decomposition is sharpened: the Tools axis composes through [[DSPySignatures|Signature]] (which declares `tools` input and `ToolCalls` output), [[DSPyModules|Module]] (which picks managed vs manual), [[DSPyAdapters|Adapter]] (which picks native vs text wire format), and [[DSPyOptimizers|Optimizer]] (which tunes the prompts and demos that govern tool selection). The wiki mints [[DSPyTools]], which **resolves the long-standing forward reference** carried by every prior DSPy ingest, and *extends* [[react|the existing ReAct concept page]] in-place with the *managed-vs-manual* duality plus the `trajectory` field documentation — consistent with the [[dspy-modules]]-era precedent of extending [[ChainOfThought]] and [[react|ReAct]] in place rather than minting parallel `DSPyChainOfThought` / `DSPyReAct` pages.

The **first external tool-source protocol** the corpus records lands with [[dspy-mcp]] (page 8 of 13), which defines DSPy's integration with the **[[ModelContextProtocol|Model Context Protocol (MCP)]]** — [[anthropic|Anthropic]]'s open standard for connecting LMs to external tools, resources, and prompts via standalone servers. The page's load-bearing framing claim is **separation of responsibility**: *"DSPy doesn't manage MCP server connections directly. Instead, you connect to an MCP server using the `mcp` library, then convert the server's tools into DSPy tools with `dspy.Tool.from_mcp_tool`."* The protocol surface (transports, session lifecycle, JSON-RPC wire format) belongs to the `mcp` Python SDK; DSPy's contribution is a **single class-method bridge** — [[DSPyMCP|`dspy.Tool.from_mcp_tool(session, tool)`]] — that converts an MCP tool descriptor into a [[DSPyTools|`dspy.Tool`]] instance whose execution callback routes asynchronously back through the open `mcp.ClientSession`. The resulting `dspy.Tool` is **indistinguishable** from a locally-built one — it composes through every existing DSPy pathway ([[react|`dspy.ReAct`]], manual [[DSPyPredict|`dspy.Predict`]] with `tools: list[dspy.Tool]` input, direct `tool.acall(...)`) without any further MCP-aware code. Two transports are documented — **stdio** (`stdio_client` + `StdioServerParameters` for local server processes) and **streamable HTTP** (`streamablehttp_client` for remote endpoints) — and the page's API symmetry is deliberate: once the `ClientSession` is open, the conversion code is byte-identical across transports. Three operational constraints follow from MCP's async-end-to-end design: (1) [[react|`dspy.ReAct`]] must be invoked via `.acall(...)`, not the sync form; (2) the agent invocation must live *inside* the `async with` session block (closing the session invalidates further tool calls); (3) the toolset is fixed for the lifetime of the session unless `list_tools()` is re-issued. Installation is `pip install -U "dspy[mcp]"`. The wiki mints **two** concept pages — [[ModelContextProtocol]] (the framework-agnostic protocol; **resolves the long-standing forward reference** carried by every prior DSPy ingest) and [[DSPyMCP]] (the DSPy-specific binding, lighter-weight, treats the `from_mcp_tool(...)` class-method as the first-class abstraction). The split mirrors the [[LiteLLM]] / [[DSPyLM]] precedent — protocol/library page upstream + framework-binding page downstream. [[anthropic|Anthropic]]'s entity page is updated in-place to add MCP-authorship as a **third wiki role** alongside its frontier-model role ([[ClaudeOpus47]] in the [[2604.25067-frontier-coding-agents-c4|C4-AlphaZero benchmark]]) and its managed-API-provider role (via [[DSPyLM]] / [[LiteLLM]]). The MCP integration is the wiki's first concrete demonstration that DSPy's [[DSPyTools|`dspy.Tool`]] abstraction is **portable across tool origin** — local Python functions and MCP-server tools compose through the same Signature / Module / Adapter / Optimizer machinery without modification; the [[DSPyProgrammingModel|four-concerns decomposition]] survives the introduction of external tool registries. The page also **vindicates the [[dspy-tools|page-7]] async-tool surface** (`tool.acall(...)`, `dspy.context(allow_tool_async_sync_conversion=True)`) as load-bearing infrastructure rather than corner-case feature — MCP integration *requires* the async tool API, not as an option but as the only viable path.

The **Evaluation stage** of the three-stage model opens with [[dspy-evaluation-overview]] (page 9 of 13) — the first page outside the Programming stage. Where the seven prior pages defined *how to express* a DSPy program (signatures / modules / adapters / tools / MCP under [[DSPyProgrammingModel|the Programming Model]]), this page defines *how to measure* one before any [[DSPyOptimizers|optimization]] is attempted, and is the documentation that fills in the *"bad metric"* half of the [[dspy-learn-index|Learn index's]] load-bearing stage-order claim — *"it's unproductive to launch optimization runs using a poorly designed program or a bad metric."* The page operationalizes the Evaluation stage as a **four-step iterative loop**: (1) **collect a development set** of 20–200 worked examples — *"Even 20 input examples of your task can be useful, though 200 goes a long way"* — from adjacent public datasets, permissive-license re-use, manual labeling, or deployed-demo collection; (2) **define a DSPy metric**, a callable `(example, prediction) -> score` that is either scalar `accuracy` for simple tasks or a *"smaller DSPy program that checks multiple properties of the output"* for long-form tasks — DSPy's structural operationalization of the [[llmasjudge|LLM-as-judge]] pattern made disciplined by the typed-[[DSPySignatures|Signature]] / [[DSPyAdapters|Adapter]]-managed prompt machinery; (3) **run development evaluations** to produce a numerical baseline plus a qualitative diagnostic that may force a return to the Programming stage rather than proceed to Optimization; (4) **(recursively) optimize the metric itself** when the metric is a DSPy program — *"That's usually easy because the output of the metric is usually a simple value (e.g., a score out of 5), so the metric's metric is easy to define and optimize by collecting a few examples"* — a recursive-self-improvement claim structurally novel relative to other LLM-evaluation frameworks the wiki has recorded. Three load-bearing commitments distinguish DSPy Evaluation from generic ML evaluation: **small dev sets are sufficient** (20-example floor, 200-example ceiling — Evaluation is *diagnostic*, not training); **intermediate-step labels are almost never needed** (*"You almost never need labels for the intermediate steps in your program in DSPy"* — the metric scores final outputs only, leaving intermediate-step quality as the [[DSPyOptimizers|Optimizer's]] job to discover; DSPy's structural answer to the intermediate-supervision problem in chain-of-thought training); **the metric is itself iterative** (the [[DSPyProgrammingModel|"start simple, then grow"]] discipline restated at the metric layer — the metric has versions over the project's lifetime). The wiki mints [[DSPyEvaluation]] as the canonical concept page; it specializes the general [[ModelEvaluation]] concept, operates in the [[OfflineEvaluation]] regime ([[OnlineEvaluation]] is out of scope on the Overview page), and motivates the next two sibling pages — **Data Handling** (page 10, forward reference [[DSPyData]]) which will expand Step 1 into [[DSPyExample|`dspy.Example`]] mechanics, and **[[DSPyMetrics|Metrics]]** (page 11, forward reference) which will expand Step 2 into the full `(example, prediction) -> score` contract — both owned by sibling ingests. The Evaluation Overview is **load-bearing for the entire stage** but deliberately scope-limited to motivation; the per-sub-system machinery lives in those two forward-referenced pages.

The first of those two forward-referenced pages — **Data Handling** — lands with [[dspy-data]] (page 10 of 13). The page is short and load-bearing in the same way [[dspy-language-models]] was for the *"swap the LM"* claim: it minimally defines the data primitive every other DSPy artifact composes against. Three load-bearing commitments. **First**, *"DSPy is a machine learning framework, so working in it involves training sets, development sets, and test sets"* — DSPy locates itself **inside** the supervised-ML tradition rather than presenting itself as a separate paradigm. The [[dspy-learn-index|three-stage model]] is the ML-training cycle applied to LLM programs (write the program → measure it → tune it), and the data-handling page is where that framing becomes operationally concrete. **Second**, datasets are **plain Python lists** of [[DSPyExample|`dspy.Example`]] — DSPy does **not** introduce a `Dataset` class, a `train_test_split(...)` helper, or HuggingFace / CSV / JSON loaders; train/dev/test splits are Python slicing. The framework adds **exactly one** class on the data layer ([[DSPyExample|`dspy.Example`]]) and reuses Python's `list` and `dict` semantics for everything else — the small-API discipline consistent with [[dspy-modules|*"DSPy is just Python code"*]]. **Third**, **inputs-only sufficiency**: *"You can use DSPy effectively without any intermediate or final labels, but you will need at least a few example inputs"* — the data-side mirror of [[dspy-evaluation-overview|the Evaluation Overview's]] *intermediate-step labels are almost never needed* commitment. Together the two commitments authorize a minimal-data development style: collect 20–200 *inputs* (no labels), write a reference-free metric ([[llmasjudge|LLM-as-judge]] rubric or a heuristic on the output), evaluate the program. The data primitive itself is [[DSPyExample|`dspy.Example`]] — a typed Python dict-with-utilities with arbitrary field names and value types (no enforced schema; the [[DSPySignatures|Signature]] supplies schema separately), dot-notation field access, `with_inputs("field", ...)` input-tagging that returns a **new** `Example` whose attached `input_keys` set tags the named fields (non-mutating; warn-not-fail — *"be careful about marking your labels as inputs, unless you mean it"*), and non-destructive `inputs()` / `labels()` partition accessors. The structurally important inheritance the page records explicitly is that **[[DSPyPrediction|`dspy.Prediction`]] is a subclass of `dspy.Example`** — *"Your DSPy modules will return values of the type `Prediction`, which is a special sub-class of `Example`"* — which makes the [[DSPyMetrics|metric]]'s `(example, prediction) -> score` contract **type-symmetric**: both arguments share the same dot-access / `inputs()` / `labels()` surface, so the metric author writes `example.answer == prediction.answer` with no class-aware branching. The wiki mints two concept pages — [[DSPyExample]] (the per-datapoint primitive) and [[DSPyData]] (the dataset-collection-and-splitting layer) — **resolving both long-standing forward references** carried by [[DSPyEvaluation]] / [[dspy-evaluation-overview]] since the Evaluation stage opened on page 9. The pair is structurally analogous to [[DSPyPredict]] (strategy-side minimal primitive) + [[DSPyModules]] (strategy-layer composition discipline) from the Modules ingest — one primitive, one layer of discipline over collections of that primitive. The next sibling page — [[DSPyMetrics|Metrics]] (page 11) — will consume both `Example` (as ground truth) and `Prediction` (as the system output) under the `(example, prediction) -> score` contract; the type-symmetric inheritance recorded on this page is what makes that contract clean.

The **third page of the Evaluation stage** — and the page that resolves the long-standing [[DSPyMetrics]] forward reference — lands with [[dspy-metrics]] (page 11 of 13). This page expands Step 2 of [[DSPyEvaluation|the four-step iterative-evaluation loop]] — *"define a DSPy metric"* — into the concrete **`(example, pred, trace=None) -> score`** function-signature contract every DSPy artifact composes against. The canonical claim: *"A DSPy metric is just a function in Python that takes `example` (e.g., from your training or dev set) and the output `pred` from your DSPy program, and outputs a `float` (or `int` or `bool`) score."* Three properties make the contract structurally important. **First**, it is **type-symmetric on the data side** — because [[DSPyPrediction|`dspy.Prediction`]] is a subclass of [[DSPyExample|`dspy.Example`]] (as [[dspy-data|page 10]] established), the metric author writes `example.answer == pred.answer` with no class-aware branching; both arguments expose the same dot-access / `inputs()` / `labels()` surface. **Second**, it is **regime-asymmetric on the calling side** — the optional third argument `trace` switches the metric's behavior between **evaluation/optimization** (`trace is None`, returns a continuous `float`/`int` for the [[DSPyOptimizers|Optimizer]] to climb) and **bootstrapping** (`trace is not None`, returns a strict `bool` — keep this trajectory as a few-shot demonstration? Y/N). The bootstrapping bar is always strictly tighter than the evaluation bar — only top-scoring trajectories become demos. This **single function, dual purpose** structure is what makes bootstrap-based [[DSPyOptimizers|optimizers]] like `BootstrapFewShotWithRandomSearch` possible — they need a function that *both* ranks candidates *and* gates demonstrations, and a single `trace`-aware metric provides both. **Third**, the return is **scalar** — `float` / `int` / `bool` are the only valid return types; `True`/`False` are summed by [[DSPyEvaluate|`dspy.Evaluate`]] as `1.0`/`0.0`. The page sharpens [[dspy-evaluation-overview|the Evaluation Overview's]] two-regime story into concrete code patterns: **simple metrics** (one-line scalar comparisons like `example.answer.lower() == pred.answer.lower()`, plus two built-in utilities `dspy.evaluate.metrics.answer_exact_match` and `dspy.evaluate.metrics.answer_passage_match`) for short-form / reference-based tasks; **AI-feedback metrics** (a `class Assess(dspy.Signature)` rubric template with `assessed_text` / `assessment_question` inputs and a `bool` `assessment_answer` output, called once per rubric dimension via `dspy.Predict(Assess)(...)`, summed and thresholded) for long-form tasks — DSPy's structural operationalization of the [[llmasjudge|LLM-as-judge]] pattern made disciplined by the typed-Signature / [[DSPyAdapters|Adapter]]-managed prompt machinery. The page's most consequential code receipt is the **tweet metric** — `score = (correct + engaging) if correct and (len(tweet) <= 280) else 0` — which combines two LM-judged booleans with one deterministic boolean inside the same `score` computation, then switches return type on `if trace is not None: return score >= 2 / else return score / 2.0`. This is the wiki's first explicit demonstration that a DSPy metric is **not all-or-nothing AI-feedback**: the deterministic gate (`len <= 280`) is a [[LLMModuloFramework|*sound* critic]], the LM-judged dimensions are *soft* critics, and the AND-gate encodes a *correctness-first, engagement-modulates* priority that pure averaging would lose. The **trace-aware bootstrap recipe** `validate_hops` is the only intermediate-step validator in the *Learn* corpus so far — `[outputs.query for *_, outputs in trace if 'query' in outputs]` pulls every predictor's `query` field out of the trace and filters for non-degenerate multi-hop trajectories at bootstrap time. The recipe is **bootstrap-only** because *"DSPy will not try to track the steps of your program"* during plain evaluation; intermediate-step quality remains the Optimizer's job to discover ([[dspy-evaluation-overview|page 9]]'s commitment), but the developer can **structurally constrain** what counts as a good demonstration via the trace without ever labeling intermediate steps. The page anchors [[DSPyEvaluation|the Evaluation stage's]] **recursive-self-improvement** claim (Step 4 of the four-step loop) in the AI-feedback metric: because the metric calls `dspy.Predict(Assess)(...)`, it is itself a DSPy program with learnable parameters — the `Assess` signature's instructions, its few-shot demonstrations, the underlying LM's prompts — and is therefore **optimizable by a [[DSPyOptimizers|DSPy Optimizer]] the same way the system program is**. The *"metric of the metric"* is a `(metric_example, metric_pred) -> bool` function over a small set of labeled outputs (which rubric judgments were right, which wrong) — easier to define and label than the original metric because the metric's output is bounded and scalar. Finally, the page documents **`dspy.Evaluate`** — the parallel dev-set-evaluation harness imported via `from dspy.evaluate import Evaluate` — via the canonical two-phase construction-then-call pattern: `Evaluate(devset=..., num_threads=..., display_progress=..., display_table=N)` binds the dev set + ergonomic kwargs once; the call accepts a `(program, metric)` pair and runs the metric over the dev set with thread parallelism and tabular display. The raw equivalent `for x in devset: pred = program(**x.inputs()); score = metric(x, pred)` makes the abstraction visible — `Evaluate` is a thread-parallel wrapper around it. The same `evaluator` is **reusable** across multiple program candidates and metric iterations — the dev-set-comparison primitive used internally by [[DSPyOptimizers|Optimizers]] and externally by developers during [[DSPyEvaluation|the four-step Evaluation loop's]] Step 3. The wiki mints two concept pages — [[DSPyMetrics]] (the canonical metric contract; **resolves the long-standing forward reference** carried by [[DSPyEvaluation]] / [[dspy-evaluation-overview]] / [[dspy-data]] / [[DSPyExample]] / [[DSPyPrediction]] / every prior DSPy ingest since the corpus opened on 2026-05-17) and [[DSPyEvaluate]] (the dev-set-evaluation utility; the sibling concept whose role is the *how* to apply the *what* [[DSPyMetrics]] defines). With this page the wiki's coverage of the DSPy Evaluation stage is complete — the four-step loop now has concrete API anchors at every step: [[DSPyData]] / [[DSPyExample]] for Step 1, [[DSPyMetrics]] for Step 2, [[DSPyEvaluate]] for Step 3, recursive metric optimization for Step 4. Two further sibling ingests remain to close the *Learn* corpus at 13/13: Optimization Overview (page 12) and [[DSPyOptimizers|Optimizers]] (page 13).

The **Optimization stage** of the three-stage model opens with [[dspy-optimization-overview]] (page 12 of 13). Where the prior eleven pages defined *how to express* and *how to measure* a DSPy program, this page defines *how to improve* one — and operationalizes the **fourth** of [[DSPyProgrammingModel|the Programming Model's]] four orthogonal artifacts at the workflow level. The canonical one-sentence definition: *"Once you have a system and a way to evaluate it, you can use DSPy optimizers to tune the prompts or weights in your program."* The page commits the framework to four load-bearing positions. **First**, the optimizer's interface contract is **three-input, one-output**: a [[DSPyModules|`dspy.Module`]] program (from the [[DSPyProgrammingModel|Programming stage]]) + a `(example, pred, trace=None) -> score` [[DSPyMetrics|metric]] (from the [[DSPyEvaluation|Evaluation stage]]) + a `list[dspy.Example]` training set (from the [[DSPyEvaluation|Evaluation stage]]) → an **optimized program** (the same `dspy.Module` subclass with refined instructions / demonstrations / weight references). The contract is what makes the three-stage model composable — each stage's *output* is the next stage's *input*. **Second**, the **training-set size regime is 30 to 300+** — *"You can often get substantial value out of 30 examples, but aim for at least 300 examples"* — explicitly larger than [[DSPyEvaluation|the Evaluation stage's]] 20–200-example dev-set regime (the optimizer's search benefits from more examples than diagnostic measurement does); the 30/300 progression mirrors the *"start simple, then grow"* discipline at the training-set layer. **Third**, the **conventional ML 80/20 train/val split is inverted to 20/80 for most prompt optimizers** — *"For most prompt optimizers, we recommend allocating 20% of your data for training and 80% for validation, contrary to typical deep learning conventions. This is because prompt optimizers tend to overfit on small training sets"* — a DSPy-specific defense against a DSPy-specific failure mode (the prompt-optimization search space is small enough that an optimizer can memorize a small training set and generalize poorly; a large validation set is the overfitting defense). The page names exactly **one** specific optimizer — **[[GEPA]]** — and only as a carve-out: *"the GEPA optimizer follows standard ML practice — maximizing the training set size while keeping the validation set sufficiently sized to represent the downstream task distribution"*. The wiki carries [[GEPA]] as a forward reference; its mechanism is deferred to page 13. **Fourth**, iteration spans **four axes — data, program structure, metric, and optimizer-choice** — and *three of the four point back into the Programming and Evaluation stages*, making the Optimization stage **open under revision from the prior two** (not a black-box terminus): *"Iterative development is key. DSPy gives you the pieces to do that incrementally."* The wiki mints [[DSPyOptimization]] as the canonical concept page for the optimization **workflow** — completes the four-artifact picture (Signatures / Modules / Adapters / Optimizers) at the workflow level alongside [[DSPyEvaluation|Evaluation]] as the connective stage between Programming and Optimization. The page deliberately **defers the per-optimizer catalog** ([[BootstrapFewShot]], [[BootstrapFewShotWithRandomSearch]], [[MIPROv2]], [[BootstrapFinetune]], [[GEPA]], etc.) to page 13 ([[DSPyOptimizers|Optimizers]]) — the split between [[DSPyOptimization]] (workflow) and [[DSPyOptimizers]] (catalog) mirrors the [[DSPyEvaluation]] / [[DSPyMetrics]] precedent of one page anchoring the workflow and the sibling page anchoring the per-algorithm machinery. With this page the wiki's coverage of the DSPy *Learn* corpus is **12/13** — every concern named on [[DSPyProgrammingModel|the Programming Model]] now has a corresponding source page and concept anchor at the workflow level. A single sibling ingest remains to close the corpus: page 13 ([[DSPyOptimizers|Optimizers]]) will fill in the optimizer registry and resolve the [[DSPyOptimizers]] / [[BootstrapFewShot]] / [[BootstrapFewShotWithRandomSearch]] / [[MIPROv2]] / [[BootstrapFinetune]] / [[GEPA]] / [[DSPyAssertions]] forward references this page carries.

The **final page of the DSPy *Learn* corpus** lands with [[dspy-optimizers]] (page 13 of 13). Where [[dspy-optimization-overview|page 12]] shipped the **workflow-level** contract (three inputs — *program + metric + training set*; one output — *optimized program*; 30/300 sizing; inverted 20/80 train/val split; four iteration axes), **this page ships the catalog** — the concrete `dspy.<OptimizerName>` registry enumerates eleven optimizers grouped into five families: **Automatic Few-Shot Learning** (`LabeledFewShot` / [[BootstrapFewShot|`BootstrapFewShot`]] / [[BootstrapFewShotWithRandomSearch|`BootstrapFewShotWithRandomSearch`]] / `KNNFewShot`), **Automatic Instruction Optimization** (`COPRO` / [[MIPROv2|`MIPROv2`]] / `SIMBA` / [[GEPA|`GEPA`]]), **Automatic Finetuning** ([[BootstrapFinetune|`BootstrapFinetune`]]), **Program Transformations** (`Ensemble`), and **Meta-Optimizers** (`BetterTogether`). The framework's prior name for the family is **"teleprompters"** — *"Formerly called teleprompters. We are making an official name update."* — and the canonical worked-example local-variable name `teleprompter` is still the *de-facto* idiomatic name. Three orthogonal **what-it-tunes** axes anchor the catalog: **demonstrations** (the few-shot examples in each [[DSPyPredict|`dspy.Predict`]]'s prompt) / **instructions** (the natural-language task description) / **LM weights** (via fine-tuning). Only [[MIPROv2]] tunes more than one axis in the same run (instructions **and** demonstrations); only [[BootstrapFinetune]] tunes weights. The page uses [[MIPROv2|`dspy.MIPROv2`]] as its **reference example** of how a non-trivial DSPy optimizer works, walking through a three-stage decomposition that becomes the **structural template** the rest of the catalog can be read against: **(1) bootstrapping stage** — run the program on training inputs, collect per-module traces, filter by the [[DSPyMetrics|metric]] (in `trace is not None` mode — the bootstrap-only strict-bool branch); **(2) grounded proposal stage** — preview the program's *code*, *data*, and *traces* and draft candidate instructions per prompt (the **distinctive contribution** — DSPy's *"writing code instead of strings"* discipline pays off because the proposer can inspect the actual Python program, not just a string prompt); **(3) discrete search stage** — sample mini-batches, propose (instructions, demos) combinations, evaluate candidates, update a **surrogate model** ([[BayesianOptimization|Bayesian Optimization]]) that improves proposals over time. Every non-trivial DSPy optimizer is then some combination of *(a) collect traces, (b) propose candidates, (c) search the candidate space against the metric*, with different optimizers occupying different positions in this 3-step space — `COPRO` uses coordinate ascent; [[BootstrapFewShotWithRandomSearch]] uses random search; `KNNFewShot` uses k-NN ranking; `SIMBA` uses mini-batch stochastic search; [[GEPA]] uses LM reflection on what worked / didn't; [[BootstrapFinetune]] fine-tunes the LM on filtered traces. The page commits the framework to a **composability** claim — *"You can run `dspy.MIPROv2` and use the produced program as an input to `dspy.MIPROv2` again or, say, to `dspy.BootstrapFinetune` to get better results. This is partly the essence of `dspy.BetterTogether`."* — that is **structurally novel** relative to conventional ML hyperparameter optimization: a `sklearn.GridSearchCV` doesn't typically consume another `GridSearchCV`'s output as input, but DSPy optimizers preserve the program's structure as their output type (`dspy.Module -> dspy.Module`), so they compose like ordinary Python functions over a single algebraic type. Two compositional patterns: **sequential composition** (`BetterTogether`'s prompt → weight → prompt schedule) and **ensemble composition** (run an optimizer, extract top-k candidate programs, wrap them in `dspy.Ensemble` for inference-time voting — scales DSPy's *unique* **pre-inference-time compute** axis on top of conventional **inference-time compute**). The page ships a **five-rule getting-started rubric** — **10 examples → [[BootstrapFewShot]]**, **50+ → [[BootstrapFewShotWithRandomSearch]]**, **want 0-shot prompts → [[MIPROv2]] (0-shot mode)**, **40+ trials + 200+ examples → [[MIPROv2]] (full)**, **post-success efficiency → [[BootstrapFinetune]]** — that operationalizes [[DSPyOptimization|page 12's]] *"are you using the most sophisticated optimizer that fits your needs?"* diagnostic question into a concrete (data, compute) → optimizer map. Five optimizers are **absent** from the rubric ([[GEPA]], `SIMBA`, `COPRO`, `KNNFewShot`, `Ensemble`, `BetterTogether`, `LabeledFewShot`) — those are *expert paths* the user must discover via the catalog. The page records DSPy's **first explicit operating-cost ballpark**: *"A typical simple optimization run costs on the order of $2 USD and takes around ten minutes ... a few cents up to tens of dollars, depending on your LM, dataset, and configuration."* This anchors [[DSPyOptimization|page 12's]] *"this is an emerging paradigm"* framing at the wallet level — optimization is a **finite budget**, not free. Three worked end-to-end optimization receipts anchor the abstract decision rubric to concrete metric improvements: **[[react|`dspy.ReAct`]] + [[MIPROv2|`dspy.MIPROv2(auto="light")`]] on HotPotQA — 24% → 51%** (prompt-only optimization of a tool-using agent + Wikipedia search via `dspy.ColBERTv2`); **`RAG(dspy.Module)` + [[MIPROv2|`dspy.MIPROv2(auto="medium")`]] with [[llmasjudge|`dspy.SemanticF1()`]] on StackExchange — 53% → 61%** (AI-feedback-metric-driven optimization — exercises the [[DSPyMetrics|recursive-metric-optimization]] claim from [[DSPyEvaluation|Step 4 of the four-step Evaluation loop]] in practice, since `SemanticF1` is itself a DSPy module scoring another DSPy program); **Banking77 classification + [[BootstrapFinetune|`dspy.BootstrapFinetune`]] on `gpt-4o-mini-2024-07-18` — 66% → 87%** (the **only weight-tuning receipt** in the corpus, 2000 examples, `Literal[tuple(CLASSES)]`-typed [[DSPySignatures|Signature]], a simple lambda metric, and the **only place in the corpus** that `classify.set_lm(lm)` is exercised). The **save/load inspectability commitment** — *"The resulting file is in plain-text JSON format. It contains all the parameters and steps in the source program. You can always read it and see what the optimizer generated."* — is the optimizer's structural payoff at the deployment boundary: the output is not a `*.pt` weight file or an opaque fine-tuned-model handle but a **refined version of the same program** the developer wrote, consistent with the [[DSPyProgrammingModel|*"writing code instead of strings"*]] discipline ([[BootstrapFinetune]] is the only exception — it produces a fine-tuned-model handle, but the surrounding DSPy program is still JSON). The structurally important per-optimizer disclosure: **[[GEPA]]** is the **only optimizer named on [[dspy-optimization-overview|page 12]]** — and named precisely because it is the **named carve-out** from the framework-level inverted 20/80 train/val split (*"the GEPA optimizer follows standard ML practice"*). Page 13 partially develops the mechanism — GEPA *"uses LM's to reflect on the DSPy program's trajectory, to identify what worked, what didn't and propose prompts addressing the gaps"* and *"can leverage domain-specific textual feedback"* — but defers full detail to tutorials. The implication is that reflection-driven instruction proposals are **more robust to small training sets** than search-driven mechanisms (which is the structural justification for the carve-out). Reading the page-13 per-optimizer documentation is therefore **load-bearing** before applying the 20/80 split mechanically — the train/val split is a **per-optimizer recommendation**, not a universal rule. The wiki mints 6 concept pages — [[DSPyOptimizers]] (the canonical catalog page; the **catalog-level sibling** of [[DSPyOptimization]] — workflow vs catalog, mirroring [[DSPyEvaluation]] / [[DSPyMetrics]]; **resolves the long-standing forward reference [[DSPyOptimizers]]** carried by every prior DSPy ingest since the corpus opened on 2026-05-17), plus four per-optimizer concept pages [[BootstrapFewShot]], [[BootstrapFewShotWithRandomSearch]], [[MIPROv2]], [[GEPA]], [[BootstrapFinetune]]; minor variants (`KNNFewShot` / `COPRO` / `SIMBA` / `Ensemble` / `BetterTogether` / `LabeledFewShot`) are folded into the catalog table on [[DSPyOptimizers]] rather than minting separate pages. **With this page the DSPy *Learn* corpus closes at 13/13** — every concern named on [[DSPyProgrammingModel|the Programming Model]] now has corresponding source pages and concept anchors at **both the workflow and catalog levels**: Signatures ([[dspy-signatures]] / [[DSPySignatures]]), Adapters ([[dspy-adapters]] / [[DSPyAdapters]]), Modules ([[dspy-modules]] / [[DSPyModules]] + 6 module-specific pages), Optimizers ([[dspy-optimization-overview]] / [[DSPyOptimization]] for workflow + [[dspy-optimizers]] / [[DSPyOptimizers]] for catalog). The Evaluation stage as the connective tissue between Programming and Optimization is similarly complete ([[DSPyEvaluation]] workflow + [[DSPyMetrics]] / [[DSPyData]] / [[DSPyExample]] / [[DSPyEvaluate]] catalog). **Every long-standing forward reference** the DSPy ingest sequence carried is now resolved at both layers — there are no remaining DSPy-internal forward references in the wiki except [[DSPyAssertions]] (no scheduled ingest yet — the advanced-features escape hatch named on [[dspy-optimization-overview|page 12]]'s diagnostic-questions list) and [[PromptOptimization]] (a general-concept forward reference not specific to DSPy).

## VI. *Probabilistic Machine Learning: An Introduction* ([[KevinMurphy|Murphy]], 23 chapters)

[[KevinMurphy]]'s 860-page [[MITPress]] textbook ([[pml1-murphy]], 2022; third printing January 2025; CC-BY-NC-ND) is the wiki's **theory-and-foundations layer**. Twenty-three chapters across five parts — Foundations (probability, statistics, decision theory, information theory, linear algebra, optimization), Linear Models (LDA, logistic / linear / generalized linear regression), Deep Neural Networks (tabular / image / sequence), Nonparametric Models (KNN, kernels, trees + boosting), and Beyond Supervised Learning (semi-/self-supervised, dimensionality reduction, clustering, recommender systems, graph embeddings) — all framed through the unifying [[ProbabilisticPerspective]].

**The probabilistic perspective** (§1.1) is the commitment that *every* unknown quantity (predictions, parameters, latent factors, missing data) is a random variable; learning is inference over distributions, not point estimation. Two justifications: (i) [[DecisionMakingUnderUncertainty|decision-theoretic]] necessity — Dutch-book / Cox / Savage axiomatizations show non-probabilistic uncertainty representations are inconsistent; (ii) it is the lingua franca of every neighboring computational science (control, OR, information theory, statistical physics).

**Three ML regimes, one math** (§1.2–§1.4). Supervised: $p(y|\mathbf{x};\boldsymbol\theta)$. Unsupervised: $p(\mathbf{x};\boldsymbol\theta)$. RL: policy $a=\pi(\mathbf{x})$ from sparse reward. The LeCun chocolate-cake analogy ranks information density: unsupervised is the cake (millions of bits/sample), supervised the icing, RL the cherry.

**The ERM → MLE → NLL bridge** (§1.2). [[EmpiricalRiskMinimization|ERM]] $\hat\theta=\arg\min \frac{1}{N}\sum\ell(y_n,f(\mathbf{x}_n;\theta))$ specializes to misclassification under zero-one loss, MSE under quadratic loss, and [[MaximumLikelihoodEstimation|MLE]] under NLL. For Gaussian regression NLL = MSE/($2\sigma^2$) + const, so least squares *is* MLE under fixed-variance Gaussian noise. For softmax classification, NLL = cross-entropy. These equivalences are how the rest of the book (and most of Corpus II's pretraining objectives) connect probabilistic modeling to optimization.

**The overfitting/generalization apparatus** (§1.2.3, §1.2.4). [[GeneralizationGap]] $\mathcal{L}(\theta;p^*)-\mathcal{L}(\theta;\mathcal{D}_{\text{train}})$ defines overfitting; train/validation/test partitions estimate it. [[NoFreeLunchTheorem]] (Wolpert 1996) forces every learner to commit to an inductive bias. Classical U-curves coexist with modern double-descent in the overparameterized regime LLM pretraining operates in.

**Why this corpus matters now.** Corpus II's 2026 LLM papers tacitly assume the *whole* of Murphy's prerequisites — Bayes' rule, NLL/MLE equivalence, GLMs, SGD/Adam, PCA, the [[CurseOfDimensionality]]. When [[2001.08361-scaling-laws]] fits a power law to pretraining cross-entropy, Murphy Ch 6 is the cross-entropy reference; when [[2605.12966-agentic-ai-to-agi]] argues the [[AverageTrap]] under a [[StructuredRealWorldDistribution]], it builds on Murphy's quadratic-loss / weighted-average / [[EmpiricalRiskMinimization|ERM]] primitives; when [[1706.03762-attention-is-all-you-need]] outputs $p(\mathbf{x}_t|\mathbf{x}_{<t})$, that conditional density is exactly Murphy §1.2.1.5.

**Connections to other corpora.**
- **Corpus I (math):** Murphy's Ch 7 (Linear Algebra) is a compressed version of the [[matrices]] / [[vectors]] / [[eigenvalues-and-eigenvectors]] / [[matrix-diagonalization]] / [[rank-of-a-matrix]] block in algebrica.org. Ch 6 (Information Theory) is downstream of [[logarithms]]. Ch 2–3 (Probability) extend the [[real-numbers]] / [[supremum-and-infimum]] / [[absolute-value]] foundations.
- **Corpus II (LLM research):** Murphy is the prerequisite-and-vocabulary layer. The [[NoFreeLunchTheorem]] of §1.2.4 is the entry point [[2605.12966-agentic-ai-to-agi]] uses to motivate the [[StructuredRealWorldDistribution]]; Murphy's Ch 8 (Optimization) underwrites every gradient-based result in the corpus.
- **Corpus III (Molnar interpretability):** Murphy provides the *fitted* models that Corpus III interprets. Ch 10 (Logistic Regression) ↔ [[imlbook-logistic]]; Ch 11 (Linear Regression) ↔ [[imlbook-limo]]; Ch 17 (Kernels) ↔ [[imlbook-shap]]'s game-theoretic substrate; Ch 18 (Trees / Forests / Boosting) ↔ [[imlbook-tree]] / [[imlbook-rulefit]]; Ch 14 (CNN feature learning) ↔ [[imlbook-cnn-features]] / [[imlbook-pixel-attribution]].
- **Corpus IV (McKinney PDA):** McKinney is the *tooling* layer (pandas/numpy/sklearn API); Murphy is the *theory* layer for the same API surface. [[pydata-modeling]] uses [[scikitlearn]] estimator objects that Murphy Ch 10–18 supplies the mathematical content of.
- **Corpus V (Made With ML):** Mohandas's foundations track is a *fast-applied* recapitulation of Murphy Ch 10–15 (logistic, MLP, CNN, RNN, attention) — same content, optimized for production rather than for theoretical completeness. Use Murphy for *why*, Mohandas for *how to ship*.

**Live tensions.** Murphy's framing is *agnostic* on the AGI path question — Part III (DNNs) is organized around monolithic supervised learning. By contrast, [[2605.12966-agentic-ai-to-agi]] argues monolithic scaling is *structurally* bottlenecked by the [[AverageTrap]] and the [[CurseOfDimensionality]] applied to ambient $D$. The two are compatible (Murphy doesn't take a position) but Murphy's structural choices read as implicit acceptance of the scaling story Liao et al. contest. Likewise, Murphy's MAR (missing-at-random) assumption (§1.5.5) is standard but bites in causal-inference / RLHF preference-data settings Corpus II partially inhabits. Finally, Murphy's "self-supervised learning as a recently popular approach" (§1.3.3) is now dated — pretraining-then-finetuning is the default, not the curiosity it was when the book was written.

## VII. *An Introduction to Statistical Learning* ([[GarethJames|James]] / [[DanielaWitten|Witten]] / [[TrevorHastie|Hastie]] / [[RobertTibshirani|Tibshirani]], 10 chapters)

[[islr-seventh-printing|ISLR]] ([[springer|Springer]], 2013, 8th corrected printing 2017) is the **classical-statistical-learning** layer. Ten chapters move from [[StatisticalLearning]] basics and the [[BiasVarianceTradeoff]] through the classical supervised toolbox ([[LinearRegression]], [[LogisticRegression]], [[LinearDiscriminantAnalysis|LDA]], [[QuadraticDiscriminantAnalysis|QDA]], [[KNearestNeighbors|KNN]]), resampling ([[CrossValidation]], [[Bootstrap]]), regularization & dimension reduction ([[RidgeRegression]], [[Lasso]], [[PrincipalComponentsRegression|PCR]], [[PartialLeastSquares|PLS]]), non-linearity ([[RegressionSplines]], [[SmoothingSplines]], [[LocalRegression]], [[GeneralizedAdditiveModels|GAMs]]), [[TreeBasedMethods|tree-based methods]] with [[Bagging]] / [[RandomForests]] / [[Boosting]], [[SupportVectorMachine|SVMs]] via the [[MaximalMarginClassifier]] → [[SupportVectorClassifier]] progression, and unsupervised learning ([[PrincipalComponentAnalysis|PCA]], [[KMeansClustering]], [[HierarchicalClustering]]). Every chapter ends with an [[Rlanguage|R]] lab using the [[ISLRPackage]].

**The accessibility move.** ISLR is the deliberately low-math companion to [[ElementsOfStatisticalLearning|ESL]] (Hastie/Tibshirani/Friedman 2001/2009). Premise 3 — "*while it is important to know what job is performed by each cog, it is not necessary to have the skills to construct the machine inside the box*" — explains the pedagogical bet: maximize the audience by minimizing matrix algebra, sacrifice depth, regain it via R labs. The book is the canonical reference for applied practitioners outside statistics — exactly the audience Corpus V ([[MadeWithML]]) targets, but with the *classical* methods rather than the deep-learning stack.

**Connections to other corpora.**
- **Corpus I (math):** ISLR explicitly avoids matrix algebra, but [[LinearRegression]], [[RidgeRegression]], [[Lasso]] and [[PrincipalComponentAnalysis|PCA]] all rest on the [[matrices]] / [[determinant-of-a-square-matrix]] / [[eigenvalues-and-eigenvectors]] block. Treat algebrica.org as the formal prerequisite ISLR explicitly waives.
- **Corpus III (Molnar interpretability):** ISLR's Ch.3 ([[LinearRegression]]), Ch.4 ([[LogisticRegression]] / [[LinearDiscriminantAnalysis|LDA]]), Ch.8 ([[DecisionTrees]] / [[Bagging]] / [[RandomForests]] / [[Boosting]]) are the *fitted models* whose interpretation Molnar formalizes (e.g. [[imlbook-tree]] ↔ ISLR §8.1; [[imlbook-limo]] ↔ ISLR §3.1; [[imlbook-rulefit]] ↔ ISLR §8.2.3 Boosting + Friedman's RuleFit).
- **Corpus IV (McKinney PDA):** [[pydata-modeling]] uses [[scikitlearn]] / [[statsmodels]] estimators that implement the same methods ISLR teaches in R — `LinearRegression` ↔ Ch.3, `LogisticRegression` ↔ Ch.4, `RandomForestRegressor` ↔ Ch.8.2.2, `Lasso` ↔ Ch.6.2.2. The [[Patsy]] formula syntax in `pydata-modeling` is the Python port of ISLR's R formula syntax.
- **Corpus V (Made With ML):** Mohandas's foundations track recapitulates the *neural* side of statistical learning; ISLR is the *classical* counterpart. For a tabular problem, ISLR's Ch.6 ([[Lasso]] / [[RidgeRegression]]) / Ch.8 ([[RandomForests]] / [[Boosting]]) typically beats the MLP/CNN stack of the Made With ML foundations track — confirming ISLR Premise 2 ("no single approach will perform well in all possible applications").
- **Corpus VI (Murphy):** Strong overlap — Murphy Ch.10 ([[LogisticRegression]]) ↔ ISLR Ch.4; Murphy Ch.11 ([[LinearRegression]]) ↔ ISLR Ch.3; Murphy Ch.18 (Trees / Forests / Boosting) ↔ ISLR Ch.8; Murphy Ch.20 (Clustering) ↔ ISLR Ch.10. Use Murphy for the [[ProbabilisticPerspective|probabilistic]] derivation and exponential-family unifying frame ([[GeneralizedLinearModels]]); use ISLR for the applied recipe, the bias-variance intuition, and the R lab. They are deeply complementary: Murphy supplies the *why* at the level of MLE/Bayes/optimization; ISLR supplies the *how* at the level of fit-evaluate-tune.

**Live tensions.**
- **The R / Python split.** ISLR's labs are R-only; Corpora IV–V are Python-only. The methods are language-agnostic, but the lab-style "hands-on" learning loop ISLR commits to (Premise 4) does not translate verbatim to the Python ecosystem — practitioners coming from [[pydata-modeling]] need to translate from `lm()`/`glm()`/`tree::tree()` to [[scikitlearn]] / [[statsmodels]] estimators.
- **Classical vs deep.** ISLR ends in 2013 and includes no deep learning, attention, or representation learning — the entire frontier of Corpus II. This is the corpus's load-bearing limitation: when a 2026 paper discusses [[Attention]], [[Transformer]], or [[Backpropagation]] through deep stacks, ISLR is silent and Corpora V–VI take over. ISLR is canonical for *tabular* and *classical* problems; Corpus VI (Murphy) is the bridge into deep learning.
- **The Lasso lineage.** [[RobertTibshirani]] is both ISLR co-author and the original proposer of the [[Lasso]] (1996). The Lasso's role in Corpus II is mostly historical — modern LLM regularization is dropout / weight decay / layer norm — but the *idea* of $\ell_1$-induced sparsity reappears in [[MixtureOfExperts]] gating and in skill-selection mechanisms across the 2026 agentic papers. ISLR Ch.6 is the canonical reference for the original argument.

## VIII. *Mathematics for Machine Learning* ([[MarcDeisenroth|Deisenroth]] / [[AAldoFaisal|Faisal]] / [[ChengSoonOng|Ong]], 12 chapters)

[[MarcDeisenroth|Marc Peter Deisenroth]], [[AAldoFaisal|A. Aldo Faisal]] & [[ChengSoonOng|Cheng Soon Ong]]'s 417-page [[CambridgeUniversityPress]] textbook ([[mml-book]], 2020, draft revision 2024-01-15, freely distributed at <https://mml-book.com>) is the wiki's **prerequisites-and-foundations** layer. Where Murphy ([[pml1-murphy]]) is encyclopedic-and-probability-first and ISLR is hands-on-and-statistical, MML is **math-first** with four worked ML examples: it surfaces the [[LinearAlgebra]], [[AnalyticGeometry]], [[MatrixDecomposition]], [[VectorCalculus]], [[ProbabilityAndDistributions]], and [[ContinuousOptimization]] machinery that the other textbook corpora assume and only re-derives a small number of ML algorithms ([[LinearRegression]], [[PrincipalComponentAnalysis|PCA]], [[GaussianMixtureModel|GMM]], [[SupportVectorMachine|SVM]]) as load-bearing examples.

**Structure.** The 12 chapters split across two parts following the Foreword's "four pillars on six foundations" diagram (Fig 1.1):

- **Part I — Mathematical Foundations:**
  - **Ch 2 [[LinearAlgebra]]** — [[VectorSpace]]s, [[LinearIndependence]], [[Basis]], [[Rank]], [[LinearMapping]], Gaussian elimination, [[AffineSpace]]s.
  - **Ch 3 [[AnalyticGeometry]]** — [[Norm]], [[InnerProduct]], [[CauchySchwarzInequality]], angles, [[OrthogonalProjection]], rotations, [[SymmetricPositiveDefiniteMatrix|SPD matrices]] ↔ inner products.
  - **Ch 4 [[MatrixDecomposition]]** — [[Determinant]], [[Trace]], [[CharacteristicPolynomial]], [[Eigendecomposition]], [[CholeskyDecomposition]], [[SingularValueDecomposition|SVD]], matrix approximation, "matrix phylogeny."
  - **Ch 5 [[VectorCalculus]]** — [[PartialDerivative]], [[Gradient]], [[Jacobian]], [[Hessian]], [[ChainRule]], [[Backpropagation]] / [[AutomaticDifferentiation]], [[TaylorSeries]], [[Linearization]].
  - **Ch 6 [[ProbabilityAndDistributions]]** — [[ProbabilitySpace]], [[RandomVariable]], discrete vs continuous, [[BayesTheorem]], summary statistics, [[GaussianDistribution]], [[ExponentialFamily]] + [[ConjugatePrior]], change of variables.

  - **Ch 9 [[LinearRegression]]** — Gaussian-noise likelihood ⇒ closed-form MLE $\boldsymbol\theta_{\text{ML}}=(\mathbf{X}^\top\mathbf{X})^{-1}\mathbf{X}^\top\mathbf{y}$; [[FeatureMap]] + [[DesignMatrix]] ⇒ polynomial / nonlinear regression; [[BayesianLinearRegression]]; MLE *as* [[OrthogonalProjection]].
  - **Ch 10 [[PrincipalComponentAnalysis|PCA]]** — four equivalent derivations (max variance, min reconstruction error, [[KarhunenLoeveTransform]], probabilistic latent-variable); [[DataCovarianceMatrix]]; algorithm via [[Eigendecomposition]] (or directly [[SingularValueDecomposition|SVD]]).

**Why this corpus matters now.** Every other textbook corpus assumes its content. When Murphy writes "let $\boldsymbol\Sigma$ be SPD" or "by Cauchy-Schwarz" or "the Hessian $\nabla^2 f$" or "let's apply Bayes' rule with conjugate prior," the reader needs MML. When ISLR derives the normal equations or projects onto the principal subspace, the reader needs MML. When [[1706.03762-attention-is-all-you-need]]'s attention is "scaled dot-product" + "softmax-cross-entropy NLL," the reader needs MML Ch 3 (inner products) + Ch 6 (NLL = exponential-family loss). When [[2001.08361-scaling-laws]] fits a power law to cross-entropy, the reader needs MML §8.3 (MLE) + Ch 6 ([[CrossEntropyLoss]] via Bernoulli/Categorical likelihoods).

introduces the [[MarginalLikelihood|marginal-likelihood]] objective $-\tfrac{1}{2}\mathbf{y}^\top[K_\theta+\sigma^2 I]^{-1}\mathbf{y}-\tfrac{1}{2}\log|K_\theta+\sigma^2 I|+c$ that compartmentalizes into data-fit + complexity-penalty and **encodes [[OccamsRazor|Occam's razor]] automatically** — the single biggest ML contribution to GP research; full-batch [[Adam]] / L-BFGS since the marginal likelihood does not factorize over data). Builds the searcher / scheduler / tuner API ([[d2l-hyperparameter-optimization]] §hyperopt-api — the same decomposition implemented by [[SyneTune]], [[RayTune]] and [[Optuna]]); implements [[RandomSearch]] from a SciPy `loguniform` config space and grounds it in the [[JamesBergstra|Bergstra]] & [[YoshuaBengio|Bengio]] 2012 *random-beats-grid* result; benchmarks it against [[BayesianOptimization]] ([[JasperSnoek|Snoek]] et al. 2012 — BO matches random search ≤1000 s, dominates afterwards via surrogate-model exploitation); distributes random search asynchronously via [[SyneTune]] § rs-async (linear $K$-worker speed-up because each config is independent of past observations — *unlike* model-based methods which need synchronization); introduces [[MultiFidelityOptimization|multi-fidelity HPO]] with the objective $f(\mathbf{x}, r)$, $r$ a resource budget (epochs / subset size / CV folds) and the assumption that low-$r$ rankings predict high-$r$ rankings; implements [[SuccessiveHalving]] ([[Jamieson|Jamieson & Talwalkar 2016]] / [[Karnin|Karnin et al. 2013]]) — $N=\eta^K$ configs at $r_\text{min}$, keep top $1/\eta$ at each rung, only one reaches $r_\text{max}$ — flagging the synchronization-barrier idle-worker pathology of synchronous SH on heterogeneous workloads; and finally pivots to **[[ASHA|asynchronous successive halving]]** ([[LishaLi|Li]] et al. 2018) — *"promote the moment $\eta$ observations land on a rung"* — the algorithm that eliminates SH's barrier at the cost of mildly-suboptimal early promotions, ubiquitous in production HPO ([[SyneTune]] / [[RayTune]] / [[Optuna]]). Closes by positioning [[NeuralArchitectureSearch|NAS]] and [[AutoML]] as natural HPO extensions. The chapter is the **non-learnable-parameter complement to [[d2l-optimization]]** — where the optimization chapter handles SGD/Adam search over learnable weights, this one handles black-box / multi-fidelity search over the hyperparameters that those optimizers themselves require); and [[d2l-generative-adversarial-networks]] (the two-section *Generative Adversarial Networks* chapter — D2L's **first dedicated generative-modeling chapter**, pivoting from discriminative learning into the regime where training's output is a *sampler*, not a classifier. §`gan` builds the [[generativeadversarialnetwork|GAN]] from first principles on a 2-D Gaussian toy: [[Generator|generator]] $G$ maps noise $\mathbf{z}\sim\mathcal{N}(0,1)$ to fakes; [[Discriminator|discriminator]] $D$ is a binary BCE classifier; the two play a [[MinMaxGame|minimax game]] $\min_D\max_G\{-E_x\log D(\mathbf{x})-E_z\log(1-D(G(\mathbf{z})))\}$ from [[IanGoodfellow|Goodfellow]], Pouget-Abadie, Mirza et al. 2014; the non-saturating $\min_G\{-\log D(G(\mathbf{z}))\}$ reformulation feeds fakes through $D$ with the *real* label $y=1$ to fix the vanishing-gradient pathology of the original $\max_G$ objective when $D(G(\mathbf{z}))$ is small early in training. §`dcgan` scales the scaffold to RGB-image synthesis on a Pokémon-sprite dataset via [[DCGAN]] ([[AlecRadford|Radford]], Metz & Chintala 2015): all-convolutional discriminator (4 strided convs + [[BatchNormalization|BN]] + [[LeakyReLU]] $\alpha=0.2$ — fixes the "dying ReLU" pathology that would otherwise cripple $D$ early in training) and mirror-image generator (4 [[TransposedConvolution|transposed convs]] + BN + [[ReLU]] inflating $1{\times}1{\times}100$ noise through $4{\times}4 \to 8{\times}8 \to 16{\times}16 \to 32{\times}32 \to 64{\times}64$ with channel widths $100\!\to\!512\!\to\!256\!\to\!128\!\to\!64\!\to\!3$ and a final $\tanh$ landing in $[-1,1]$). Practical recipe: same LR for both nets, weights init $\mathcal{N}(0, 0.02)$, **Adam $\beta_1 = 0.5$** (vs default $0.9$) to track the fast-changing adversarial gradients — the single most-cited hyperparameter tweak in the GAN literature. The chapter is operationally minimal but conceptually load-bearing: it grounds the [[generativeadversarialnetwork|GAN]] concept page (previously cited only at the framing level via [[d2l-introduction]]), introduces the [[TransposedConvolution]]-as-upsampling-primitive role beyond [[FCN]] (cf. [[d2l-computer-vision]]), and sets up the [[DiffusionModel|diffusion]] successor story D2L's Introduction already flagged — diffusion models have "started to replace GANs in production systems like DALL-E 2 and Imagen"); and [[d2l-recommender-systems]] ([[ShuaiZhang|Zhang]] ([[Amazon]]), [[AstonZhang|Zhang]] ([[Amazon]]) & [[YiTay|Tay]] ([[google|Google]])'s ten-section *Recommender Systems* chapter — D2L's only chapter on **personalized retrieval / ranking** as a learning problem distinct from classification and regression. Builds the recommender stack on [[MovieLens]] 100K (943 users × 1682 movies, 93.695% sparse [[InteractionMatrix|interaction matrix]]): [[CollaborativeFiltering|CF]] taxonomy ([[MemoryBasedCF|memory-based]] / [[ModelBasedCF|model-based]] / hybrid; It demonstrates that the `[[wikilink]]` graph + source-page + concept-page architecture generalizes to *any* technical domain with terminology, layered dependencies, and design tradeoffs. The Rust-specific patterns ([[TypeStateProgramming]], [[ZeroCostAbstraction]], [[Singleton]]) and the hardware-specific patterns ([[MemoryMappedIO]], [[VolatileMemoryAccess]], [[Interrupt]], [[NVIC]], [[ExceptionFrame]]) are now first-class citizens of the wiki and reachable from anywhere via the standard query workflow.

## XI. *Embedded Controllers Using C and Arduino* ([[JamesFiore]] — single 166-page book, ingested 2026-05-17)

The wiki's **second embedded-systems corpus** and the load-bearing **counter-example** to the Rust-first pedagogy of corpus X. Fiore's [[embedded-controllers-fiore|*Embedded Controllers Using C and Arduino*]] (version 2.1.11, 15 Oct 2024, CC BY-NC-SA — see [[OER]]) is the textbook for a one-semester embedded-controllers course in [[MohawkValleyCommunityCollege|MVCC]]'s AAS Electrical Engineering Technology program. Two halves:

- **Chs. 1–14: [[CLanguage|C language]] tutorial** for students arriving from Python / BASIC / Pascal — memory model, types, functions, libraries, [[BitwiseOperations|bitwise ops]], `#define`, pointers, arrays, structures. The last four chapters (linked lists, malloc/free, file I/O, command-line args) are marked optional because real small-MCU code rarely needs them.
- **Chs. 15–29: "Bits & Pieces"** — embedded chapters that drop down to the [[ATmega328P]] [[AVR]] microcontroller on the [[ArduinoUno|Arduino Uno]] and read the [[Arduino]] runtime library source code chapter by chapter (`pinMode`, `digitalWrite`, `digitalRead`, `analogRead`, `analogReference`, `analogWrite`, `delay`, `ISR(...)`). Each chapter opens with the library's public docs, dissects the implementation in [[wiring_digital_c|`wiring_digital.c`]] / [[wiring_analog_c|`wiring_analog.c`]], then shows the equivalent direct-register C (`PORTB |= 0x01;`, `DDRB |= 0x3F;`, `sbi(ADCSRA, ADSC);`) that runs faster and works on any AVR — not just an Arduino board.

**Anchor concepts introduced.** [[Arduino]] / [[ArduinoUno]] / [[ATmega328P]] / [[AVR]] / [[Atmel]] / [[ArduinoCC]] / [[JamesFiore]] / [[MohawkValleyCommunityCollege]]; the [[HarvardArchitecture|Harvard]]-vs-[[VonNeumannArchitecture|Von-Neumann]] and [[RISC|RISC]]-vs-[[CISC]] taxonomies; the [[DataDirectionRegister|DDR]] / [[PortRegister|PORT]] / [[PinRegister|PIN]] register triple that underlies AVR [[GPIO]]; [[ADC|10-bit ADC]] with `ADCSRA` / `ADMUX` programming; [[PulseWidthModulation|PWM]] via three [[TimerCounter|timer/counters]]; [[InterruptServiceRoutine|ISR]] mechanics with the 26-vector table and the `ISR(VECTOR_vect)` macro; [[StatusRegister|SREG]]'s `I T H S V N Z C` bits and the manual-save-on-ISR discipline; [[CrossCompiler|cross-compilation]] as the embedded toolchain shape; [[FlashMemory]] / [[SRAM]] / [[EEPROM]] memory-tier comparison; [[BitwiseOperations|bitwise idioms]] and the Arduino `bitSet` / `bitClear` macro family; [[PullUpResistor]] mechanics and the pin-13-LED caveat; [[OER]] as the publishing model.

**The tension with corpus X.** Same hardware abstraction at the bottom (GPIO pin = DDR-bit + PORT-bit + PIN-bit + pull-up MOSFET + Schmitt trigger; ADC = successive-approximation 10-bit + multiplexer; timer = up-counter + compare-match + waveform gen). **Opposite design philosophy at the top:**

| Axis | [[TheEmbeddedRustBook]] (Rust on Cortex-M) | [[embedded-controllers-fiore]] (C on AVR) |
|---|---|---|
| Substrate | 32-bit [[ARMCortexM\|Cortex-M4]] / [[STM32F303VCT6]] / 256 k Flash / 48 k SRAM | 8-bit [[AVR]] / [[ATmega328P]] / 32 k Flash / 2 k SRAM |
| Language | [[RustLanguage\|Rust]] with `#![no_std]` | [[CLanguage\|C]] |
| Abstraction layer | [[HALCrate\|HAL]] over [[PeripheralAccessCrate\|PAC]] over [[MicroArchitectureCrate\|µarch]] crate | Arduino Wiring library; bypass via direct register writes when needed |
| Safety stance | [[TypeStateProgramming\|Typestate]] + [[StaticGuarantee\|static guarantees]] + [[ZeroCostAbstraction\|zero-cost abstractions]] — misuse becomes a compile-time type error | Hardware understanding first; safety comes from knowing the registers, not from the type system |
| Build system | [[Cargo]] + [[Rustc]] + linker scripts | Arduino IDE wrapping `avr-gcc` + `avrdude` |
| Concurrency | [[Send]] + [[Sync]] + [[Mutex]] + [[CriticalSection]] + [[RTIC]] | `volatile` + `sei()` / `cli()` brackets |
| Audience | Production embedded engineers writing portable safe firmware | First-time embedded undergraduates learning what a register is |

Neither corpus is wrong. The Rust book argues that production firmware needs the type-system payoff because mistakes are common and expensive; Fiore argues that you cannot use the type-system payoff without first understanding what's underneath, and the OER-textbook audience hasn't paid for that intuition yet. A student going from this corpus to corpus X gets the safety machinery added to their existing hardware mental model; a student going the other direction gets the hardware intuition that Rust's typestate API otherwise hides. **The wiki should serve both trajectories.**
