# Machine Learning Systems (mlsysbook Vol 1) — Ch 4: Data Engineering

## Summary

Chapter 4 is the **capstone of Part I (Foundations)** of Vijay Janapa Reddi's *Machine Learning Systems* ([mlsysbook.ai/vol1](https://mlsysbook.ai/vol1), Harvard, 2026), the chapter that turns the workflow of [[mlsysbook-ch03-ml-workflow|Ch 3]] into a "factory floor." Its governing thesis is that **data is the actual source code of ML systems** — traditional code merely describes how to compile it — so the chapter reframes [[DataEngineering|data engineering]] not as "data cleaning" but as **Dataset Compilation**: a compiler-style pipeline (acquisition → ingestion → processing → labeling → storage → maintenance) where filtering is dead-code elimination, augmentation is loop unrolling, deduplication is common-subexpression elimination, and schema validation is the type checker. The corollary: datasets must be versioned (like git), unit-tested ([[DataQuality|quality]] checks), and debugged, and "retraining a model is simply recompiling the binary."

The chapter is organized by a **[[FourPillarsOfDataEngineering|four pillars framework]]** — Quality, Reliability, Scalability, Governance — applied at every stage, with the [[DataCascade|data cascade]] (errors at collection silently amplifying through the whole pipeline) as the motivating failure pattern. It opens with the **physics of data** ([[DataGravity|data gravity]], [[InformationEntropy|information entropy]], the energy-movement invariant, and the "feeding tax" / [[DataLoaderChokePoint|dataloader choke point]]), then runs a single **[[KeywordSpotting|Keyword Spotting (KWS)]]** lighthouse through acquisition, ingestion ([[BatchIngestion|batch]] vs [[StreamIngestion|streaming]], [[ETL]] vs [[ELT]]), systematic processing (the [[TrainingServingConsistency|consistency imperative]], [[Idempotency|idempotent]] transforms, distributed processing under [[AmdahlsLaw|Amdahl's Law]]), [[DataLabeling|labeling]] (label types, consensus, [[AIAssistedLabeling|AI-assisted]] / [[WeakSupervision|weak supervision]] / [[ActiveLearning|active learning]], automated [[ForcedAlignment|forced-alignment]] labeling), [[StorageArchitecture|storage architecture]] (databases vs warehouses vs lakes, file formats, [[FeatureStore|feature stores]], [[DataVersioning|data versioning]]), and finally **operational data health** ([[DataDebt|data debt]] categories and a debugging flowchart).

It is rich with memorizable constants (2024 cloud pricing): data work is 60–80% of ML effort; labeling can cost 500×–1,500× a single 8×A100 ResNet-50 run; moving 1 PB across a 10 Gbps link takes ~9 days and ~$90K egress; local NVMe loads ~50× faster than object storage; Parquet over CSV is "mathematically equivalent to buying a 5× faster hard drive." It explicitly extends the prior DMLS Ch 3 data-engineering source ([[dmls-ch03-data-engineering]]) and links forward to model compression, model training, and MLOps chapters.

## Key Claims

- **Data is the source code of ML systems.** Changing the data changes system behavior even if no traditional code changes; subtle labeling inconsistencies → subtle behavioral inconsistencies; missing edge cases → edge-case failures; historical bias → perpetuated bias. "Deleting a row of training data is the engineering equivalent of deleting a line of code, and retraining a model is simply recompiling the binary." Data work consumes **60–80% of ML project effort** (the "D" of the [[DAMTaxonomy|D·A·M taxonomy]]).
- **Data engineering = Dataset Compilation, not data cleaning.** The pipeline mirrors compiler phases: ingestion = lexer, pipeline architecture = compiler frontend, processing = optimization pass, retry/DLQ/circuit-breaker = runtime error handlers. [[DataDeduplication|Deduplication]] = common-subexpression elimination; [[DataAugmentation|augmentation]] = loop unrolling; [[SchemaValidation|schema validation]] = type checker.
- **Physics of data: gravity, entropy, and the feeding tax.** [[DataGravity|Data gravity]] = movement cost = $D_{\text{vol}}/\text{BW}$ ([[IronLawOfMLSystems|iron law]] data term). Moving 1 PB over 10 Gbps takes ~9 days; ~$90K egress at 2024 AWS rates → "for petabyte-scale data, **code moves to data**; for gigabyte-scale, data moves to code." [[InformationEntropy|Information entropy]] = signal density (bits/byte); **Data Selection Gain ∝ Entropy / Gravity** — 1M identical images have high gravity, zero entropy; 10K diverse edge cases have low gravity, high entropy.
- **The energy-movement invariant.** Moving a bit costs ~100× to nearly 1,000,000× more energy than computing on it, rising as data leaves the chip (DRAM access ≫ 1 FP32 MAC; network transfer = hundreds of thousands× per bit). Pruning 50% of training data via dedup eliminates the most energy-intensive stages — *why data selection is the highest-leverage systems lever*.
- **The feeding tax / dataloader choke point.** Training step time $T_{\text{step}} = \max(T_{\text{compute}}, T_{\text{io}})$. A standard cloud disk can leave a 300-TFLOP/s accelerator >80% idle ("feeding tax"). Training ResNet-50 on an A100 needs ≥8 CPU dataloader workers just to keep the GPU from starving — adding more GPUs in the "starvation region" yields zero speedup.
- **Four interdependent pillars with explicit trade-offs.** Quality (correctness + coverage + freshness), Reliability (fault tolerance), Scalability (growth + cost), Governance (ethics + compliance). Tensions: validation overhead vs throughput; consistency vs distributed scale; privacy vs performance; bias mitigation vs data availability. Diagnostic lens: gradual accuracy decline → Quality (drift); intermittent crashes → Reliability; slow training despite hardware → Scalability; audit gaps → Governance. **Data infrastructure failures outnumber model failures by a wide margin** — yet practitioners instinctively debug the model first.
- **The pipeline-jungle failure (canonical cascade example).** A credit model rejected all applicants from a region because an upstream team changed `zip_code` from `integer` to `string`; "02139" was silently cast to 2139, the leading zero lost, and the model treated "2139" as a new high-risk category. Defense: explicit [[DataContract|data contracts]] and schema validation at the ingestion interface.
- **DLRM is the scalability lighthouse.** Recommendation models with billion+ users/items grow embedding tables to TB/PB scale; the wall is **memory capacity** (tables exceed single-GPU memory → sharding) and **sparse-access bandwidth**, not compute — distinguishing it from compute-bound ResNet and bandwidth-bound GPT-2.
- **KWS design space is quantified, not intuited.** Targets: 98% accuracy, <200 ms latency, <1 false wake/month, $150K budget, ≤64 KB always-on-island model, 6-month timeline. A "1 false wake/month" SLA over 1-second windows demands **>99.9999% rejection** (FPR ≈ 3.9×10⁻⁷) — standard "99% accuracy" is meaningless; evaluate on **False Accepts per Hour**. The $150K budget (60% labeling / 25% storage / 15% governance) at $0.10/label + 20% review buys ~750K real labels; final config = 16 kHz, 13 MFCCs, 750K real + 2M synthetic, INT8 local inference.
- **Cost constants to memorize (2024).** Crowdsourced image label cents; bounding box per box; expert medical label per study (radiologist); S3 Standard ~$23/TB-mo; Glacier retrieval — standard (3–5h) vs expedited (1–5 min, 3× cost) vs bulk (free, 5–12h); A100 GPU-hour $2–4; human review hour $15–50. **Labeling dominates storage and compute by 1–3 orders of magnitude**: a $100K labeling budget ≈ 500×–1,500× one 8×A100 ResNet-50 run; 80% of labeling effort goes to 20% of features (the long tail). Time constants span ~9 orders: label 1M images = 2–4 weeks; train ResNet-50 on ImageNet = 4–6h (8×A100); feature store lookup = 1–10 ms.
- **Acquisition is a strategic multi-source decision.** ImageNet's 14.2M images = 49,000 MTurk workers across 21,841 categories (2 years of [[FeiFeiLi|Fei-Fei Li]]'s labeling infrastructure); GPT-3 used tens of TB Common Crawl filtered to hundreds of GB plus curated web/books/Wikipedia. KWS needs 23.4M samples across 50 languages — no single method suffices. Four sources trade quality/cost/scale/ethics differently: preexisting datasets ([[Kaggle]], UCI, ImageNet), [[WebScraping|web scraping]], [[Crowdsourcing|crowdsourcing]] ([[AmazonMechanicalTurk|MTurk]]), and [[SyntheticDataGeneration|synthetic generation]]. Shared-dataset bias propagation: many models trained on one repo inherit identical blind spots → correlated failures.
- **Web scraping noise is irreducible by scale.** Scraping "traffic light" returns a 1914 manual-semaphore photo → spurious correlation (officer standing in street). No amount of scraped data removes the need for validation against anachronistic/contextually-inappropriate content; ongoing litigation bounds the legal/ethical envelope.
- **Synthetic data changes the scaling constraint, not validation burden.** Valuable for rare-event coverage and augmentation (AutoAugment, RandAugment, SpecAugment); inherits its generator's biases. A KWS system trained purely on synthesized speech fails on unmodeled accents/noises — synthetic augments real data, cannot replace it.
- **Quality through validation + statistical monitoring.** A self-driving car company had 15% of LiDAR point-cloud labels misaligned by 10–20 cm for 3 months — every record was *structurally* valid, so only **statistical** monitoring of label-to-sensor alignment caught it. Mechanical vs **semantic** quality: a dataset can be mechanically perfect (no nulls, correct types) yet semantically broken (all users suddenly 25 due to a default-value change). Validate both **Container** (mechanical) and **Content** (semantic). The [[KolmogorovSmirnovTest|K-S test]] is the continuous-feature drift detector ($\mathcal{D}_{\text{crit}} \approx 1.36\sqrt{(n_0+n_t)/(n_0 n_t)}$ ≈ 0.061 for n=1000); categorical drift uses PSI/chi-squared.
- **Data quality as code catches ~60% of issues pre-training.** [[GreatExpectations|Great Expectations]] / Pandera / Pydantic codify executable expectation suites (range, null, uniqueness, categorical-set checks) that fail CI/CD deployments before bad data reaches training; the suites version alongside training code. The remaining ~40% require runtime monitoring.
- **Drift taxonomy operationalizes the degradation equation.** Drift detection/response consumes **30–40% of ongoing ML ops effort**. The divergence term $\mathcal{D}(P_t \lVert P_0)$ is exactly what **[[PopulationStabilityIndex|PSI]]** (>0.2 = significant) and **[[KullbackLeiblerDivergence|KL divergence]]** measure. Four shift types: [[CovariateShift|covariate]] ($p(x)$ changes), [[LabelShift|label]] ($p(y)$ changes), [[ConceptDrift|concept]] ($p(y\mid x)$ changes — needs ground truth, hardest), and **label-quality drift** (annotation reliability degrades while data is stable — invisible to feature monitoring, detected via [[CohensKappa|Cohen's κ]] / Fleiss' κ; κ<0.4 = unreliable; a medical project dropped from κ=0.85 to 0.72 in 6 months as untrained annotators joined).
- **Reliability through graceful degradation.** Failure modes: data corruption (date format "YYYY-MM-DD"→"MM/DD/YYYY" passes schema, breaks features), [[SchemaEvolution|schema evolution]] (silent type changes degrade accuracy >5% for weeks), resource exhaustion. Patterns: exponential backoff (1s→2s→4s), [[DeadLetterQueue|dead letter queues]] (dual-use: failure analysis *and* surfacing model blind spots — a fraud DLQ revealed a new payment type), [[CircuitBreaker|circuit breakers]] (closed/open/half-open), multi-tier fallback (stale/approximate features), progressive timeouts.
- **Ingestion: batch vs streaming is a value-of-latency judgment.** Streaming is ~3× (often an order of magnitude) more expensive per byte: always-on infra + redundancy + low-latency networking, no batch economies of scale. Worked example: 1M events/s × 1 KB = 1 GB/s; streaming ~$120/day (100 always-on cores) vs batch ~$33/day. Streaming adds [[Backpressure|backpressure]] handling and freshness SLAs (100 ms vs 1 hr → different infra). Hybrids predominate.
- **ETL vs ELT is a transformation-authority choice.** [[ETL]] validates schema + distributional properties before loading (clean warehouse, but reprocessing all sources on schema change = hours/days); [[ELT]] loads raw then transforms in-warehouse via SQL (flexible, faster iteration — minutes per schema change vs ETL's 8× longer, but higher storage + repeated compute + privacy risk from raw retention). Worked 10 TB/day example: ETL slightly cheaper on cloud cost, ELT 8× cheaper on engineering time per schema change. [[CAPTheorem|CAP theorem]] governs streaming choices: [[ApacheKafka|Kafka]] = CP (consistency + partition tolerance, availability gap during leader re-election), Pulsar = AP, Kinesis exposes the trade-offs.
- **Feature computation placement: storage pays or compute/latency pays.** Pipeline-computed (precomputed/materialized): fast training, reproducible, but storage cost + staleness + inflexibility. Loader-computed (on-the-fly): always fresh, flexible, low storage, but slow training + idle GPUs + nondeterminism risk. Hybrid predominates: precompute expensive/stable features (user embeddings), compute cheap/time-sensitive features (recency) in the loader.
- **The consistency imperative is a mathematical requirement.** Transformation logic must be immutable across training/serving; degradation ∝ $\mathcal{D}_{\text{KL}}(p_{g_{\text{serve}}} \lVert p_{g_{\text{train}}})$. Not "fixed" by sharing code — it's a **state synchronization** problem: parameters computed on training data (means, std devs, vocabularies) must be persisted alongside the model and reused at serving. [[TrainingServingSkew|Training-serving skew]] (e.g., a materialized view refreshed weekly in training vs daily in serving) causes 10–15% accuracy drops with no errors. **Architectural guarantees (shared code, not copied code) are the only reliable fix.**
- **Idempotency + determinism enable safe retries.** [[Idempotency|Idempotent]] = light switch (reapply → same result, via upsert-by-key) vs toggle (append → duplicates corrupt training data). [[DeterministicTransformation|Deterministic]] = no dependence on time/RNG/global state: replace "days since event" with "days from event to fixed reference date"; seed RNGs from input data. KWS: same audio → same MFCC features regardless of when/where computed; FFT window, hop length, coefficient count versioned with code.
- **Distributed processing pays a coordination tax bounded by Amdahl's Law.** Local ops = µs, network coordination = ms (1,000× gap). Mean-normalizing 1 TB across 100 nodes: gathering centrally ~105–120s vs local-means-then-aggregate ~0.05–0.2s (hundreds–thousands× faster). Operations that *reduce* data (sum/mean/count) run locally first; operations that *expand* (joins/cross-products) face unavoidable network cost — the [[MapReduce]] compute-follows-data principle. [[AmdahlsLaw|Amdahl's Law]]: embarrassingly-parallel KWS feature extraction gets ~64× on 64 cores, but coordination-heavy global normalization only ~10×. Exhaust single-machine optimization (Parquet over CSV, Dask/Vaex out-of-core) before distributing.
- **Labeling is the most human-dependent, error-prone, expensive stage.** Ground truth is a *proxy*, not reality. Label types scale in cost/storage: classification (1 scalar) → bounding box (4 coords/object, 10–20× slower than classification) → segmentation mask (~2.1M pixel labels for 1080p, ~50,000× more scalar entries than 10 boxes) → caption → transcription. Some fraction of labels is always wrong (manage, don't eliminate). Consensus: collect 3–5 labels, compute **Fleiss' κ**; κ<0.4 → route to expert review (5–15% of examples); expert review costs 10–50× crowdsourcing but forcing nonexpert majority votes on ambiguous cases produces biased labels.
- **AI-assisted labeling is a force multiplier, not a replacement.** Hierarchy (precision↓, throughput↑): traditional supervision → [[SemiSupervisedLearning|semi-supervised]] → [[WeakSupervision|weak supervision]] ([[Snorkel]] labeling functions) → [[TransferLearning|transfer learning]], with [[ActiveLearning|active learning]] as the cost-saving alternative. Pre-annotation cuts manual effort 50–80%. LLM labeling: $0.01–$1/example, 100–10,000 req/min limits, needs output validation. **Active learning**: query highest-uncertainty examples → 50–90% fewer labels than random; but compute must be in the budget model — scoring a full 10M-image pool at $0.01/image = $100K *before any labels*, exceeding a $50K budget. Viable only if the candidate pool is pre-filtered or compute is funded separately.
- **Automated labeling via forced alignment makes corpus-scale KWS feasible.** [[ForcedAlignment|Forced alignment]] (Viterbi) aligns known transcriptions to audio at ms precision, converting sentence-level audio to word-level samples at near-zero marginal cost. MSWC: 23.4M one-second examples, 340K keywords, 50 languages. Manual labeling at 10 s/example would take ~65,000 hours ≈ 32+ person-years — infeasible.
- **Storage architecture optimizes IOPS vs throughput per workload.** Databases (OLTP) = high IOPS / small blocks → online feature serving (random reads); warehouses (OLAP, columnar) = high throughput → batch training / feature engineering (5–10× I/O reduction reading only needed columns); data lakes = capacity + schema-on-read → petabyte raw training data (degrade into "data swamps" without metadata/cataloging). Choosing wrong = order-of-magnitude penalty no software fix can overcome. Mature orgs use all three via a unified catalog.
- **Storage performance is the iteration-speed lever.** Tiers (2024 $/TB-mo): NVMe local $100–300 / 5–7 GB/s / 10–100 µs; object S3/GCS $20–25 / 100–500 MB/s / 10–50 ms; warehouse $20–40 / 1–5 GB/s columnar; in-memory cache (Redis) $500–1000 / 20–50 GB/s / 1–10 µs; archival (Glacier) $1–4 / hours. KWS 736 GB dataset: NVMe loads ~50× faster than object storage — daily vs weekly iteration. Jeff Dean's latency numbers (if a CPU cycle were 1 second): L1=1s, DRAM=3 min, local SSD=2 days, cross-country network=6 years.
- **File format and compression directly scale effective bandwidth.** Effective Bandwidth = Physical Bandwidth × η_format. Reading 20 of 100 columns: CSV η=0.2 (wastes 80%), Parquet η≈1.0 → "switching CSV→Parquet is mathematically equivalent to buying a 5× faster hard drive." Columnar (Parquet/ORC) = 5–10× I/O reduction (20–100× with dictionary/RLE compression). [[Snappy]] (2–3× compression, 500 MB/s decompress) beats gzip (6–8×, 120 MB/s) for training throughput — over 50 epochs on 100 GB, ~7 hours saved. JSON/CSV decode can be 10× slower than columnar binary — the CPU becomes the bottleneck, idling an H100.
- **Storage bandwidth budget dictates training speed.** Saturating an A100 on ResNet-50 needs the storage to deliver multiple GB/s (max throughput / image size). SATA SSD (~500 MB/s) caps the $15,000 GPU at ~13% utilization ("expensive space heater"); S3 needs ~30+ concurrent worker threads; NVMe is required. Training Throughput = min(Compute Capacity, Data Supply Rate). NVIDIA DALI offloads augmentation to the GPU.
- **Model artifacts impose unique storage needs.** GPT-3 ≈ 700 GB FP32 (175B × 4 bytes), ~350 GB FP16 — exceeds many orgs' operational databases. AlexNet (60M params, 2012) → GPT-3 (175B, 2020) = ~3,000× growth in 8 years. Git fails on large binaries; [[DVC]] / [[MLflow]] keep metadata pointers + content-addressed external storage. Activation/gradient checkpointing trades compute for GPU memory.
- **Feature stores eliminate skew by design.** Uber found **30–40% of initial deployments suffered training-serving skew**, motivating [[MichelangeloPlatform|Michelangelo]]. A feature store stores the *logic* (not just data), enforces point-in-time correctness, and exposes dual modes: offline store (columnar/Parquet, batch training) + online store (key-value/Redis, ms serving). Time-travel prevents label leakage (use Jan-14 features for a user who churned Jan-15). Online store: thousands–millions reads/s at single-digit ms.
- **Data debt compounds silently and superlinearly.** $\text{Debt}_n \approx \text{Debt}_0 (1+r)^n$ (r = 10–30%/period). Four categories: **documentation debt** (missing data cards/provenance), **schema debt** (accumulated workarounds, defensive null checks), **quality debt** (known-but-uncorrected errors; a 3% label-error dataset poisons every retrain via feedback loops), **freshness debt** (training distribution diverging from production). Thresholds: data cards <80%/<50%; schema branches >3/>10; label error >1%/>5%; days since retrain >90/>365; PSI >0.1/>0.25. Remediation = budgeted, not heroic: documentation sprints (20/80 by usage), schema contracts, ~10% capacity for quality burn-down, drift-triggered retraining. Strategic (conscious) debt is rational; unconscious debt is the danger.
- **Debug data before model.** Diagnostic flowchart: accuracy degrades over time → data drift (check PSI); train ≫ val → overfitting/label noise/duplicates; val ≫ production → training-serving skew (check transforms/schema/feature store); subgroup inconsistency → bias/coverage gap; only if all "no" → model architecture. *"Debugging the model before verifying data consistency wastes engineering cycles on the wrong part of the problem space."*

## Contradictions

- **No direct contradiction with [[dmls-ch03-data-engineering]].** mlsysbook Ch 4 is a deepening and re-grounding rather than a revision: where DMLS Ch 3 frames data sources, formats (row vs columnar), batch vs streaming, ETL/ELT, and data governance in MLOps terms, mlsysbook Ch 4 adds the systems-physics layer (data gravity, the energy-movement invariant, the iron-law data term, the feeding tax) and the compiler metaphor. Read DMLS Ch 3 as the practitioner's-workflow predecessor and mlsysbook Ch 4 as the systems-engineering formalization.
- **Batch-vs-streaming cost framing differs from [[dmls-ch07-model-deployment]].** DMLS Ch 7 (Huyen) argues that *online prediction* is not necessarily more expensive than batch and is "on track to become the default" because batch wastes compute on absent users (Grubhub 622K/31M). mlsysbook Ch 4 instead emphasizes that *streaming ingestion* is materially (~3×–10×) more expensive than *batch ingestion* per byte due to always-on infrastructure. No true conflict — the two are discussing different pipeline stages (inference serving vs data ingestion) and different cost drivers (request density vs always-on infra) — but the wiki should keep the "online/streaming is expensive" claims scoped to their stage.
- **"More data always helps" fallacy, consistent with [[DataSelection]].** Ch 4 explicitly rejects naive data accumulation (test loss follows a power law in dataset size; redundant low-entropy examples add mass without signal), reinforcing the [[DataSelection|data-selection]] and [[InformationEntropy|information-entropy]] arguments from Ch 1 and the active-learning/dedup levers rather than contradicting any wiki page.
