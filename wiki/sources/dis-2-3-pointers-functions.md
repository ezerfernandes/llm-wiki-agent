## Summary

Section 2.3 of [[DiveIntoSystems]] is the chapter that **operationalizes the [[PassByPointer|pass-by-pointer]] idiom** introduced in [[dis-2-2-pointers|Ch 2.2]] as the first of [[Pointer|pointers]]' five use cases — *"implement functions whose parameters can modify values in the caller's stack frame."* Ch 2.3 takes that one-liner and makes it the entire section: it formalizes the pass-by-pointer pattern as the [[CLanguage|C]] mechanism through which functions can modify argument values, codifies it as a **three-step recipe** ([[PointerDeclaration|pointer-typed parameter]] → [[AddressOfOperator|`&`]]-of-variable at call site → [[DereferenceOperator|`*`]]-deref in callee body), and walks a complete `change_value` worked example whose printed output (`x: 100 y: 30`) makes both effects visible at once — `y` receives the [[ReturnStatement|`return`]]ed original value (30) while `x` is *also* mutated through the pointer parameter (to 100). The section's headline claim re-states [[dis-1-4-functions|Ch 1.4]]'s [[PassByValue|pass-by-value]] rule **with surgical precision**: *"All arguments in C are passed by value … the parameter gets a copy of its argument value, and modifying the parameter's value does not change its argument's value."* The pass-by-pointer pattern does **not violate** this rule: *"the parameter still gets the value of its argument, but it is passed the value of an address. … changing a pointer parameter's value will not change its argument's value (that is, assigning the parameter to point to a different address will not change the argument's address value). However, by dereferencing a pointer parameter, the function can change the contents of memory that both the parameter and its argument refer to; through a pointer parameter, a function can modify a variable that is visible to the caller after the function returns."* This is the **same reconciliation** Ch 2.2 stated at the conceptual level (*"C is always pass-by-value; pass-by-reference is just pass-by-value of a pointer"*), now grounded in a runnable example and a [[StackFrame|stack-frame]] diagram showing `input`'s storage in `change_value`'s frame holding the [[CMemoryAddress|address]] of `x` in `main`'s frame. The chapter also names the **back-channel return** capability this unlocks: a function returns *one* value through [[ReturnStatement|`return`]] but can mutate *additional* caller variables through pointer parameters — the canonical workaround for [[CLanguage|C]]'s single-return-slot restriction. The connection to [[dis-1-5-arrays-strings|Ch 1.5]]'s [[CArray|array]] [[PassByReference|pass-by-reference]] story is made explicit: *"We have already seen similar functionality with array parameters, where an array function parameter gets the value of the base address of the passed array … In general, this same idea can be applied by passing pointer parameters to functions that point to the memory locations in the caller's scope."* Arrays-by-reference and explicit-pass-by-pointer are now revealed as **the same mechanism** — a pointer (or array name decayed to a pointer) is passed by value, and dereference inside the callee reaches the caller's storage.

## Key Claims

- **Pass-by-pointer is the [[CLanguage|C]] mechanism for function-side caller mutation.** Per the chapter's opening: *"Pointer parameters provide a mechanism through which functions can modify argument values. The commonly used **pass by pointer** pattern uses a pointer function parameter that gets the value of the address of some storage location passed to it by the caller."* Ch 2.3 promotes the [[PassByPointer|pass-by-pointer]] idiom from *"one of five [[Pointer|pointer]] use cases"* (its [[dis-2-2-pointers|Ch 2.2]] framing) to **the** mechanism — the entire section is built around it.
- **The three-step recipe.** Ch 2.3 codifies pass-by-pointer as three syntactic moves: (1) **declare the parameter as a [[Pointer|pointer]]** to the variable's type — `int change_value(int *input)` — so the parameter expects an [[CMemoryAddress|address]] of an `int`, not an `int` value; (2) **at the call site, pass the [[AddressOfOperator|address]] of a variable** of the matching type — `change_value(&x)` — letting the caller hand the callee a handle to its own storage; (3) **inside the body, [[DereferenceOperator|dereference]] the pointer parameter** to read (`val = *input;`) or write (`*input = 100;`) the caller's variable. The same three moves [[dis-2-2-pointers|Ch 2.2]] introduced as the pointer-variable mechanics are now re-applied at the function-parameter boundary.
- **[[CLanguage|C]] is still [[PassByValue|pass-by-value]] — but the *value* is now an [[CMemoryAddress|address]].** The chapter's precision-restatement: *"All arguments in C are passed by value and follow pass-by-value semantics: the parameter gets a copy of its argument value … In the pass-by-pointer pattern, the parameter still gets the value of its argument, but it is passed the value of an address."* The [[dis-1-4-functions|Ch 1.4]] rule is *not* broken — pointer parameters still receive a copy. What changes is the *type* of value being copied: an [[CMemoryAddress|address]] instead of an `int`/`float`/`char`. Mutations of the *parameter itself* (the local pointer) remain caller-invisible; mutations *through* the parameter (via [[DereferenceOperator|`*`]]) reach the caller because the address resolves to caller-side storage.
- **Pointer-parameter assignment is two-flavored, just like in [[dis-2-2-pointers|Ch 2.2]].** *"Changing a pointer parameter's value will not change its argument's value (that is, assigning the parameter to point to a different address will not change the argument's address value). However, by dereferencing a pointer parameter, the function can change the contents of memory that both the parameter and its argument refer to."* The same `ptr = &something_else;` vs `*ptr = value;` distinction Ch 2.2 made for pointer variables now applies to pointer *parameters*: rewiring the local copy is local-only; writing *through* the pointer crosses the function boundary.
- **The worked `change_value` example shows back-channel return.** The canonical code: `int change_value(int *input)` reads `val = *input;`, branches on `val < 100`, writes either `*input = 100` or `*input = val * 2`, and returns `val`. Called as `y = change_value(&x);` with `x == 30`, the function takes the *"low-value"* branch and writes `100` into `x` via the pointer parameter while returning the *original* `30` through the [[ReturnStatement|`return`]] slot. The output `x: 100 y: 30` makes the **two return channels** simultaneously visible: the [[ReturnStatement|`return`]]'s single value and the pass-by-pointer back-channel.
- **The single-return-value restriction of [[CLanguage|C]] is the headline problem pass-by-pointer solves.** [[dis-1-4-functions|Ch 1.4]]'s [[Function|function]] model gives one explicit output: the [[ReturnStatement|`return`]] value. Real functions often need to produce more than one — e.g. integer division wants both quotient and remainder; a parse routine wants both the parsed value and a *success / failure* status; a lookup wants both the located record and an *insertion point*. Pass-by-pointer provides *additional* output slots via pointer parameters — pass the addresses of the extra destinations, deref-write inside the function. Ch 2.3's `change_value` is the minimal demonstration: one [[ReturnStatement|`return`]] for the original value, one pointer parameter for the new value, both produced by the same call.
- **The [[StackFrame|stack-frame]] picture: a pointer parameter holds a [[CMemoryAddress|cross-frame address]].** Ch 2.3's diagram (Figure 1 in the source) shows `change_value`'s frame containing the local `input` (holding the [[CMemoryAddress|address]] of `main`'s `x`) and the local `val` (holding `30`, the value read through `*input`), while `main`'s frame contains `x` (now `100`, after the deref-write) and `y` (still uninitialized until `change_value` returns). The arrow from `input` *into* `main`'s frame is what makes pass-by-pointer work: the callee's local pointer reaches *across* the stack to the caller's storage. The [[dis-2-1-scope-memory|Ch 2.1]] [[StackSection|stack-section]] / [[StackFrame|frame]] geography is now load-bearing — pass-by-pointer is a function of *which frame stores the pointee*.
- **Arrays and pointers unify under the same mechanism.** *"We have already seen similar functionality with array parameters, where an array function parameter gets the value of the base address of the passed array (the parameter refers to the same set of array elements as its argument), and the function can modify the values stored in the array. In general, this same idea can be applied by passing pointer parameters to functions that point to the memory locations in the caller's scope."* The [[dis-1-5-arrays-strings|Ch 1.5]] [[PassByReference|array pass-by-reference]] story — promised a Ch 2 reconciliation — is now fully reconciled: the array name decays to a [[Pointer|pointer]] to its first element, the pointer is passed by value, and dereferences (including `a[i]` which is sugar for `*(a + i)`) reach the caller's array storage. Explicit pass-by-pointer is the same mechanism, just spelled out by the programmer instead of synthesized by array decay.
- **Type discipline carries across the function boundary.** The chapter notes: *"since the parameter's type is `int *`, the address passed must be the address of an `int` variable."* Just as [[dis-2-2-pointers|Ch 2.2]] forbade `char *cptr = &intvar;` for *pointer variables*, Ch 2.3 forbids `change_value(&char_var)` for *pointer parameters* — the compiler enforces type compatibility at the call site. The [[PointerType|pointer's static type]] determines what addresses are valid arguments; this is the language's only barrier between well-typed pass-by-pointer and the type-pun / [[BufferOverflow|buffer-overflow]] hazards of later chapters.

## Key Quotes

> "Pointer parameters provide a mechanism through which functions can modify argument values. The commonly used **pass by pointer** pattern uses a pointer function parameter that gets the value of the address of some storage location passed to it by the caller." — the section's headline definition; promotes [[PassByPointer|pass-by-pointer]] from a [[dis-2-2-pointers|Ch 2.2]] enumerated use case to *the* function-side caller-mutation mechanism.

> "All arguments in C are passed by value and follow pass-by-value semantics: the parameter gets a copy of its argument value, and modifying the parameter's value does not change its argument's value." — the surgical re-statement of [[dis-1-4-functions|Ch 1.4]]'s rule, set up to be *upheld* (not overturned) by what comes next.

> "In the pass-by-pointer pattern, the parameter still gets the value of its argument, but it is passed the value of an address. … by dereferencing a pointer parameter, the function can change the contents of memory that both the parameter and its argument refer to; through a pointer parameter, a function can modify a variable that is visible to the caller after the function returns." — the load-bearing reconciliation: pass-by-value of an [[CMemoryAddress|address]] gives caller-visible mutation without breaking [[PassByValue|pass-by-value]] semantics. The conceptual claim [[dis-2-2-pointers|Ch 2.2]] made at the variable level, now grounded at the function-parameter level.

> "We have already seen similar functionality with array parameters, where an array function parameter gets the value of the base address of the passed array (the parameter refers to the same set of array elements as its argument), and the function can modify the values stored in the array. In general, this same idea can be applied by passing pointer parameters to functions that point to the memory locations in the caller's scope." — folds [[dis-1-5-arrays-strings|Ch 1.5]]'s [[CArray|array]] [[PassByReference|pass-by-reference]] under the same mechanism; the reconciliation [[dis-2-2-pointers|Ch 2.2]] flagged is now fully delivered.

> "`int change_value(int *input);` ... `y = change_value(&x);` ... `*input = 100;`  ... output: `x: 100 y: 30`" — the worked example showing both return channels (the [[ReturnStatement|`return`]] producing `y == 30` and the pass-by-pointer back-channel producing `x == 100`) from a single function call.
