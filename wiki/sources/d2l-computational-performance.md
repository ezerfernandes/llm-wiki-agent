[[AstonZhang|Zhang]], [[ZacharyLipton|Lipton]], [[MuLi|Li]] & [[AlexanderSmola|Smola]]'s seven-section *Computational Performance* chapter — D2L's systems-and-scaling layer. Bridges the *single-GPU, single-process* idiom of the previous chapters to the *multi-GPU, multi-machine, hardware-aware* regime that every frontier deep-learning workload assumes. ## Key Claims

- **Imperative vs symbolic.** Python is an *interpreted language* — `e=add(a,b); f=add(c,d); g=add(e,f)` runs each statement individually with Python-interpreter overhead. *Symbolic programming* (Theano, original TensorFlow, MXNet Gluon `HybridSequential`) defines → compiles → executes; the compiler can skip Python entirely, rewrite `print(fancy_func(1,2,3,4))` as `print(10)`, and free intermediate memory. **Imperative is easier to write/debug; symbolic is more efficient and more portable** (independent of Python).
- **Hybrid programming bridges both.** PyTorch's [[TorchScript|`torch.jit.script`]], TensorFlow 2's `tf.function` (with optional `jit_compile=True` for [[XLA]]), and MXNet's `HybridSequential.hybridize()` all *write code imperatively, compile to symbolic*. After hybridization the model is a [[ComputationalGraph]] executed by a C++ backend with no Python in the inner loop; control flow involving Python `if`/`for`/`print` is dropped. The compiled form can be serialized (`net.save` / `net.export` / `tf.saved_model.save`) and loaded from non-Python front-ends (C++, R, Scala).
- **Frontend / backend decoupling = async dispatch.** Every modern framework ([[MXNet]], [[PyTorch]], [[TensorFlow]]) has a Python *frontend* that enqueues ops onto a C++ *backend* maintaining its own threads. By default **PyTorch GPU operations are asynchronous**: the Python call returns as soon as the op is queued. The backend tracks dependencies on a [[ComputationalGraph]] so it can refuse to parallelize ops with data deps. For 10,000 sequential `y=x+1`, async dispatch reduces total time from $10000(t_1+t_2+t_3)$ to $t_1+10000\,t_2+t_3$.
- **Implicit blockers ruin async.** Calls that force the frontend to wait: `npx.waitall()` / `torch.cuda.synchronize()` (explicit), printing a variable, `.asnumpy()`/`.item()` (NumPy / scalar conversion), and `wait_to_read()`. *Copying small amounts of data frequently from device to host can destroy performance of an otherwise efficient code* — each conversion forces the dependency graph to be evaluated. Recommendation: synchronize once per minibatch, keep logs on the GPU.
- **Auto-parallelism.** A single operator already uses all CPU cores / all SMs on a GPU, so parallelization buys little on a single device. Across multiple devices the framework's dep-graph scheduler *automatically* overlaps independent ops — e.g. two `dot` products on `gpu0` and `gpu1` finish in `max(t0,t1)` not `t0+t1` if you remove the intermediate barrier. **Computation–communication overlap** (PCIe DMA in flight while the GPU still computes) is the other axis: PyTorch exposes `non_blocking=True` on `.to()` / `.copy_()` for exactly this.
- **Memory hierarchy and the burst-vs-random asymmetry.** DDR4 RAM has ~100 ns address-setup followed by 0.2 ns per subsequent transfer in a burst read — **the first read is ~500× more expensive than subsequent ones**, so avoid random memory access and align data to 64-bit boundaries. CPU caches: ~tens of registers (1 cycle), L1 32–64 KB (1.5 ns / 4 cycles), L2 256–512 KB (5 ns / 12–17 cycles), L3 shared 4–256 MB (16 ns / 42 cycles). GPU global memory ≈ 200 ns; GPU shared memory ≈ 30 ns. *False sharing* across cache lines can make multi-threaded code slower than single-threaded.
- **GPU memory: HBM vs GDDR.** Server-grade GPUs (V100, A100, H100) use [[HBM|high-bandwidth memory]] stacked on a silicon interposer for ≥1 TB/s aggregate bandwidth; consumer cards (RTX/Titan) use GDDR6 at ≥500 GB/s. Wider memory bus (RTX 2080 Ti: 352-bit) lets more bytes move per cycle. **GPU memory is much smaller than CPU memory due to higher cost**.
- **GPU architecture: tensor cores + many cores.** GPUs scale by (a) adding wider vector / matrix units — [[TensorCore|tensor cores]] specialize in $4{\times}4$–$16{\times}16$ matrix multiplies at FP16/INT8/INT4 — and (b) adding many more cores (a Turing TU102 has 12 graphics-processing clusters × N streaming multiprocessors × 4 processing blocks each with 16 INT + 16 FP units + 2 tensor cores). **Training accelerators need higher precision (FP16/FP32 mixed) and more memory than inference accelerators** (which can run INT8/FP16 with no gradient storage) — NVIDIA T4 targets inference, V100 targets training.
- **Interconnects in order of bandwidth.** [[NVLink]] (300 Gbit/s per link, 6 links on V100 ≈ 18 GB/s × 6 per direction) > [[PCIe]] 4.0 16-lane (32 GB/s) > 100 GbE [[Ethernet]] (10 GB/s) > 1 GbE (100 MB/s). NVLink lives between GPUs in the same chassis; PCIe connects GPU↔CPU; Ethernet connects nodes. **D2L recommends [[NCCL]] for high-bandwidth GPU-to-GPU transfer**.
- **Three ways to parallelize a network across $k$ GPUs.** (1) **Network partitioning** — assign distinct *layers* to distinct GPUs (lets you train very large models, but tight cross-layer sync, hard to load-balance — *not recommended* unless you have framework support). (2) **Layerwise / [[TensorParallelism|tensor]] partitioning** — split the channels/units *within* a layer ([[AlexNet]] did this on 2× GTX 580 with 2 GB each — see [[fig_alexnet_original]]); scales compute and memory, but each layer requires sync barriers — *not recommended*. (3) **[[DataParallelism|Data parallelism]]** — every GPU holds a full model replica, shards the minibatch, computes local gradients, [[AllReduce|all-reduces]] gradients across GPUs, updates locally. **Data parallelism is the recommended default** because it scales to arbitrary devices, only requires sync at the end of each minibatch, and modern GPU memory is large enough to hold any reasonable model.
- **Data-parallel training procedure.** (a) Split the minibatch into $k$ shards distributed to $k$ GPUs; (b) each GPU computes loss + gradient on its shard against its local replica; (c) gradients are **aggregated** ([[AllReduce|all-reduced]]) across GPUs; (d) aggregated gradient is broadcast back; (e) each GPU updates its local parameters. Practical rule: **increase minibatch size $k$-fold and the learning rate accordingly when scaling to $k$ GPUs**; [[BatchNormalization]] needs per-GPU statistics. In modern frameworks `nn.DataParallel(net, device_ids=devices)` (PyTorch) or `gluon.Trainer` (MXNet) wraps all of this.
- **All-reduce is the universal primitive.** [[AllReduce]] sums a vector across all nodes and broadcasts the result back. D2L implements a naive O(n) version (everyone copies to GPU 0, sum, broadcast). The aggregation strategy interacts with hardware: on a 4-way GPU server, aggregating all gradients on one GPU (60 ms for 160 MB) is faster than CPU aggregation (80 ms — every GPU has to ship to CPU), but **splitting the gradient into 4 chunks and aggregating each chunk on a different GPU in parallel** (15 ms via the PCIe switch's full-bandwidth cross-traffic) is dramatically faster — synchronization strategy depends on bus topology.
- **Ring synchronization is $O(1)$ in the number of nodes.** Naive serial pass around $n$ nodes is $O(n)$. But by breaking the gradient into $n$ chunks and starting chunk $i$ from node $i$, each link is fully utilized in every step — total time $(n-1)/n \approx 1$, independent of $n$. On 8× V100 with [[NVLink]], 160 MB all-reduce takes ~6 ms via [[RingAllReduce|ring synchronization]] — better than the PCIe path even with 8 GPUs. [[Horovod]] uses ring-allreduce with NVLink topology awareness. *"Ring synchronization is not fundamentally different from other synchronization algorithms — the only difference is that the synchronization path is somewhat more elaborate."*
- **Parameter server scales across machines.** Single PS becomes a bandwidth bottleneck: $m$ workers → $O(m)$ ingest time. Sharding parameters across $n$ servers gives each server $O(1/n)$ work → total update time $O(m/n)$ — matching $m=n$ gives **constant scaling**. The PS abstraction is a [[KeyValueStore|key–value store]] with `push(key, value)` (accumulate gradient) and `pull(key, value)` (retrieve aggregated parameter) — a *commutative reduction* indexed by parameter key. **In practice the same machines serve as both workers and parameter servers**.

## Key Quotes

> "Imperative programming is easier. When imperative programming is used in Python, the majority of the code is straightforward and easy to write. It is also easier to debug imperative programming code. […] Symbolic programming is more efficient and easier to port. Symbolic programming makes it easier to optimize the code during compilation, while also having the ability to port the program into a format independent of Python." — §`hybridize` framing the imperative ↔ symbolic trade-off that motivates `torch.jit.script` / `tf.function` / `hybridize`.

> "By default, GPU operations are asynchronous in PyTorch. When you call a function that uses the GPU, the operations are enqueued to the particular device, but not necessarily executed until later. This allows us to execute more computations in parallel, including operations on the CPU or other GPUs." — §`async-computation`, the structural rationale for the frontend / backend decoupling.

> "Copying small amounts of data frequently from MXNet's scope to NumPy and back can destroy performance of an otherwise efficient code, since each such operation requires the computational graph to evaluate all intermediate results needed to get the relevant term before anything else can be done." — §`async-computation`, the canonical "don't `.item()` in a tight loop" warning.

> "Devices have overheads for operations. Hence it is important to aim for a small number of large transfers rather than many small ones. This applies to RAM, SSDs, networks and GPUs." — §`hardware` Summary, the universal cost-model rule of thumb for systems-aware deep learning.

> "If we use the same example of synchronizing 160 MB across 8 V100 GPUs we arrive at approximately $2 \cdot 160 \textrm{MB} / (3 \cdot 18 \textrm{GB/s}) \approx 6\,\textrm{ms}$. This is better than using the PCIe bus, even though we are now using 8 GPUs. […] The time spent to aggregate gradients does not grow as we increase the size of the ring." — §`parameterserver`, the surprising $O(1)$-scaling result that motivates [[RingAllReduce]] in [[NCCL]] / [[Horovod]].
