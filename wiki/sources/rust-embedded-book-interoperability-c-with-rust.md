## Summary

File 39/44 of *[[TheEmbeddedRustBook]]* — **first leaf** of the *Interoperability* chapter opened at file 38 ([[rust-embedded-book-interoperability-index]]). Operationalizes calling **C/C++ from Rust** as two orthogonal tasks: **(1) define the Rust-side interface** (data layout via [[ReprC|`#[repr(C)]`]] + function signatures via [[ExternC|`extern "C"`]] blocks, either hand-written or auto-generated by [[Bindgen]]), and **(2) build the C/C++ to a static archive** that Cargo's final link step pulls in (either by shelling out to `make`/`CMake` via `std::process::Command` from a [[BuildRs|`build.rs`]] script, or by compiling C directly with the [[CcCrate|`cc` crate]]). Explicit ABI guidance: C++ has **no stable ABI** for [[Rustc|rustc]] to target → always use the `C` ABI as the lingua franca. The chapter closes the prior chapter's promise that the marshaling table from [[rust-embedded-book-interoperability-index]] would be operationalized.

## Key Claims

- **Use the C ABI, never the C++ ABI** — *"As C++ does not have a stable ABI for the Rust compiler to target, it is recommended to use the `C` ABI when combining Rust with C or C++."* Even when calling C++, the public boundary must be `extern "C"`-declared (typically via a thin C wrapper layer). Cf. [[ReprC]] doing the same job for **data layout** that [[ExternC|`extern "C"`]] does for **function calling convention**.
- **The interface = two halves: layout + signature.** For each C header `cool.h` defining `typedef struct CoolStruct { int x; int y; } CoolStruct; void cool_function(int i, char c, CoolStruct* cs);`, the Rust translation is **(layout)** `#[repr(C)] pub struct CoolStruct { pub x: cty::c_int, pub y: cty::c_int }` + **(signature)** `extern "C" { pub fn cool_function(i: cty::c_int, c: cty::c_char, cs: *mut CoolStruct); }`. The `extern "C"` block declares the function exists in another translation unit — *"the definition of this function will need to be provided elsewhere, or linked into the final library or binary from a static library."*
- **Use `cty` for C primitive aliases.** *"Due to the flexibility of how C or C++ defines an `int` or `char`, it is recommended to use primitive data types defined in `cty`, which will map types from C to types in Rust."* The chapter uses `cty::c_int` / `cty::c_char` rather than direct `i32` / `i8` because **C primitive widths are platform-dependent** — `cty` is the [[NoStd|`no_std`]]-compatible equivalent of the `std::ffi` / `core::ffi` aliases the previous chapter ([[rust-embedded-book-interoperability-index]]) introduced.
- **Rust references don't cross FFI; raw pointers do.** *"As C does not have a concept of Rust's references, which would look like this: `&mut CoolStruct`, we instead have a raw pointer."* C-interop function arguments are typed as `*const T` / `*mut T` ([[RawPointer]]) — *"As dereferencing this pointer is `unsafe`, and the pointer may in fact be a `null` pointer, care must be taken to ensure the guarantees typical of Rust when interacting with C or C++ code."*
- **Auto-generate bindings with [[Bindgen]] instead of hand-translating.** Four-step recipe: (1) collect the C/C++ headers; (2) write a `bindings.h` that `#include`s all of them; (3) feed it (plus the compilation flags used by the C build) to `bindgen` — for `no_std` use `Builder.ctypes_prefix("cty")` (or `--ctypes-prefix=cty`) and `Builder.use_core()` (or `--use-core`) so the generated code is `#![no_std]`-compatible; (4) pipe the generated Rust to a `bindings.rs` in your project. Don't forget to depend on the [`cty`](https://crates.io/crates/cty) crate.
- **`build.rs` is Rust's pre-build hook — runs on the host, before your crate.** *"A `build.rs` script is a file written in Rust syntax, that is executed on your compilation machine, AFTER dependencies of your project have been built, but BEFORE your project is built."* Three canonical uses: code generation (calling [[Bindgen]]), shelling out to external build systems (`Make` / `CMake` via `std::process::Command`), and **direct C/C++ compilation** via the [[CcCrate|`cc` crate]]. **Crucial subtlety:** the target crate may be `no_std` / `thumbv7m-none-eabi`, but **`build.rs` itself executes on the *host*** — *"This means you may use any Rust crates which will run on your compilation host."*
- **For complex C builds: shell out via `std::process::Command`.** *"For projects with complex external projects or build systems, it may be easiest to use `std::process::Command` to 'shell out' to your other build systems by traversing relative paths, calling a fixed command (such as `make library`), and then copying the resulting static library to the proper location in the `target` build directory."*
- **For simple C builds: use the [[CcCrate|`cc` crate]].** *"In the simplest case of compiling a single C file as a dependency to a static library, an example `build.rs` script using the [`cc` crate] would look like this:"*
  ```rust
  fn main() {
      cc::Build::new()
          .file("src/foo.c")
          .compile("foo");
  }
  ```
  The `build.rs` is placed at the **package root**. *"Then `cargo build` will compile and execute it before the build of the package. A static archive named `libfoo.a` is generated and placed in the `target` directory."*
- **For prebuilt static archives, skip the build.** *"If the library you would like to use is already distributed as a static archive, it is not necessary to rebuild your code. Just convert the provided interface header file as described above, and include the static archive at compile/link time."* The interface-translation half is still required; only the compilation half is skipped.
- **Static archive is the embedded delivery format.** *"For embedded projects, this most commonly means compiling the C/C++ code to a static archive (such as `cool-library.a`), which can then be combined with your Rust code at the final linking step."* — there is no dynamic loader in [[BareMetalProgramming|bare-metal]] firmware, so dynamic linking is not an option.

## Key Quotes

> "As C++ does not have a stable ABI for the Rust compiler to target, it is recommended to use the `C` ABI when combining Rust with C or C++." — the ABI universalization principle

> "Before consuming C or C++ code from Rust, it is necessary to define (in Rust) what data types and function signatures exist in the linked code. In C or C++, you would include a header (`.h` or `.hpp`) file which defines this data. In Rust, it is necessary to either manually translate these definitions to Rust, or use a tool to generate these definitions." — naming the interface-translation problem

> "By default, Rust does not guarantee order, padding, or the size of data included in a `struct`. In order to guarantee compatibility with C code, we include the `#[repr(C)]` attribute, which instructs the Rust compiler to always use the same rules C does for organizing data within a struct." — the FFI motivation for [[ReprC|`#[repr(C)]`]] (parallel to [[rust-embedded-book-peripherals-a-first-attempt]]'s MMIO motivation)

> "This statement defines the signature of a function that uses the C ABI, called `cool_function`. By defining the signature without defining the body of the function, the definition of this function will need to be provided elsewhere, or linked into the final library or binary from a static library." — what `extern "C" { fn ... }` means semantically

> "As the Rust compiler does not directly know how to compile C or C++ code (or code from any other language, which presents a C interface), it is necessary to compile your non-Rust code ahead of time." — why `build.rs` exists for FFI

> "While your crate may be targeting a `no_std` embedded platform, your `build.rs` executes only on machines compiling your crate. This means you may use any Rust crates which will run on your compilation host." — the host/target split inside one Cargo package
