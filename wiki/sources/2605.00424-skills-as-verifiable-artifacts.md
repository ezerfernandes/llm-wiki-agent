## Summary
Alfredo Metere (Metere Consulting) argues a SKILL.md package is **untrusted code until verified**. Signature + clearance is not behavioral verification; the runtime must default to HITL for irreversible calls and only relax that gate as a function of an explicit, immutable per-skill verification level. The paper specifies a trust schema (manifest tuple with classification label, capability set, signer, version, verification level), a four-state HITL lifecycle for irreversible side-effects, and a **biconditional correctness criterion** — every observed corpus delta must match an approved-and-executed audit record and vice versa — which doubles as a benchmark a candidate skill-verification procedure must pass on an adversarial ensemble. Ten normative guidelines (G1–G10) abstracted from the reference implementation **enclawed** sketch a portable runtime profile for any SKILL.md-adopting harness.

## Key Claims
- **Skills are a new supply-chain surface.** A skill is a persistent prompt-injection vector that survives context truncation; the analogous attack class (memory/KB poisoning) has already been demonstrated in the wild.
- **Default-untrusted is the only stable HITL discipline.** Without verification, HITL must fire on every irreversible call, which degrades into rubber-stamping at scale; the fix is verification, not weaker gates.
- **Verification happens at bootstrap, never at runtime.** Verification levels (`unverified` / `declared` / `tested` / `formal`) are pinned to the signed manifest pre-bootstrap and are immutable for the session — a fixed enum, not a continuous trust score, to prevent the agent from arguing itself into permission gradients.
- **No agent mutation of loaded skills.** Any attempted modification is itself an irreversible capability that walks the HITL gate and is hash-chained-audited; on approval it produces a new artifact requiring re-verification.
- **Capability vocabulary is finite and irreversibility-tagged.** `net.egress`, `fs.read`, `fs.write.rev`, `fs.write.irrev`, `tool.invoke`, `spawn.proc`, `publish`, `pay`, `mutate.schema`. The reversible/irreversible split is the design's load-bearing distinction.
- **Biconditional correctness criterion.** `delta(s0, s1) == { approved-and-executed records }` (multiset, projected on op-and-target). Catches gate bypass (F1), audit forgery (F2), approved-but-failed-silently (F3), wrong-target execution (F4). Does not catch read-only exfiltration, TOCTOU races, or attacker-coincident actions.
- **Adversarial-ensemble evaluation.** K agents biased toward destruction (cleaner / consolidator / auditor / critic) over R rounds on a SHA-256-baselined corpus; verdict is mechanical (binary, deterministic for fixed broker policy).
- **Ten guidelines G1–G10.** Capability bootstrap, deny-by-default, mandatory classification, clearance-bounded signing, hash-chained audit, reversible/irreversible split, biconditional post-hoc check, adversarial test corpus, named configuration profiles (strict vs dev — no feature-flag continuum), and a no-bypass-switch invariant.

## Key Quotes
> "A skill is untrusted code until it is verified, and the runtime that loads it must enforce that default rather than infer trust from a signature, a clearance, or a registry of origin."
> "The skill is the instruction; the model is the executor."
> "Verification is what buys the runtime permission to stop asking, and only for what the verification covered."
