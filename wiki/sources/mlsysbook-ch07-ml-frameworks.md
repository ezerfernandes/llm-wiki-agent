# Machine Learning Systems (mlsysbook Vol 1) — Ch 7: ML Frameworks

## Summary

Chapter 7 of Vijay Janapa Reddi's *[[MachineLearningSystems|Introduction to Machine Learning Systems]]* (Vol 1, Harvard / mlsysbook.ai, 2026) — the software chapter of the *Build* part — argues that **a machine learning framework is a compiler, not a library**: "A framework is to machine learning what a compiler is to traditional programming." The framework is the translation layer between mathematics (the model definition, the **$O$** term of the [[IronLawOfMLSystems|iron law]]) and silicon (kernel launches that minimize data movement $D_{\text{vol}}$, maximize utilization $\eta_{\text{hw}}$, and minimize overhead $L_{\text{lat}}$). Its choices are "insidious" because they operate below daily attention yet silently determine which optimizations are possible, which hardware is reachable, and which deployment paths exist; framework migration costs **three to six engineer-months** for production systems, making framework selection an *infrastructure commitment*.

The chapter's spine is **three problems every framework must solve**: the **execution problem** (when/how computation runs — [[EagerExecution|eager]] vs [[StaticGraph|static graph]] vs hybrid [[JITCompilation|JIT]]); the **differentiation problem** (computing gradients automatically via reverse-mode [[AutomaticDifferentiation|autodiff]]); and the **abstraction problem** (targeting CPUs/GPUs/[[GoogleTPU|TPUs]]/MCUs from one interface via [[Tensor|tensors]], [[IntermediateRepresentation|IRs]], and runtime systems). These map to iron-law terms: execution → $L_{\text{lat}}$, differentiation → $D_{\text{vol}}$, abstraction → $\eta_{\text{hw}}$. A "[[LadderOfAbstraction|Ladder of Abstraction]]" (BLAS 1979 → LAPACK 1992 → [[NumPy]] 2006 → [[Theano]] 2007 → [[TensorFlow]] 2015 → [[PyTorch]] 2016 → [[JAX]] 2018) frames each generation as automating what the rung below exposed.

The back half is a comparative platform analysis — **TensorFlow** (graph-first, prioritizes the *abstraction* problem for deployment breadth from TPU pods to TF Lite Micro), **PyTorch** (eager-first, prioritizes the *execution* problem for research velocity), **JAX** (functional, reframes the *differentiation* problem through composable `grad`/`vmap`/`jit`/`pmap` transformations) — plus the [[nnModule|nn.Module]] programming model, a [[MemoryWall|memory-wall]]-driven account of [[KernelFusion|kernel fusion]] / [[GradientCheckpointing|activation checkpointing]] / [[MixedPrecisionTraining|mixed precision]], two quantitative laws ([[CompilationContinuum|Compilation Continuum]] and [[DispatchOverhead|Dispatch Overhead]]), an end-to-end **anatomy of a training step**, and a long Fallacies & Pitfalls section. Thesis: frameworks are "the control room instruments" — the layer where the book's governing physics becomes executable code.

## Key Claims

- **A framework *is* a compiler.** A C compiler manages register allocation, instruction scheduling, and memory layout; an ML framework manages operator fusion, memory reuse, and device placement. Modern frameworks "literally include compilers" ([[XLA]], [[TorchCompile|torch.compile]]). Genuine frameworks solve all three of execution/differentiation/abstraction, distinguishing them from numerical libraries like NumPy that only address one.
- **The memory wall is the master constraint.** On an [[GPU|A100]] GPU (312 TFLOP/s FP16 vs 2.04 TB/s bandwidth → ~153 FLOP/byte ridge point), element-wise ops like ReLU achieve **<1% of peak compute** — not because hardware is slow but because they wait for data. Most individual op *types* (activations, normalizations, element-wise) are **memory-bound**; the large matmuls that dominate total compute time are **compute-bound** ([[RooflineModel|Roofline Model]]).
- **Kernel fusion is *the* optimization for memory-bound ops.** Fusing LayerNorm+Dropout+ReLU into one [[KernelFusion|kernel]] can yield **5×** speedup by eliminating intermediate HBM writes. [[FlashAttention]] fuses the whole attention computation, cutting HBM traffic **10–20×** for **2–4×** wall-clock speedup — transforming a memory-bound op into a compute-bound one. A framework can only fuse operations it can *see together*: this is why execution strategy gates everything.
- **The execution choice has a four-way cascade.** Debugging (visibility into intermediates), optimization (cross-op fusion), deployment (Python-independent execution), flexibility (data-dependent control flow). No single execution model wins all four. The [[ComputationalGraph|computational graph]] (a DAG, pioneered by Theano 2007) is the data structure that makes fusion and autodiff possible; the question is *when* it is built.
- **Eager pays a "dispatch tax."** Each op goes through Python dispatch (function lookup, arg parsing, type checking) at **~10 μs/op**; each GPU [[Kernel|kernel]] launch costs **5–20 μs** of CPU-side overhead. For a 1 μs ReLU the dispatch tax is **~91%** (overhead-bound); for a 100 μs matmul it drops to **~9%** (compute-bound). A ResNet-50 eager forward pass adds ~5–10 ms of dispatch+tape overhead vs compiled. The autograd tape itself raises memory **2–3×** vs forward-only.
- **Static graphs enable ahead-of-time optimization unreachable op-by-op:** kernel fusion, exact memory preallocation + buffer reuse, global layout transforms (NCHW↔NHWC), [[DeadCodeElimination|dead code elimination]] (eliminates 5–15% of nodes in large transformers), and [[ConstantFolding|constant folding]]. Together DCE+constant folding can cut total FLOPs **5–10%** "before the first batch even arrives." [[XLA]] achieves **1.5–2×** speedup on a transformer encoder block via aggressive fusion + hardware-specific codegen. The cost: no standard Python control flow (`tf.cond`/`tf.while_loop` required), and debugging points at symbolic node names.
- **JIT trades fidelity vs generality.** [[TorchScript]] *tracing* records one execution path with example inputs — silent **wrong outputs** for untaken data-dependent branches (a forensic bug). *Scripting* parses the AST, preserves both branches, but demands a restricted Python subset (no arbitrary imports/NumPy/f-strings, type annotations where inference fails). TorchScript IR uses the `aten`/`prim` namespaces and SSA form.
- **`torch.compile` is overhead amortization, not magic.** Its three stages: **[[TorchDynamo]]** (captures bytecode via CPython's PEP 523 frame-eval API, inserts *graph breaks* on unsupported code rather than failing silently), **[[FXGraph|FX Graph]]** (PyTorch's LLVM-IR analog, separates frontend from backend), **[[TorchInductor]]** (codegen → [[Triton]] for CUDA, C++/AVX for CPU). First call ~100 ms (small) to 5–10 min (GPT-3 scale); subsequent same-shape calls dispatch to cached code in microseconds. Typical **1.3–2×** on transformers, **2–5×** on matrix ops. Triton hits **80–95%** of hand-tuned CUDA; [[PTX]] forward-compat costs another 10–15%.
- **Graph breaks reset the amortization.** Data-dependent control flow, I/O (`print`), custom objects, and non-PyTorch calls force a return to eager dispatch (tensors marshalled GPU→CPU→back). Shape changes trigger recompilation (shape specialization — PyTorch keeps a compiled version per unique shape). Diagnose with `TORCH_LOGS="graph_breaks"`. Modes: `default` (5–30 s, dev/training), `reduce-overhead` (CUDA graphs, +20–40% inference throughput), `max-autotune` (minutes–hours, +10–30%, long runs).
- **The Compilation Continuum Principle** quantifies *when* to compile: $\text{Benefit} = \frac{N_{\text{prod}}(T_{\text{eager}}-T_{\text{compiled}})}{T_{\text{compile}}+N_{\text{dev}}\cdot T_{\text{compile}}}$; compile when >1. Research prototyping ($N_{\text{dev}}\gg N_{\text{prod}}$) → stay eager; training/inference → compile. ResNet-50 breakeven ≈ **134,000 images** at a 30 s compile cost — within the first ImageNet epoch (1.28M images). Continuum: Eager →(tracing) JIT →(AOT) Static Graph →(synthesis) Custom Hardware.
- **The Dispatch Overhead Law:** $\text{Overhead Ratio}=\frac{N_{\text{ops}}\cdot t_{\text{dispatch}}}{T_{\text{compute}}+T_{\text{memory}}}$. A small MLP (6 ops, 2.6 μs HW, 30 μs SW) is **~92% overhead-bound**; a GPT-3 layer (100 ms HW, 50 μs SW) is **<0.05%**. A 100-param toy model can see 10× from compilation; a 175-billion-param model only **1.3×** — small models benefit disproportionately.
- **Reverse-mode autodiff is the *only* viable training method.** A network has one scalar loss but $P$ parameters; [[ForwardModeAutodiff|forward mode]] needs $P$ passes (each parameter a separate pass, using dual numbers), [[ReverseModeAutodiff|reverse mode]] computes all $P$ gradients in **one** backward pass at a constant ~2–3× overhead regardless of $P$. Forward mode keeps niche uses (sensitivity analysis, feature importance — few inputs, many outputs). All major frameworks default to reverse mode.
- **Training memory dwarfs inference by ~100×, and reverse-mode autodiff is why.** Reverse mode must store every forward activation until the backward pass consumes it (a "memory wave" peaking at backprop start). ResNet-50 (25.6M params, ~102 MB FP32) trains at **10–15 GB** (8–12 GB activations + ~102 MB gradients + ~205 MB Adam state) — a **~100–150×** ratio vs ~102 MB inference. GPT-3 (175B params) needs **350 GB** in FP16 just for weights. Total memory: $M = M_{\text{weights}}+M_{\text{gradients}}+M_{\text{optimizer}}+M_{\text{activations}}$.
- **Two memory levers + the "administrative tax."** [[GradientCheckpointing|Gradient/activation checkpointing]] stores only $\sqrt{N_L}$ checkpoints and recomputes the rest — cuts activation memory **50–90%** for **+20–33%** compute (trades $D_{\text{vol}}$ for $O$). Operation fusion eliminates intermediate allocations for **2–3×** speedup (registers/L1 deliver 10–100× HBM bandwidth). The "administrative tax": a 2 GB (1B-param FP16) model carries ~19 GB of VRAM during training (2 GB weights + 2 GB gradients + 8 GB Adam + ~6.3 GB activations). Adam optimizer state alone ≈ 4× FP16 weight memory; a 7B model needs **~70 GB** (14 GB weights + 56 GB optimizer state).
- **PyTorch autograd internals:** every differentiable tensor stores a `grad_fn`; each `Function` links inputs via `next_functions`, forming a reverse chain (`PowBackward0` → `MulBackward0` → `AccumulateGrad`). Gradients **accumulate** by default (must call `zero_grad()`). `retain_graph=True` doubles memory for multi-loss/higher-order; `.detach()` cuts gradient flow safely (`.detach().clone()` before in-place mutation); legacy `.data` silently corrupts gradients; in-place ops (`x += 1`) trip PyTorch's tensor version counters. Hooks (`register_hook`) intercept gradients for clipping/inspection without touching the core traversal.
- **Tape-based vs transform-based autodiff.** PyTorch records a dynamic *tape* (flexible, debuggable, hard to optimize globally). JAX treats `grad(f)` as a function *transformation*: because functions are pure, `jit(grad(vmap(f)))` compiles to a single XLA kernel reaching **>90% TPU utilization** — but any impurity (print, mutation, unkeyed randomness) silently vanishes after the first trace.
- **Tensors carry shape + dtype + device + stride metadata.** A contiguous 1024×1024 FP32 tensor = exactly 4,194,304 bytes (~4.2 MB). Non-contiguous layouts (post-transpose) need `.contiguous()` copies. Choosing NCHW when hardware prefers NHWC can **halve** throughput (broken memory coalescing). Optimal layouts hit 80–90% of peak bandwidth (1.5–3.0 TB/s on A100/H100) vs 20–30% for suboptimal patterns. Tensor: from Latin *tendere* "to stretch," coined by Woldemar Voigt (1898).
- **The bandwidth hierarchy spans ~64×.** PCIe 4.0 ≈ 32 GB/s CPU↔GPU vs HBM2e ≈ 2.04 TB/s on-GPU. [[NVLink]] 3.0 (A100) ≈ 600 GB/s bidirectional (~10× PCIe). A single misplaced transfer can erase all GPU speedup; transferring a 1 GB tensor over PCIe ≈ equivalent compute time of trillions of FLOPs. Frameworks hide latency with [[CUDAStream|CUDA streams]] (overlap → max(compute,transfer) not sum), [[PinnedMemory|pinned memory]] for DMA (`non_blocking=True` only works on page-locked memory; 2–3× faster than pageable), and CUDA events for fine-grained sync (vs `torch.cuda.synchronize()` which serializes everything).
- **The DataLoader is a throughput contract.** Sustaining 1,000 images/s at 224² requires ~150 MB/s. Three mechanisms: parallel workers (`num_workers` ≈ CPU cores), prefetching (`prefetch_factor=2` → 8 batches in flight with 4 workers), pinned memory for DMA. Map-style datasets (`__getitem__`) allow shuffling; iterable-style (`__iter__`) stream in arrival order. Workers need per-worker RNG seeding (`worker_init_fn`) for reproducible augmentation.
- **Caching allocators maximize $\eta_{\text{hw}}$.** `cudaMalloc` is synchronous (10–100 μs, can stall the whole device). Frameworks request large blocks upfront and bin allocations into power-of-2 sizes, preventing **fragmentation** — the "Swiss cheese" pattern where OOM errors appear despite `nvidia-smi` showing free memory.
- **The nn.Module pattern is universal across frameworks.** Three principles: (1) **automatic parameter discovery** (metaclass intercepts `nn.Parameter` assignment; `.parameters()` does a recursive DFS so `optimizer.step()` updates millions of params in one vectorized call); (2) **mode-dependent behavior** (a single `.eval()` flag propagates `training=False` to all descendants, switching dropout/batchnorm; forgetting it = silently wrong predictions); (3) **hierarchical composition + serialization** (`state_dict()` flattens the tree to dotted keys like `blocks.0.conv1.weight` for sequential-byte-stream checkpointing). Same problem in Keras (`trainable_weights`), Flax (`params`/`state`), TF (`trainable_variables`). Parameters vs buffers: buffers (`register_buffer`) travel with the model but get no gradients (e.g. BatchNorm running stats).
- **The three frameworks make three deliberate trade-offs.** **TensorFlow** (Google) → abstraction: static "Define-and-Run" enables AOT compilation for deployment breadth (TPU pods, Android via TF Lite, browser via TF.js, SavedModel→TF Serving). **PyTorch** (FAIR) → execution: dynamic "Define-by-Run" treats DL as standard Python (loops, `pdb`); fragmented deployment via ONNX/TorchScript/torch.compile. **JAX** (Google Research) → differentiation: pure functions enable `pmap(jit(vmap(grad(f))))` as one expression; younger ecosystem (Flax/Haiku/Optax), steep learning curve, 75–95% memory efficiency via XLA fusion. "No framework optimizes all three problems simultaneously."
- **[[ONNX]] reduces but does not eliminate fragmentation.** The best training framework (PyTorch for velocity) rarely matches the best serving runtime ([[TensorRTLLM|TensorRT]] for latency, TF Lite for mobile). ONNX is a hub-and-spoke interchange format; export can lose framework-specific optimizations or custom operators. [[TinyML]] at the far edge: [[TensorFlowLite|TF Lite Micro]] runs a tiny C/C++ interpreter with a fixed memory arena on MCUs with 256 KB RAM (a standard PyTorch runtime is ~500 MB; the Python interpreter alone ~20 MB). TF variants: ~1,400 ops (full) → ~130 (Lite) → ~50 (Micro); binary ~MB → tens of KB → ~10 KB.
- **Deployment target reweights the three problems.** At the edge the differentiation problem often *disappears* (inference only), the execution problem becomes "fit inside 10 ms / 50 KB," and the abstraction problem intensifies (ARM vs x86, NPUs vs edge TPUs). Specialized inference engines (TensorRT/TVM) give 2–10× over untuned eager; mobile runtimes (TF Lite/Core ML/ExecuTorch) shrink footprint from hundreds of MB to MB-scale.

## Key Quotes

> "A framework is to machine learning what a compiler is to traditional programming. … This analogy is more than metaphor: modern frameworks literally include compilers." — Ch 7, on the central thesis

> "In the context of the iron law, a framework is a compiler for the silicon contract." — the framework's role: minimize $D_{\text{vol}}$ (fusion), maximize $\eta_{\text{hw}}$ (Tensor Cores), minimize $L_{\text{lat}}$ (async dispatch)

> "Framework choices are more insidious because they operate below the level of daily attention, silently determining which optimizations are possible, which hardware is reachable, and which deployment paths exist." — on framework selection as an irreversible infrastructure commitment

> "Compilation is not magic; it is *overhead amortization*. For small, element-wise operations such as LayerNorm, GELU, and Add, overhead often exceeds compute time by 10–100×. Fusing them is the only way to use the hardware effectively." — the "physics of software overhead" callout

> "Framework abstractions are valuable because they carry contracts: shape, dtype, device placement, and sometimes units. If those contracts are implicit, two pieces of correct code can still compose into a wrong system." — systems lesson of the Mars Climate Orbiter war story (a 4.45× pound-force vs newton unit mismatch destroyed the ~$327M mission)

> "The restriction is the feature; purity is what makes transformation composition possible." — on JAX's pure-function requirement

> "A control room without a source of energy … is just a room with glowing lights." — closing connection to Ch 8 (Model Training)

## Contradictions

- **No direct contradictions with prior mlsysbook chapters** — Ch 7 is a deepening. The static-vs-dynamic graph distinction and the GEMM/im2col lowering reuse [[mlsysbook-ch06-network-architectures|Ch 6]] vocabulary; the iron-law decomposition is inherited from [[mlsysbook-ch01-introduction|Ch 1]] / [[IronLawOfMLSystems]]. The Lighthouse Models (ResNet/GPT/DLRM/MobileNet/KWS) recur identically.
- **Eager-vs-compiled performance is regime-dependent, not absolute.** This chapter repeatedly stresses that torch.compile/TensorRT speedups (1.2–3× / 2–10×) and JAX's >90% TPU utilization "vary significantly by model architecture, batch size, and operation mix" and "cannot substitute for profiling specific workloads." The Fallacies section explicitly debunks "all frameworks provide equivalent performance" and "increasing batch size is a free throughput optimization" (larger batches can *reduce* throughput 20–30% by triggering recomputation). Reconcile any wiki page asserting a fixed framework speedup by treating it as workload-conditional.
- **Compilation overhead is *not* always a one-time cost.** Contrary to the common framing (and the [[CompilationContinuum|continuum]]'s "compile once" intuition for production), during rapid prototyping with frequent recompiles a compiled workflow can be **~44× slower** than eager (10 code changes × 30 s recompile ≫ the throughput gain on a 10k-image experiment). The fix is the Compilation Continuum decision rule, not a blanket "compilation helps."
- **Quantization/precision relationship to the [[Quantization]] page:** Ch 7 treats INT8/FP16 mostly as *tensor dtype levers* (4× memory cut, 2–4× throughput on INT8-capable hardware) and as a deployment-runtime feature (TF Lite native quantization tooling), rather than as a standalone compression algorithm — complementary to, not in tension with, the DMLS treatments of quantization as model compression.
