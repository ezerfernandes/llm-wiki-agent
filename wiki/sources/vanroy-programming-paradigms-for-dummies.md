## Summary

**[[PeterVanRoy|Peter Van Roy]] ([[UCL|Université catholique de Louvain]], written during sabbatical at [[IRCAM]], 2009; chapter in *New Computational Paradigms for Computer Music*, G. Assayag & A. Gerzso eds., IRCAM / Delatour France).** A 39-page paradigm-taxonomy chapter aimed at a programmer audience but rigorous as a survey: **27 useful programming paradigms** organized by two key properties — **[[ObservableNondeterminism|observable nondeterminism]]** (yes/no) and **[[NamedState|named state]]** (none / unnamed / named, sequential / concurrent / nondeterministic). Names the **four most important [[ProgrammingConcept|programming concepts]]** — records, [[Closure|lexically scoped closures]], independence ([[Concurrency|concurrency]]), and [[NamedState|named state]] — and the **four kinds of [[DataAbstraction|data abstraction]]** ([[AbstractDataType|ADT]] / [[OPMObject|object]] / declarative object / stateful ADT). Argues for two design strategies: **[[DualParadigmLanguage|dual-paradigm languages]]** (one paradigm in the small + one for the large) and **[[DefinitiveLanguage|definitive languages]]** (four-layer architecture: functional core → declarative concurrency → message passing → named state, exemplified by Erlang, E, Distributed Oz, Didactic Oz). Presents **four little-known [[Concurrency|concurrent]] paradigms with no race conditions** — [[DeclarativeConcurrency|declarative concurrency]] (eager + lazy [[DataflowVariable|dataflow]]), [[FunctionalReactiveProgramming|functional reactive programming]], [[DiscreteSynchronousProgramming|discrete synchronous programming]], and [[ConcurrentConstraintProgramming|constraint programming]]. Closes with the [[SelfSufficientSystem|self-sufficient-systems]] architecture (interacting [[FeedbackLoop|feedback loops]] via stigmergy + management) as the large-scale alternative to monolithic software. Direct intellectual descendant of [[vol1000-oz-programming-model|Smolka's 1995 OPM paper]] (Van Roy ran the **PERDIO** distributed-Oz project at [[DFKI]] with Smolka in 1995); the chapter is the *programmer-facing* sibling to the formal-model exposition, positioned alongside the textbook *Concepts, Techniques, and Models of Computer Programming* ([[CTM|CTM]], Van Roy & Haridi, MIT Press 2004).

## Key Claims

- **Paradigms decompose into concepts.** *"Each paradigm is defined by a set of programming concepts, organized into a simple core language called the paradigm's **[[KernelLanguage|kernel language]]**."* With $n$ concepts one can construct up to $2^n$ paradigms; the chapter names 27 practically useful ones. **Often two paradigms that seem quite different (e.g., functional vs object-oriented) differ by just one concept.**
- **Two organizing axes for the taxonomy** (Figure 2 / Figure 3): **observable nondeterminism** (yes/no) and **expressiveness of state** (less / more, across three axes: unnamed-vs-named, deterministic-vs-nondeterministic, sequential-vs-concurrent). The eight (3-way) combinations give a lattice from functional programming (unnamed/det/seq) at the top through declarative concurrency (unnamed/det/conc) to message-passing / shared-state concurrency (named/nondet/conc) at the bottom.
- **The [[CreativeExtensionPrinciple|creative extension principle]]** (Felleisen 1990, rediscovered in CTM): *"In a given paradigm, it can happen that programs become complicated for technical reasons that have no direct relationship to the specific problem that is being solved. This is a sign that there is a new concept waiting to be discovered."* Three canonical examples: independent activities → **[[Concurrency|concurrency]]**; updatable memory → **[[NamedState|named state]]**; pervasive error-handling → **exceptions** (Figure 5).
- **Four most important programming concepts** (Section 4): **records** (group of references to data items with indexed access; foundation of symbolic programming), **lexically scoped [[Closure|closures]]** (*"the most expressive concept ever invented in programming"* — basis for first-class procedures, functions, objects, classes, components, AOP weaving, separation of concerns), **independence / concurrency** (constructing programs as independent parts), **[[NamedState|named state]]** (entity with unique identity whose behavior changes during execution; required for **modularity**).
- **Concurrency ≠ parallelism.** *"Concurrency is a language concept and parallelism is a hardware concept. Two parts are parallel if they execute simultaneously on multiple processors. Concurrency and parallelism are orthogonal."* Three levels of concurrency in the computing world: distributed system / OS process / thread.
- **Four ways to organize data abstraction** (Figure 14) along two axes — **state** (stateful / stateless) × **bundling** (object / ADT): **pure ADT** (e.g., Java integers — unbundled, stateless), **pure object** (most popular in modern languages — bundled, stateful), **stateful ADT** (less common), **declarative object** (less common).
- **Object-oriented programming = data abstraction + polymorphism + inheritance.** Two failure modes: **violating the [[SubstitutionPrinciple|substitution principle]]** (subclass behaves differently from superclass, breaking polymorphism) and **using subclasses to mask bugs** (deep, complicated, slow, buggy hierarchies). Cautionary tale: an unnamed multinational lost a several-billion-dollar OO project to these two errors.
- **Four [[ConcurrencyParadigm|concurrent paradigms]] with no observable nondeterminism** (Table 2): **[[DeclarativeConcurrency|declarative concurrency]]** ([[Oz]], [[Alice]]), **[[ConcurrentConstraintProgramming|constraint programming]]** ([[Gecode]], [[Numerica]]), **[[FunctionalReactiveProgramming|functional reactive programming]]** ([[FrTime]], [[Yampa]]), **[[DiscreteSynchronousProgramming|discrete synchronous programming]]** ([[Esterel]], [[Lustre]], [[Signal]]). *"These paradigms have no race conditions and can be used in cases where no other paradigm works."* By contrast, [[MessagePassingConcurrency|message-passing concurrency]] ([[Erlang]], [[E_Language|E]]) has races possible / nondeterministic inputs.
- **Declarative concurrency = threads + [[DataflowVariable|dataflow variables]].** A dataflow variable is **single-assignment** with three primitive operations: `NewVar` (create) / `Bind` (bind to value or another dataflow variable) / `Wait` (block until bound). *"All operations of the language [are extended] to wait until their arguments are available and to bind their result."* Result: **declarative dataflow programming** — confluent like functional programming but concurrent.
- **Lazy declarative concurrency adds `WaitNeeded`.** *"The current thread waits until a thread does `Wait X`."* By-need synchronization stays confluent and gives the **most general declarative paradigm based on functional programming known so far.**
- **Layered structure of a [[DefinitiveLanguage|definitive language]]** (Table 1): four projects independently converged on the same four-layer architecture — **functional core** → **deterministic [[DeclarativeConcurrency|declarative concurrency]]** → **asynchronous [[MessagePassingConcurrency|message passing]]** → **global named [[SharedStateConcurrency|state]]**. Projects: [[Erlang]] (Armstrong, Ericsson, 1986+), [[E_Language|E]] (Miller, Barnes et al.), **[[DistributedOz|Distributed Oz]]** (Smolka, Schulte, Van Roy — PERDIO at DFKI 1995, Mozart released 1999), **[[CTM|Didactic Oz]]** (Van Roy & Haridi 2004 textbook + UCL FSAB1402 course). The convergence is "Lightning Striking Four Times in the Same Place" (Van Roy 2006, FLOPS).
- **[[SelfSufficientSystem|Self-sufficient systems]] via interacting [[FeedbackLoop|feedback loops]].** Architecture for software that maintains, adapts, and corrects itself: components as first-class entities (specified by closures), concurrent message-passing agents, named state for system reconfiguration. Two interaction modes between loops: **stigmergy** (two loops share one subsystem) and **management** (one loop controls another loop directly). Real-world example: the human respiratory system as a 4-loop structure (Figure 8).
- **[[ConcurrentConstraintProgramming|Constraint programming]] is the most declarative paradigm.** *"Telling the computer what is needed instead of how to calculate it."* CSP: variables ranging over well-defined domains + constraints (logical relations) + propagate-distribute solving algorithm. **The [[Propagator|propagator]] is a concurrent agent that implements a constraint** — triggered when argument domains change; runs until no more reduction is possible (a fixpoint). Three independent factors in the propagate-distribute algorithm (Figure 17): **propagation over constraint domains** × **distribution strategy** × **search strategy**.
- **Multi-core programming should default to [[DeclarativeConcurrency|declarative concurrency]] or [[MessagePassingConcurrency|message passing]].** *"Declarative concurrency is a good paradigm for parallel programming ... Any correct program can be parallelized simply by executing its parts concurrently on different cores. Paradigms that have named state (variable cells) make this harder because each variable cell imposes an order. ... A common programming style is to have concurrent agents connected by streams. This kind of program can be parallelized simply by partitioning the agents over the cores, which gives a pipelined execution."*

## Key Quotes

> "More is not better (or worse) than less, just different." — the paradigm paradox (epigraph)

> "Solving a programming problem requires choosing the right concepts. All but the smallest toy problems require different sets of concepts for different parts. This is why programming languages should support many paradigms."

> "Popular mainstream languages such as Java or C++ support just one or two separate paradigms. This is unfortunate, since different programming problems need different programming concepts to solve them cleanly, and those one or two paradigms often do not contain the right concepts."

> "Concurrency is a language concept and parallelism is a hardware concept. Two parts are parallel if they execute simultaneously on multiple processors. Concurrency and parallelism are orthogonal."

> "The lexically scoped closure is an enormously powerful concept that is at the heart of programming. ... Almost all programming languages (except for a few venerable ancestors such as Pascal and C) use this kind of closure: functions are closures; procedures are closures; objects are closures; classes are closures; software components are closures."

> "Named state is important for a system's modularity. We say that a system (function, procedure, component, etc.) is modular if updates can be done to part of the system without changing the rest of the system." — and the worked example showing that **without named state, adding a call counter to module `M` forces every user of `M` to rewrite their code** (the bureaucratic-overhead failure mode).

> "Decades of research show that parallel programming cannot be completely hidden from the programmer: it is not possible in general to automatically transform an arbitrary program into a parallel program. There is no magic bullet. The best that we can do is to make parallel programming as easy as possible."

> "A true multiparadigm language is *factored*: it is possible to program in one paradigm without interference from the other paradigms."

## Contradictions

- **No direct contradictions** with prior wiki content — the chapter is a *programmer-facing* survey of programming paradigms, the wiki's first such anchor. **Confirms and extends** the [[vol1000-oz-programming-model|1995 Smolka OPM]] framing: where Smolka exposed the formal model and the [[Oz]] language as its surface, Van Roy places Oz in a 27-paradigm taxonomy and contextualizes it as one of four converging *definitive language* projects.
- **Live tension** with the wiki's existing concurrency vocabulary continues. The [[DiveIntoSystems]] / [[TheEmbeddedRustBook]] corpora ground concurrent programming in [[Pthreads]] / [[Mutex]] / [[Semaphore]] / [[ConditionVariable]] / [[MPI]] (named state + observable nondeterminism). Van Roy's taxonomy classifies these as **the most expressive but hardest-to-reason-about** paradigm region. He explicitly recommends [[DeclarativeConcurrency|declarative concurrency]] or [[MessagePassingConcurrency|message-passing]] as the multi-core default — a position the [[DiveIntoSystems]] Ch 14 (Pthreads) / Ch 15 (MPI) coverage does not engage with. **Not a contradiction**, a complementary recommendation worth flagging for future synthesis.
- **Live tension** with the wiki's OOP coverage (Java cross-walks in [[DiveIntoSystems]] Appendix 1; [[CPlusPlus]] / class-based Python in various ML corpora). Van Roy's recommendation — *"use inheritance as little as possible. When defining a class, we recommend to define it as nonextensible if at all possible. In Java this is called a final class. Instead of inheritance, we recommend to use composition instead"* — is more skeptical of inheritance than typical Java / C++ pedagogy. **Aligned with**, not contradictory to, modern "composition over inheritance" guidance.
