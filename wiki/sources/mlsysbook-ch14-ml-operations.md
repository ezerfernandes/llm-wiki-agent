# Machine Learning Systems (mlsysbook Vol 1) — Ch 14: ML Operations

## Summary

Chapter 14 of [[VijayJanapaReddi|Vijay Janapa Reddi]]'s *Introduction to Machine Learning Systems* ([[Harvard]], mlsysbook.ai, 2026) is the operational core of the **Deploy** part (Ch 13–16). Where Ch 13 ([[mlsysbook-ch13-model-serving]]) showed how to answer requests in milliseconds, Ch 14 addresses the harder problem: *keeping models correct once they are in production*. Its thesis is captured in the chapter's opening question — "Why can an ML system be perfectly available and perfectly wrong at the same time?" Traditional software fails loudly (crashes, red dashboards, paged engineers); ML systems fail silently — a model under [[DataDrift|data drift]] keeps serving confident predictions while accuracy decays week by week, with every health check (latency, throughput, uptime) staying green ([[SilentDegradation]]). [[MLOps]] is defined as "the engineering discipline that closes the feedback loop between model behavior and data reality by automating retraining, validation, and deployment in response to measurable production drift." It extends [[DevOps]] but breaks DevOps's core assumption of determinism: ML correctness depends on training-data distributions, learned parameters, and a world that shifts continuously.

The chapter organizes single-model operations (the "ML node": data pipelines + feature computation + training + serving + monitoring for one application) around **five foundational principles** — Reproducibility, Separation of Concerns, Consistency Imperative, Observable Degradation, Cost-Aware Automation — and **three critical interfaces** (Data-Model, Model-Infrastructure, Production-Monitoring). It then walks the lifecycle: ML **technical debt** patterns ([[BoundaryErosion]], [[CorrectionCascade|correction cascades]], undeclared consumers, data-dependency debt, [[FeedbackLoop|feedback loops]], pipeline/configuration debt, glue code — with YouTube/Zillow/Tesla/Facebook case studies); **development infrastructure** ([[FeatureStore|feature stores]], [[DataVersioning|data/model versioning]], [[ModelRegistry|model registries]], ML-adapted [[CICD]] pipelines, [[ModelValidation|validation]]); **production operations** (deployment strategies, [[ModelMonitoring|monitoring]] & [[Observability|observability]], [[DriftDetection|drift detection]] via [[PopulationStabilityIndex|PSI]]/[[KullbackLeiblerDivergence|KL divergence]], [[IncidentResponse|incident response]], [[ModelDebugging|debugging]], [[OnCallRotation|on-call]], governance); a **maturity framework** (Ad Hoc → Repeatable → Scalable, the [[MLTestScore|ML Test Score]], [[OperationalMaturity]], investment economics); and two **case studies** — the [[OuraRing|Oura Ring]] (edge wearable) and [[ClinAIOps]] (healthcare). Both demonstrate that domain constraints reshape *how* the five principles are implemented without changing *which* principles matter.

A defining feature is its quantitative "napkin math": worked closed-form models throughout. The **retraining economics** uses an exponential accuracy-decay / "half-life of a model" framing, yielding the square-root law $T^* \approx \sqrt{2C / (Q V A_0 \gamma)}$ for the optimal retraining interval ([[RetrainingEconomics]]). Skew cost, silent-failure cost, drift-detection delay, observability sampling cost, monitoring budget, and ROI are all derived with concrete numbers. The chapter explicitly contrasts itself with [[ChipHuyen|Chip Huyen]]'s [[dmls-ch07-model-deployment|DMLS]] deployment/monitoring/continual-learning chapters: same vocabulary (training-serving skew, batch vs online, drift), but mlsysbook's framing is more systems-theoretic (degradation equation, verification invariant, iron law of ML systems, D·A·M taxonomy) and quantitative.

## Key Claims

- **The operational mismatch is the whole point.** Traditional monitoring tracks deterministic system health (uptime, latency, success rate); ML monitoring must track *statistical* health (accuracy over time, input-distribution shift, per-segment quality). "A 94 percent accurate model degrading to 81 percent throws no exceptions, triggers no alerts, and maintains perfect uptime while actively harming users." The motivating ridesharing example: 94% accuracy + 15 ms P99 at deploy → 88% accuracy by week 4 with all infra metrics green; root cause a competitor promotion that shifted behavior; retraining was needed six weeks earlier.
- **MLOps definition (quantitative significance):** recommendation models without drift monitoring can lose ~10–20 percentage points of accuracy within six months; a KL-style divergence $\mathcal{D}(P_t\|P_0) > 0.1$ is a common runbook threshold; automated retraining compresses MTTR from days to hours (sub-hour for well-instrumented low-risk updates). **Common pitfall:** retraining on shifted data without diagnosing *which* distribution moved ($p(x)$ vs $p(y\mid x)$) can entrench the shift — [[DataDrift|data drift]] needs fresh sampling, [[ConceptDrift|concept drift]] needs relabeling.
- **Five foundational principles** (the evaluation framework for all tooling): **Reproducibility** — `Model Output = f(Code_v, Data_v, Config_v, Environment_v)`; versioning only code is a critical failure mode. **Separation of Concerns** — Data/Training/Serving/Monitoring layers evolve independently, reducing blast radius. **Consistency Imperative** — training and serving must process data identically; `Skew Cost = Base Error Rate × Query Volume × Error Impact` (a worked example: 1% skew error × 1M queries/day × $0.10 = **$365,000/year**). **Observable Degradation** — make silent failures visible. **Cost-Aware Automation** — `Retrain if ΔAccuracy × Value > Training Cost + Deployment Risk`.
- **Three critical interfaces:** Data-Model (feature consistency → feature stores), Model-Infrastructure (environment parity → registries + containers), Production-Monitoring (statistical telemetry feedback → retraining cadence).
- **The 5%/95% rule.** Google's analysis found model code is ~5% of a production ML codebase; the other ~95% is data pipelines, configuration, serving infra, and monitoring (Sculley et al. 2015, "Hidden Technical Debt in ML Systems"). [[TechnicalDebt|Technical debt]] in ML "compounds as silent accuracy degradation rather than slower development velocity."
- **Six+ technical-debt patterns** with the **CACHE principle** (*Change Anything Changes Everything*): [[BoundaryErosion|boundary erosion]] (entanglement, implicit data coupling), [[CorrectionCascade|correction cascades]] (a fix triggers more fixes through statistical dependencies), undeclared consumers, data-dependency debt, [[FeedbackLoop|feedback loops]], pipeline jungles, configuration debt, glue code, dead experimental codepaths, abstraction debt. The **ML Test Score** rubric (Breck et al. 2017) = 28 tests across data/model/infrastructure/monitoring (7 each).
- **Real-world debt failures:** **Zillow** iBuying — Zestimate correction cascade; losses > $500M in Q3 2021, ~2,000 layoffs (25% of workforce), $304M inventory write-down; iBuying shut down 2021. **YouTube** — recommendation feedback-loop debt (content amplification), fixed via cohort evaluation + delayed labeling. **Tesla** Autopilot — undeclared-consumer debt across subsystems via OTA updates. **Facebook** News Feed — configuration debt / opaque settings.
- **Feature stores** (pioneered by Uber's [[MichelangeloPlatform|Michelangelo]], 2017) compute features *once* through a single code path for both training and serving, eliminating 5–15% accuracy degradation from [[TrainingServingSkew|training-serving skew]]. Worked skew case: a recommender drops 8% one month post-deploy with no code change — `user_session_length` mean is 45 min in serving vs 12 min in training (training excluded shorter mobile sessions). Michelangelo: features in Spark/Hive (train) + Cassandra (serve), DSL-generated, point-in-time correctness, 5,000+ features across 100+ teams. Large feature stores (Uber/Airbnb) serve millions of features/s at P99 < 10 ms.
- **Retraining is an engineering optimization, not a guess.** Model accuracy decays like radioactive material: $A(t) = A_0 e^{-\gamma t}$, with a measurable **half-life**. The square-root law $T^* \approx \sqrt{2C/(QVA_0\gamma)}$ gives the optimal interval. Worked fraud example ($Q$=1M txns/day, $V$=$0.50/query per unit accuracy, $A_0$=0.95, $\gamma$=2%/day, $C$=$5,000) → **$T^* \approx$ 1 day**. Sensitivity: 4× cost → 2× longer; 4× volume or 4× decay → 2× shorter. Three retraining strategies: scheduled (daily ads / weekly fraud / monthly demand / quarterly medical imaging), triggered (PSI/accuracy/prediction-shift thresholds), continuous (online learning).
- **Deployment is a systems problem, not a file transfer.** Strategies: [[ShadowDeployment|shadow]] (10–20% compute overhead, eliminates catastrophic tail risk), [[CanaryDeployment|canary]] (1–5% traffic; detecting a 2% accuracy diff at 95% confidence needs thousands of inferences), [[BlueGreenDeployment|blue-green]]. **Knight Capital (2012):** deploying new code to 7 of 8 servers; the 8th ran old code where reused flag `SMARS` triggered a dormant "Power Peg" test routine → millions of erroneous orders in 45 minutes, > $460M loss, emergency financing. Lesson: configuration drift + partial rollouts are catastrophic in automated systems; ML inherits the same risk surface (wrong registry version, drifting schema, half-canaried fleet).
- **Tiered [[RollbackStrategy|rollback]]:** immediate (< 1 min, hot standby, stateless), rapid (< 15 min, registry redeploy, clear caches), delayed (< 4 hr, state migration/replay). Untested rollbacks fail at 3 AM; monthly "fire drills" and automated thresholds (e.g., "P99 > 2× baseline for 5 min → rollback") are required. Stateful models and feedback-contaminated training data complicate rollback.
- **A/B testing** vs canary: A/B measures *business* lift with statistical confidence. Sample size $n = 2(z_{\alpha/2}+z_\beta)^2\sigma^2/\delta^2$; a 2% relative lift on a 5% baseline at 95%/80% needs ~**745K users/variant** (25K/variant would only detect ~0.5pp). ML-specific challenges: delayed feedback, novelty effects (burn-in), interference (independence violated in ranking), segment heterogeneity. Use guardrail metrics, preregistration, CUPED variance reduction, sequential testing.
- **Latency budget:** model inference is often a *minority* of end-to-end latency. Worked 100 ms P99: network 15 + feature fetch 25 + parse 5 + **inference 45** + post-proc 5 + serialization 5; inference is 45% of total, so a 2× model speedup yields only ~1.3× end-to-end. "Measure everything, optimize the bottleneck" (Patterson); use the [[DAMTaxonomy|D·A·M taxonomy]].
- **Format optimization** ([[ONNX]] interchange, [[TensorRT]] NVIDIA-only, [[OpenVINO]] Intel, [[CoreML]] Apple, [[TensorFlowLite|TFLite]] mobile/Edge TPU) routinely gives 2–10× latency improvement; validate numerical equivalence (< 0.1% divergence for classification), edge cases, memory at peak, warm-up (kernel compilation cold starts), and pin runtime versions.
- **Edge AI** changes every cloud assumption (smoke detector: ceiling-mounted, intermittent WiFi, coin-cell, 256 KB). Three-tier hierarchy: sensor (1–100 mW), gateway (1–10 W), cloud (GPU). [[TinyML]] (< 1 MB, mW, TFLite Micro/CMSIS-NN, no dynamic allocation, 90%+ sparsity), Mobile AI (5–50 ms, < 500 mW, NPUs). [[OverTheAirUpdates|OTA updates]] with cryptographic signatures + differential compression (80–95% payload reduction); [[GracefulDegradation|graceful degradation]] must be designed in, not bolted on. [[FederatedLearning|Federated learning]] lets edge devices improve models without sending raw data.
- **Monitoring is layered** (infra / data / model). **[[Observability]]** (from control theory) answers *why* it's broken, not just *whether*. **Drift detection delay** is physically bounded by traffic: detecting a 5pp accuracy drop with 95% confidence needs ~1,000 labeled samples → ~17 min at 1 QPS but ~10 days at 100 requests/day, so low-traffic high-stakes models stay in silent failure for days/weeks and need proactive model audits. [[ConceptDrift|Concept drift]] ($p(y\mid x)$) is invisible until ground truth arrives (COVID-19 is the canonical abrupt example); [[DataDrift|data drift]]/[[CovariateShift|covariate shift]] ($p(x)$) is detectable immediately without labels.
- **PSI math:** $\text{PSI} = \sum_i (\text{actual}_i - \text{expected}_i)\ln(\text{actual}_i/\text{expected}_i)$; thresholds from credit-risk scoring — < 0.1 no shift, 0.1–0.2 investigate, > 0.2 review. Worked age-distribution example: 6 bins, several shift 3pp, total PSI = 0.029 (stable) — aggregate PSI prevents false alarms that per-bin inspection would raise. KS > 0.1 for continuous, JS > 0.1 for probability distributions.
- **Observability economics:** cost ≈ Frequency × Metrics × (Ingest + Storage). At 1M req/s, 1-second sampling = ~1 GB/s vs 60-second = ~16.7 MB/s (60× swing). Use dynamic sampling: 1% of successes, 100% of errors; tiered retention (15 s / 24 h → 1 min / 7 d → 5 min / 30 d) cuts storage 80–90%. Single-model monitoring budget ≈ **$261/month** (3 variants × 50 metrics, 15 s sampling, 30 d retention). Monitoring ROI = Incidents Prevented × Avg Cost / Annual Cost; 5 × $50K / $50K = **5×**.
- **Netflix monitoring at scale:** hundreds of models, billions of predictions/day, 200M+ subscribers. Three layers: Statistical Process Control (control charts vs fixed thresholds), cohort-based monitoring (tenure/device/region), counterfactual evaluation (holdout lift). "Interleaving" experiments run old + new models on the same users to detect subtle quality diffs.
- **Incident response & on-call** are the human side of the Production-Monitoring interface. Severity P0 (complete failure, 15 min) → P3 (minor anomaly, 24 hr). Debugging decision tree starts with **data** (60–80% of production ML issues originate in data), then training-serving skew, subpopulation slices, temporal patterns, then the model last. **Slice analysis** worked example: 91% overall accuracy masks 62% accuracy for tablet users (5% of traffic). [[SHAP]] feature attribution + counterfactuals diagnose root causes; "zombie features" linger in feature stores/contracts after code owners forget them. Tiered escalation (Tier 1 ML eng → Tier 2 senior/DS → Tier 3 platform lead) + a parallel data on-call. Combat alert fatigue: consolidate, adaptive thresholds, retire alerts acted on < 10% of the time; limit consecutive on-call to 3–4 days.
- **Reliability patterns** adapted for ML's third failure state (responding *incorrectly* with no error signal): [[CircuitBreaker|circuit breakers]] (accuracy thresholds ≠ availability thresholds), bulkhead pattern (10–20% capacity for experiments), Byzantine fault tolerance (ensemble majority voting needs ≥ 3× overhead; strict $3f+1$ = 4× for $f$=1) — "semantic failures" pass health checks.
- **Maturity:** Ad Hoc → Repeatable → Scalable; the leap is architectural (isolated scripts → cohesive system), ~3–6 months engineering per transition. The "uptime iceberg": visible uptime sits atop hidden threats (data drift, concept drift, broken pipelines, schema changes, bias, underperforming segments). Single-model MLOps investment: CI/CD $10–30K one-time, monitoring $2–10K/yr, feature store $5–20K/yr, registry $0–5K/yr, 1–2 FTE-months. Single-model ROI worked example = **4.5×**. Invest proportional to model criticality; start with monitoring + CI/CD (highest ROI).
- **Oura Ring case study:** 106 participants / 3 continents, 440 nights, 3,400+ hours synchronized with PSG. Accelerometer-only model = 57% four-stage accuracy; enhanced (HRV + temperature → autonomic/circadian features) = 79%; human PSG inter-scorer agreement is only 82–83% (a noisy ceiling), so the 22pp gain closes ~85–88% of the baseline-to-human gap. DS-CNN "Tiny Constraint" archetype: monitor duty cycle + false-positive rate (no ground truth), quarterly OTA retraining, quantization + pruning, tiered fallback.
- **ClinAIOps case study** (Chen et al. 2023): standard MLOps is insufficient for high-stakes clinical domains. Three interlocking feedback loops — patient treatment (bounded self-management within clinician thresholds), clinician oversight (human accept/reject/modify), developer feedback — reframe feedback loops *as beneficial architecture* rather than debt. Hypertension example: PPG/ECG/PTT-derived BP estimates, tiered titration recommendations with human-in-the-loop gates. ClinAIOps differs from MLOps across 8 dimensions (focus, stakeholders, objective, validation, etc.): it optimizes *patient outcomes* and *aligns human incentives*, not just model metrics.

## Contradictions

- **No hard contradictions with [[dmls-ch07-model-deployment]].** mlsysbook Ch 14 and DMLS are complementary: DMLS Ch 7 covers the deployment mechanics (batch vs online, model compression, edge/IR/compiler), DMLS Ch 8/9/10 cover distribution shift / continual learning / monitoring; mlsysbook Ch 14 consolidates monitoring + retraining + governance + maturity into one operations chapter with heavier quantitative framing (degradation equation, square-root retraining law, drift-detection-delay physics). Where DMLS frames batch prediction as a legacy MapReduce artifact, mlsysbook is agnostic and treats serving paradigm choice as latency-budget-driven.
- **"Online prediction is on track to become the default" (DMLS) vs mlsysbook's neutral framing.** mlsysbook Ch 14 does not push the "online-by-default" thesis; it treats batch vs online as a per-archetype monitoring/cost decision (e.g., batch inference targets > 85% GPU utilization tolerating queuing; online inference targets 50–70% with headroom).
- **Drift-correction caution (internal nuance, not a contradiction).** Both books warn against naive retraining, but mlsysbook is sharper: retraining on shifted data without diagnosing $p(x)$ vs $p(y\mid x)$ "can entrench the shift rather than correct it" — and covariate-shift importance weighting (Shimodaira 2000) silently fails when deployment inputs fall outside training support, requiring full retraining rather than reweighting.
- **Illustrative-vs-exact numbers.** The chapter repeatedly flags its magnitudes (10–20% decay, 5–15% skew cost, $365K skew, $261/month monitoring, 4.5× ROI, 57%→79% Oura) as illustrative/calibration-dependent rather than universal constants; treat them as order-of-magnitude anchors.
