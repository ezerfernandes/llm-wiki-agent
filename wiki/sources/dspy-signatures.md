# DSPy Learn — Signatures

Page 4 of 13 in the [[DSPy]] *Learn* documentation ([dspy.ai/learn/programming/signatures/](https://dspy.ai/learn/programming/signatures/)). This is the page that **defines** the first of the four orthogonal artifacts [[DSPyProgrammingModel|the Programming Model]] factors out of a conventional prompt — the **Signature** — and gives it a concrete API surface. Where [[dspy-programming-overview|the Programming Overview]] *names* the signature concern in the abstract (*"asks the LM to take some inputs and produce some outputs of certain types"*) and [[dspy-language-models|the Language Models page]] *shows* `dspy.ChainOfThought('question -> answer')` in passing, this page is the canonical source for **what a Signature actually is** in code: a **declarative specification of input/output behavior** that comes in two forms — **inline** (a short string like `"question -> answer"` or `"context: list[str], question: str -> answer: str"`) and **class-based** (a `dspy.Signature` subclass with a docstring, `dspy.InputField()` and `dspy.OutputField()` typed attributes, and optional `desc=` hints). Mints the [[DSPySignatures]] concept page — closing the long-standing forward reference that has been carried by [[DSPy]] / [[DSPyProgrammingModel]] / [[DSPyLM]] / [[dspy-learn-index]] / [[dspy-programming-overview]] / [[dspy-language-models]] since the corpus opened on 2026-05-17.

## Summary

The Signatures page introduces DSPy's central **input/output typing surface** and is emphatic that it is **not** a documentation convention: a Signature is a **load-bearing program construct** that drives prompt construction, output parsing, and downstream optimization. Two equivalent surface forms are documented — **inline** (a Python string `"<inputs> -> <outputs>"` with optional `: type` annotations on each field, optionally paired with an `instructions=` kwarg for top-level guidance) and **class-based** (a `dspy.Signature` subclass whose docstring is the task description, whose fields are `dspy.InputField()` / `dspy.OutputField()` typed attributes, and whose `desc=` kwargs supply per-field hints). The page works through five concrete examples — **Sentiment Classification**, **Summarization** (where `dspy.ChainOfThought` is shown to silently expand the signature with an extra `reasoning` field), **Emotion Classification** with a `Literal[...]` constraint, the **CheckCitationFaithfulness** metric with mixed input/output `desc` hints and a `dict[str, list[str]]` output, and a **multi-modal `DogPictureSignature`** consuming a `dspy.Image`. A separate *Type Resolution* section enumerates the type system — basic Python (`str` / `int` / `bool`), `typing`-module composites (`list[str]` / `dict[str, int]` / `Optional[float]` / `Union[str, int]`), arbitrary pydantic models including **dot-notation nested types** like `MyContainer.Query`, and the DSPy-special types `dspy.Image` and `dspy.History`. Input-field type-checking is **on by default** with warning-level enforcement that can be disabled via `dspy.configure(warn_on_type_mismatch=False)`. The page closes by pointing forward to the value Signatures unlock — **composition into [[DSPyModules|Modules]]** and **compilation into optimized prompts / finetunings**.

## Key Claims

- **A Signature is a *declarative specification of input/output behavior of a DSPy module*.** This is the page's one-line definition and the canonical anchor for the entire abstraction. The framing is deliberately *declarative*: the developer says *what* the module's inputs and outputs are, **not** *how* the LM should be prompted to produce them. The prompt is an implementation detail the framework constructs from the Signature.

- **Signatures are not just function signatures — they *declare and initialize* module behavior.** *"Unlike traditional function signatures that merely describe arguments, DSPy Signatures both declare and initialize module behavior."* This is the page's most consequential typing claim: a Signature is a runtime program object, not a documentation convention. The framework reads it, builds messages from it, parses responses into it, and (later) optimizes against it.

- **Field names carry semantic weight.** *"A `question` differs fundamentally from an `answer`."* The names of the fields are not decorative — they are part of the prompt the framework generates. This is what justifies the page's later advice: *"Field names should be semantically meaningful but kept simple initially."*

- **Two surface forms — inline and class-based — are *equivalent* in mechanism, *different* in capacity.** The inline string `"question -> answer"` and the class-based `class GenerateAnswer(dspy.Signature): question: str = dspy.InputField(); answer: str = dspy.OutputField()` yield the same wire-level behavior; the class form exists to carry richer information — a docstring as task description, `desc=` per-field hints, and arbitrarily complex type annotations — that the inline form cannot fit on one line.

- **Inline signatures default each field to `str` and use `: type` for narrower types.** `"question -> answer"` is *equivalent* to `"question: str -> answer: str"`. Bool / int / list / dict outputs are obtained by annotating the field with `: bool` / `: int` / `: list[str]` / `: dict[str, int]`. Multiple comma-separated input and output fields are supported: `"context: list[str], question: str -> answer: str"` (the **RAG QA** signature), `"question, choices: list[str] -> reasoning: str, selection: int"` (the **multiple-choice with reasoning** signature).

- **The `instructions=` kwarg on `dspy.Signature(...)` is the inline form's task-description channel.** The class form uses the docstring; the inline form uses `dspy.Signature("comment -> toxic: bool", instructions="Mark as 'toxic' if the comment includes insults, harassment, or sarcastic derogatory remarks.")`. This is the only way to carry the task definition without dropping into the class form.

- **DSPy modules can *expand* signatures under the hood.** *"Many DSPy modules expand signatures under the hood. For example, `dspy.ChainOfThought` adds a `reasoning` field."* A user-declared `'document -> summary'` signature passed to `dspy.ChainOfThought` becomes a `document -> reasoning, summary` signature at run time, and the response object exposes both `response.reasoning` and `response.summary`. This is the page's first concrete glimpse of how [[DSPyModules|Modules]] *layer behavior on top of* a Signature without forcing the user to declare the intermediate fields.

- **Class-based signatures unlock three things the inline form cannot express.** (1) **Task nature via docstring** — *"Verify that the text is based on the provided context."*; (2) **Input field hints via `dspy.InputField(desc=...)`** — *"facts here are assumed to be true"*; (3) **Output field constraints via `dspy.OutputField(desc=...)`** — *"Supporting evidence for claims"*. These three knobs are the page's argument for when a developer should drop the string form.

- **`Literal[...]` is the DSPy-idiomatic way to express a closed-set classification output.** The `Emotion` example uses `sentiment: Literal['sadness', 'joy', 'love', 'anger', 'fear', 'surprise'] = dspy.OutputField()` and the framework constrains the LM's output to that exact set. This is the typing surface DSPy uses for categorical classification — no separate `Enum` or `Choice` primitive, just Python's `typing.Literal`.

- **The type system spans five tiers.** *"DSPy signatures support: (1) Basic types: `str`, `int`, `bool`; (2) Typing module types: `list[str]`, `dict[str, int]`, `Optional[float]`, `Union[str, int]`; (3) Custom types defined in your code; (4) Dot notation for nested types with proper configuration; (5) Special data types: `dspy.Image`, `dspy.History`."* This is the page's enumeration of *what can appear after the colon* in a field annotation — including pydantic-model nested types like `MyContainer.Query` reached by dot notation.

- **Pydantic models are first-class.** The page demonstrates `class QueryResult(pydantic.BaseModel): text: str; score: float` used as an output type: `dspy.Signature("query: str -> result: QueryResult")`. The framework will parse the LM's structured output into a populated `QueryResult` instance. This is what makes Signatures interoperable with the broader pydantic-based Python ecosystem.

- **`dspy.Image` is the multi-modal-input typing primitive.** *"image_1: dspy.Image = dspy.InputField(desc='An image of a dog')"* is the canonical multi-modal pattern, paired with `dspy.Image.from_url(image_url)` at call time. The page demonstrates a `DogPictureSignature` that consumes one image and returns a `str` dog breed — multi-modal input through the same Signature/Module/Predict pipeline used for text. The page also names `dspy.History` as the conversational-context primitive (mentioned in the type-resolution list but not separately demonstrated here).

- **Input fields are type-checked at call time with warnings.** *"DSPy automatically validates input field values match specified types. Type mismatches trigger warnings."* Passing `predictor(number="42")` to a signature whose `number` field is annotated `int` produces a warning (not an exception). The warning channel can be disabled globally via `dspy.configure(warn_on_type_mismatch=False)`.

- **Signatures' primary value emerges in composition.** *"While signatures streamline prototyping with structured inputs/outputs, their primary value emerges when composing multiple signatures into larger DSPy modules and compiling these into optimized prompts and finetunings."* The page's closing claim positions Signatures as the **stable interface layer** that [[DSPyModules|Modules]] (page 5 of 13) compose and [[DSPyOptimizers|Optimizers]] (page 13 of 13) tune against. This is the same *Signature-is-the-stable-interface, Module-is-the-swappable-strategy* point [[DSPyProgrammingModel|the Programming Model]] makes at the philosophy level, now stated at the API level.

## Key Quotes

> "A signature is a declarative specification of input/output behavior of a DSPy module." — the one-line definition; canonical anchor for the entire abstraction.

> "Signatures enable you to communicate *what* needs to happen rather than *how* to prompt the model." — the declarative vs imperative framing.

> "Unlike traditional function signatures that merely describe arguments, DSPy Signatures both declare and initialize module behavior. Field names carry semantic weight — a `question` differs fundamentally from an `answer`." — Signatures are runtime program objects, and field names are part of the prompt.

> "The DSPy compiler will figure out how to build a highly-optimized prompt for your LM (or finetune your small LM) for your signature, on your data, and within your pipeline." — the value proposition: a Signature is the input to a prompt-and-weights *compiler*, not a free-form text prompt.

> "Many DSPy modules expand signatures under the hood. For example, `dspy.ChainOfThought` adds a `reasoning` field." — Modules *layer* fields on top of a user-declared Signature without the user having to declare them.

> "For advanced tasks requiring verbosity, use class-based signatures to: (1) Clarify task nature via docstring; (2) Supply input field hints using `desc` parameter in `dspy.InputField`; (3) Supply output field constraints using `desc` parameter in `dspy.OutputField`." — the *when to drop the inline form* checklist.

> "DSPy automatically validates input field values match specified types. Type mismatches trigger warnings." — the type-checking policy: warn-not-fail, with an opt-out via `dspy.configure(warn_on_type_mismatch=False)`.

> "While signatures streamline prototyping with structured inputs/outputs, their primary value emerges when composing multiple signatures into larger DSPy modules and compiling these into optimized prompts and finetunings." — Signatures are the *interface* the rest of DSPy composes against.
