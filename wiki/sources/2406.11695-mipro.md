## Summary

Opsahl-Ong, Ryan, Purtell, Broman, [[ChristopherPotts|Potts]], [[MateiZaharia|Zaharia]] & [[OmarKhattab|Khattab]] ([[stanforduniversity|Stanford]] / [[BasisAI|Basis]] / [[KTH|KTH]] / [[UCBerkeley]], arXiv 2406.11695v2, EMNLP 2024) is the **canonical paper for [[MIPROv2|MIPRO]]** — *"**M**ulti-prompt **I**nstruction **PR**oposal **O**ptimizer"* — and the formalization of the **prompt-optimization problem for multi-stage [[LMProgram|LM programs]]**. The paper (i) gives Algorithm 1, a generic optimizer template `Initialize → Propose → Update → ExtractOptimizedSets` parameterized by an arbitrary [[LMProgram|LM program]] $\Phi$, metric $\mu$, and trainset $\mathcal{D}$, (ii) identifies the two structural challenges of multi-stage prompt optimization — the **proposal challenge** (intractable prompt-space) and the **credit-assignment challenge** (no per-module labels) — and proposes three strategies for each, (iii) instantiates the framework as **five concrete optimizers** ([[BootstrapRandomSearch|Bootstrap Random Search]], Bayesian Bootstrap, [[ModuleLevelOPRO|Module-Level OPRO]], **[[MIPROv2|MIPRO]]**, **0-Shot MIPRO**, **0-Shot MIPRO++**) plus variants (Program-Level OPRO, CA-OPRO), and (iv) releases the **[[DSPyOptimizerBenchmark|DSPy Optimizer Benchmark]]** — seven diverse [[LMProgram|LM-program]] tasks ([[hotpotqa|HotPotQA]], **[[HotPotQAConditional]]**, [[Iris]], **[[IrisTypo]]**, **[[HeartDisease]]**, **[[ScoNe]]**, [[HoVer]]) with which MIPRO outperforms baselines on **5/7** tasks by up to **13% absolute accuracy** using a Llama-3-8B task model + GPT-3.5 proposer.

The paper is the **direct predecessor of [[2407.10930-better-together|BetterTogether (2024)]] and [[2507.19457-gepa|GEPA (ICLR 2026)]]**: it ships the optimizer that GEPA explicitly benchmarks against (and beats by >10% across six tasks), and it ships the algorithmic chassis ([[BootstrapDemonstrations|bootstrap demos]] → grounded proposal → discrete search) that the entire later DSPy-adjacent optimizer line specializes.

## Key Claims

- **Problem statement** (§2). [[PromptOptimization|Prompt optimization]] for multi-stage [[LMProgram|LM programs]] is formalized as $\Phi^* = \arg\max_{\mathbf{V}\mapsto S}\frac{1}{|\mathcal{D}|}\sum_{(x,x')\in\mathcal{D}}\mu(\Phi_{\mathbf{V}\mapsto S}(x), x')$ where $\mathbf{V}$ is the set of all variables (instructions and demonstrations) used by prompt templates in $\Phi$, $S$ is the space of strings, and $\mu$ is a task-level metric. Intractable because: (i) string space is infinite, (ii) supervision is task-level only (no per-module gold labels — the **credit-assignment challenge**), (iii) no gradient/log-prob access (rules out [[PrefixTuning|gradient-based prompt tuning]] like [[PrefixTuning|prefix-tuning]] / [[AutoPrompt|AutoPrompt]]), (iv) small data budgets, (v) small LM-call evaluation budgets.

- **Algorithm 1** (the generic LM-program optimizer): every concrete optimizer in the paper instantiates the same four-method interface — `Initialize(D, θ)` (consume trainset + proposer hyperparams), `Propose(θ)` (sample $\mathbf{V} \mapsto S_k$), `Update(\mathbf{V} \mapsto S_k, \sigma)` (update internal state from observed mini-batch score $\sigma$), `ExtractOptimizedSets()` (return best assignment).

- **Three proposal strategies** (§3.1): (1) [[BootstrapDemonstrations|bootstrapping demonstrations]] — run $\Phi(x)$ on trainset inputs, keep metric-passing traces as candidate few-shot examples (after Khattab et al. 2024); (2) **grounding** — provide the proposer LM with **dataset summary + program summary + bootstrapped demos + per-stage prompt-engineering tips** as zero-shot context for instruction drafting; (3) **learning to propose** — parameterize the proposer's hyperparameters (use dataset summary? use program summary? tip choice?) and learn a [[BayesianOptimization|Bayesian model]] over which proposal configuration works best for a given task / program / LM trio.

- **Three credit-assignment strategies** (§3.2): (1) **greedy** — optimize one stage at a time (rejected: equally bad accuracy, much worse wall-clock); (2) **surrogate** — Bayesian model ([[TreeStructuredParzenEstimator|Tree-Structured Parzen Estimator]] via [[Optuna]]) over the joint space of (instruction, demo-set) per module; (3) **history-based** — pass the proposer LM a history of past evaluations and rely on its in-context inference (OPRO-style).

- **Optimizer instantiations** (§4):
  - **[[BootstrapRandomSearch|Bootstrap Random Search]]** (§4.1) — Khattab et al. 2024's baseline; bootstraps $N$ candidate demo-sets, evaluates each on full trainset, keeps best. Demos-only.
  - **[[ModuleLevelOPRO|Module-Level OPRO]]** (§4.2) — extends [[OPRO|OPRO]] (Yang et al. 2023) to multi-module programs by treating *program score* as a per-module proxy quality signal. Instructions-only.
  - **[[MIPROv2|MIPRO]]** (§4.3) — full bi-axial optimizer: bootstrap demos × Bayesian-surrogate search over (instruction, demo-set) per module + mini-batch evaluation. Bayesian model implemented via [[TreeStructuredParzenEstimator|TPE]] in [[Optuna]] (Akiba et al. 2019).
  - **0-Shot MIPRO** (§4.4) — MIPRO restricted to instructions-only (no bootstrapped demos in the optimized program).
  - **Bayesian Bootstrap** (§4.4) — MIPRO restricted to demos-only.
  - **MIPRO++ / 0-Shot MIPRO++** (§4.4) — uses Bayesian surrogate to optimize the **proposer's hyperparameters** (whether to use dataset summary, program summary, which tip), not the program parameters directly — the "Learning to Propose" instantiation.
  - **Program-Level OPRO** (§4.5) — OPRO with full multi-stage trajectory in the proposer's history. Strong assumption that the LM can do credit assignment from long traces. Did not beat Module-Level OPRO in initial experiments.
  - **CA-OPRO** ("Coordinate-Ascent OPRO", §4.5) — greedy per-module OPRO; rejected on cost / gain ratio.

- **[[DSPyOptimizerBenchmark|Benchmark]]** (§5.1, Table 1) — seven LM-program tasks:

| Benchmark | Task Type | Program | Modules | LM Calls | Metric |
|---|---|---|---|---|---|
| [[hotpotqa|HotPotQA]] | Multi-Hop QA | Multi-Hop Retrieval | 2 | 3 | Exact Match |
| **[[HotPotQAConditional]]** | Multi-Hop QA + conditional rules | Multi-Hop Retrieval | 2 | 3 | Custom |
| [[Iris]] | Classification | [[chainofthought|Chain of Thought]] | 1 | 1 | Accuracy |
| **[[IrisTypo]]** | Classification (misspelled prompt) | [[chainofthought|Chain of Thought]] | 1 | 1 | Accuracy |
| **[[HeartDisease]]** | Classification | Answer Ensemble | 2 | 4 | Accuracy |
| **[[ScoNe]]** | NLI (nested negation) | [[chainofthought|Chain of Thought]] | 1 | 1 | Exact Match |
| [[HoVer]] | Multi-Hop Claim Verify | Multi-Hop Retrieval | 4 | 4 | Recall@21 |

  500 train / 500 dev / 2000 test (or full test if smaller). Each method run 5× with [[WilcoxonSignedRankTest|Wilcoxon signed-rank]] significance testing.

- **Results headline** (Table 2): MIPRO is best on **5/7 tasks** by up to 13% absolute. Exceptions: HotPotQA, HeartDisease, Iris-no-typo — all of which Bootstrap RS and Bayesian Bootstrap (demos-only) handle adequately.

- **Five lessons for practitioners** (§6):
  1. **Optimizing bootstrapped demonstrations is essential.** For most tasks, demos-only beats instructions-only with Wilcoxon significance.
  2. **Joint optimization of both is best overall.** MIPRO wins on 5/7 with Wilcoxon significance.
  3. **Instructions matter most when the task has conditional rules** not expressible in a small number of few-shot examples — HotPotQA Conditional, Heart Disease, Iris-Typo. *"This lesson is also reflected in the Heart Disease results, as discussed above."* On Iris-Typo the instruction optimizer **even corrects mistakes in the seed prompt** (an accidental misspelling "versicolour" vs "versicolor" — left in as a realistic test).
  4. **Grounding helps for instruction proposal overall, but the best proposal strategy varies by task.** On ScoNe, grounding hurt; MIPRO++ recovers ScoNe by learning per-task that grounding isn't helpful. Importance scores from the Bayesian model are themselves interpretable diagnostics.
  5. **More to learn about LM-program optimizers.** Optimizer rankings differ across budgets; future work should study the budget-axis explicitly.

- **Default experimental setup**: GPT-3.5 as proposer (temperature 0.7), Llama-3-8B as task model. For bootstrapping few-shot demos a default Llama-3-8B teacher is used, swapped to GPT-4o for the harder tasks (ScoNe, HoVer). 20–50 trials per optimizer.

- **Composability with DSPy** (§1). The optimizers all live inside the [[DSPy]] programming model (Khattab et al., 2024). All released in `dspy.MIPROv2` and siblings on dspy.ai.

## Key Quotes

> *"To make this tractable, we factorize our problem into optimizing the free-form instructions and few-shot demonstrations of every module and introduce several strategies to craft task-grounded instructions and navigate credit assignment across modules."* — §Abstract

> *"We identify two key challenges. First, the **proposal challenge**: the space of possible prompts is intractably large, and this is exacerbated as the number of modules increase. ... Second, the **credit assignment challenge**: our problem requires jointly optimizing over many distinct variables that parameterize the prompts of all modules. To allocate search effort, we must infer the impact of our configurations for each variable effectively."* — §2

> *"Optimizing bootstrapped demonstrations as few-shot examples is key to achieving the best performance. ... Optimizing both instructions and few-shot examples with MIPRO generally yields the best overall performance."* — §6 (Lessons 1, 2)

> *"Instruction optimization is most important for tasks with conditional rules that are (i) not immediately obvious to the LM and (ii) not expressible via a limited number of few-shot examples."* — §6 (Lesson 3)

> *"By separating the task of credit assignment from prompt proposal, we allow the proposal LM to focus on the task of proposal only. Credit assignment and final selection is then done post-hoc using our surrogate model."* — §4.3

> *"In the Iris-Typo setting, our instruction optimizer even helps correct mistakes in the seed prompt."* — §6 (Lesson 3) — the misspelled-versicolour case.

## Contradictions

- **Empirical contradicts the implicit "instructions dominate" prior:** in the wiki's [[2507.19457-gepa|GEPA]] paper, declarative instructions decisively beat few-shot exemplars (Wan et al. 2024 reversed). In this paper (2024), **demos-only is typically strongest**; instructions matter most when the task has conditional rules. The Wan et al. (2024) "few-shot quasi-exemplars dominate" framing is consistent with **this paper**, not with the 2026 [[2507.19457-gepa|GEPA]] result. Both can be true with respect to different LM generations: the instruction-following + self-reflection capabilities improved between the GPT-3.5/Llama-3-8B regime (2024) and the Qwen3-8B / GPT-4.1-Mini regime (2026). The wiki should treat the **instruction-vs-demonstration prior as model-generation-dependent**, not absolute.

- **CA-OPRO greedy credit assignment underperforms:** *"From initial experiments, we found CA-OPRO's performance did not justify its inefficiency."* This is the negative result the wiki should cite when other work proposes greedy single-module prompt optimization in multi-stage programs.

- **Bayesian-surrogate optimization only over the existing proposal set:** the paper explicitly flags that surrogate-based optimization (§3.2) *"only allows for optimization over a fixed set of proposals. Learnings from past evaluations cannot be used to improve the proposals themselves."* — this is **exactly the limitation [[2507.19457-gepa|GEPA]] addresses two years later** with reflective prompt mutation that *generates new proposals* from evaluation traces.
