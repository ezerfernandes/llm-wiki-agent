# DSPy Guardrails: Building Safe LLM Applications via Self-Refining Language Model Pipelines

[[BoxiYu]] & [[PinjiaHe]] ([[CUHKShenzhen|The Chinese University of Hong Kong, Shenzhen]], arXiv preprint, 2024) — short 2-page workshop-style paper introducing **[[DSPyGuardrails]]**, a method that autonomously optimizes [[Guardrail|LLM guardrails]] through [[DSPy]]'s self-refining pipeline machinery rather than through manually-written rules and prompts.

## Summary

Existing safety guardrails — [[LlamaGuard]] ([[InanEtAl2023|Inan et al. 2023]]), [[NeMoGuardrails]] ([[RebedeaEtAl2023|Rebedea et al. 2023]]), and [[GuardrailsAI]] ([[Rajpal2023]]) — require **manual configuration and prompt engineering**, which the authors argue does not generalize to constantly evolving [[Jailbreak|jailbreak]] techniques. The paper proposes **[[DSPyGuardrails]]**: use [[DSPy]] ([[KhattabEtAl2023|Khattab et al. 2023]]) to algorithmically optimize the guardrail program. Two-step recipe: (1) define an [[LMProgram|LLM Program]] with guardrails using [[DSPySignatures|DSPy signatures]] and [[DSPyModules|modules]]; (2) supply datasets and select a DSPy [[DSPyOptimizers|compiler/teleprompter]] (here [[BootstrapFewShot]]) to automatically optimize the guardrails.

Evaluation uses [[CodeAttack]] ([[RenEtAl2024|Ren et al. 2024]]) as the jailbreak method against **gpt-3.5-turbo-instruct**, with 20 jailbreak prompts and 8-shot in-context learning ([[FewShotLearning|few-shot]]) as the baseline. Metric is [[AttackSuccessRate|Attack Success Rate (ASR)]] — lower is better. **DSPy Guardrails drop ASR from 75% (no guardrails / baseline ICL) to 5% (with optimizer); without the optimizer the DSPy program alone reaches 30%**, underscoring the optimizer's role.

## Key Claims

- Existing guardrails ([[LlamaGuard]], [[NeMoGuardrails]], [[GuardrailsAI]]) **necessitate manual configuration and prompting**, which does not universally counter evolving jailbreak methodologies.
- [[Jailbreak]] techniques *"are constantly evolving every day"* — pre-written rules cannot keep up; automatic optimization is required.
- [[DSPyGuardrails]] autonomously optimize guardrails via [[DSPy]]'s **self-improving language model pipelines** — no human prompt-iteration needed once datasets and metric are fixed.
- Two-step usage recipe: (1) define LLM Program with guardrails using DSPy signatures + modules; (2) provide datasets and select the DSPy compiler/teleprompter to auto-optimize.
- [[CodeAttack]] decreases ASR from **75% → 5%** under DSPy Guardrails on gpt-3.5-turbo-instruct.
- **The optimizer is load-bearing**: without it, the same DSPy program reaches only 30% ASR — *"This underscores the pivotal role of the optimizer in enhancing the self-refinement of the LLM Program in conjunction with guardrails."*
- Architecture (Fig. 1): `Dataset → LLM Program with Guardrails → LLM Optimizer → LLM Program with Optimized Guardrails`.

## Architecture (Listing 1)

The `Assistant` [[DSPySignatures|signature]] has two input fields (`text`, `guardrails`) and one output (`answer`). The `Assistant_Alpha` [[DSPyModules|module]] wraps `dspy.ChainOfThought(Assistant)` in a `forward(text, guardrails)` method:

```python
class Assistant(dspy.Signature):
    text = dspy.InputField(desc="Instructions to the assistant")
    guardrails = dspy.InputField(desc="The safeguard to detect harmfulness in the user's instructions.")
    answer = dspy.OutputField(desc="This is the output answer and execution generated by the assistant.")

class Assistant_Alpha(dspy.Module):
    def __init__(self):
        super().__init__()
        self.generate_answer = dspy.ChainOfThought(Assistant)

    def forward(self, text, guardrails):
        return self.generate_answer(text=text, guardrails=guardrails)
```

The program is then compiled with `BootstrapFewShot` against a dataset of jailbreak vs. benign examples, scoring via a harmfulness metric. The optimizer searches for the best instructions + few-shot demonstrations of *guardrail reasoning* on top of [[chainofthought]]. [[BootstrapDemonstrations|DSPy demonstrations]] are framed as *"like few-shot examples, but far more powerful"* — they integrate into the prompt and build optimized guardrails.

## Evaluation

| Setup | ASR ↓ |
|---|---|
| Baseline (8-shot ICL, no DSPy) | **75%** |
| DSPy Guardrails **without optimizer** | 30% |
| **DSPy Guardrails (with `BootstrapFewShot`)** | **5%** |

- **Attack**: [[CodeAttack]] ([[RenEtAl2024]]) — reformulates the text-completion jailbreak task as a *code-completion* task. The 2024 reference paper reports CodeAttack achieves >80% ASR across all tested SOTA LLMs including GPT-4 ([[GPT4_1]]).
- **Defender**: gpt-3.5-turbo-instruct + DSPy program with guardrails.
- **Optimizer**: built-in [[BootstrapFewShot]] teleprompter.
- **Baseline**: 8-shot ICL with the same examples DSPy Guardrails uses for bootstrapping.
- **Metric**: ASR — lower is better (safer guardrail).

## Connections

- [[DSPy]] — the underlying programming framework. Guardrails are an [[LMProgram|LM program]] like any other: typed [[DSPySignatures|signature]] + [[DSPyModules|module]] + [[DSPyOptimizers|optimizer]].
- [[chainofthought]] — the [[DSPyModules|module]] the `Assistant` is built on; the guardrail's reasoning step is CoT-mediated.
- [[BootstrapFewShot]] — the [[DSPyOptimizers|teleprompter]] used; the optimizer that drives ASR 30% → 5%.
- [[CodeAttack]] — the jailbreak attack method evaluated against. Reformulates text completion as code completion to bypass safeguards.
- [[Jailbreak]] — the general adversarial-input problem class this paper defends against.
- [[Guardrail]] — the general defensive abstraction; concrete instantiations: [[LlamaGuard]], [[NeMoGuardrails]], [[GuardrailsAI]], [[DSPyGuardrails]].
- [[LlamaGuard]] / [[NeMoGuardrails]] / [[GuardrailsAI]] — manual-configuration baselines the paper positions itself against.
- [[AttackSuccessRate]] — the load-bearing metric (lower = safer).
- [[BoxiYu]] / [[PinjiaHe]] / [[CUHKShenzhen]] — authors and affiliation.
- [[2406.11695-mipro|MIPRO]] / [[2507.19457-gepa|GEPA]] — successor [[DSPyOptimizers|DSPy optimizers]] that could in principle replace `BootstrapFewShot` here for stronger guardrails; the paper predates both (uses 2023-era BootstrapFewShot).
- [[2402.01817-llm-modulo|LLM-Modulo]] — orthogonal framing: this paper's guardrail-as-module is *inside* the LLM (the guardrail signature is part of the same `Assistant` prompt), whereas LLM-Modulo would put a *separate external sound critic* outside the LLM. DSPy Guardrails relies on the LLM's own judgment + optimized demonstrations, not an external verifier.

## Contradictions / Tensions

- **Vs. [[LlamaGuard]] / [[NeMoGuardrails]] / [[GuardrailsAI]] design philosophy**: those frameworks center *human-written rules* (Nvidia NeMo's [[Colang|Colang]] dialog flows, Llama Guard's safety taxonomy, Guardrails AI's pydantic-style validators) as the load-bearing safety surface. This paper argues the human-rule layer is the bottleneck and replaces it with an automatically-optimized prompt — a *category-level* methodological disagreement, not a benchmark dispute.
- **Optimizer is the load-bearing piece, not the DSPy framing per se**: the unoptimized DSPy program scores 30% ASR — better than the 75% baseline but far from the 5% optimized number. This means most of the gain is from `BootstrapFewShot`'s demonstration search, not from DSPy's signature/module abstraction itself. A reader who skims only the abstract may attribute the win to "DSPy" when it is more precisely attributable to *automatic prompt optimization* over a DSPy-shaped program.
- **Single attack, single model, 20 prompts**: the evaluation is narrow — one attack family ([[CodeAttack]]), one defender LM (gpt-3.5-turbo-instruct), 20 prompts. The paper's own framing — *"jailbreak techniques are constantly evolving every day"* — applies recursively to itself: ASR 5% on CodeAttack does not generalize to attacks crafted after the bootstrap dataset was sampled. **Not benchmarked against newer attacks or stronger models (GPT-4, Claude).**
- **No comparison against [[LlamaGuard]] / [[NeMoGuardrails]] / [[GuardrailsAI]] head-to-head** — the paper criticizes them for requiring manual configuration but does not run them on the same CodeAttack benchmark. The 75% baseline is *no guardrail at all + 8-shot ICL*, not a strong-baseline guardrail.

## Position in the DSPy paper cluster

| Paper | Year | Object of optimization | Outcome |
|---|---|---|---|
| [[KhattabEtAl2023|Khattab et al. 2023]] ([[DSPy]] core) | 2023 | Generic LM pipelines | Framework introduction |
| **DSPy Guardrails (this paper)** | **2024** | **Safety guardrails** | **CodeAttack ASR 75% → 5%** |
| [[2406.11695-mipro|MIPRO]] | 2024 | Multi-stage LM programs (instructions + demos jointly) | 7-task benchmark, +13% over baselines |
| [[2407.10930-better-together|BetterTogether]] | 2024 | Prompts + weights bi-axially | 7/9 task-LM cells beat single-axis baselines |
| [[2507.19457-gepa|GEPA]] (ICLR 2026 Oral) | 2025/26 | Reflective prompt mutation | Beats [[grpo|GRPO]] RL by 6–20%; beats MIPROv2 by >10% |

DSPy Guardrails sits as the **safety-application** entry in the DSPy optimizer-application cluster — the same `dataset + metric + optimizer` recipe MIPRO / BetterTogether / GEPA later generalize, applied to the narrow problem of jailbreak defense. It is one of the earliest published demonstrations that **`BootstrapFewShot` + a well-chosen metric is competitive with hand-engineered safety rules**, predating the strong-optimizer line.
