## Summary

File 40/44 of *[[TheEmbeddedRustBook]]* — **second leaf** of the *Interoperability* chapter ([[rust-embedded-book-interoperability-index]]), the **mirror image** of file 39 ([[rust-embedded-book-interoperability-c-with-rust]]). Where file 39 was about consuming C/C++ **from** Rust, this chapter is about exposing Rust **to** C/C++: the two halves are **(1) build a C-friendly Rust API** (export the crate as a `cdylib` or `staticlib` via the `[lib] crate-type` declaration in `Cargo.toml`; mark each exported function with [[NoMangle|`#[no_mangle]`]] to defeat Rust's symbol mangling; mark its signature with [[ExternC|`extern "C"`]] to switch from Rust's unstable internal ABI to the platform C ABI) and **(2) embed the produced library in an external build system** (Cargo emits `my_lib.so` / `my_lib.dll` / `my_lib.a` per host/setting; the host project's `make` / `CMake` / IDE links it like any other system library; the C side needs a matching header which can be hand-written or auto-generated by [[Cbindgen|`cbindgen`]] — the inverse direction of [[Bindgen|`bindgen`]]). The chapter is **explicitly the mirror** of [[rust-embedded-book-interoperability-c-with-rust]] — same C-ABI-as-lingua-franca rule, same handwave on third-party build-system integration ("This very much depends on your project and/or build system").

## Key Claims

- **Two-half task structure.** *"Using Rust code inside a C or C++ project mostly consists of two parts. — Creating a C-friendly API in Rust — Embedding your Rust project into an external build system."* Mirrors file 39's two-half structure (define the interface + build the dependency) but inverted: here it's expose the interface + embed the produced library.
- **`cargo` is the universal Rust-side build driver.** *"Apart from `cargo` and `meson`, most build systems don't have native Rust support. So you're most likely best off just using `cargo` for compiling your crate and any dependencies."* Pragmatic answer to multi-build-system interop: drive Rust with [[Cargo]], have the host build system absorb Cargo's output as a library artifact.
- **`crate-type` selects the systems-library output.** Standard `Cargo.toml` declaration:
  ```toml
  [lib]
  name = "your_crate"
  crate-type = ["cdylib"]      # Creates dynamic lib
  # crate-type = ["staticlib"] # Creates static lib
  ```
  These are the two C-consumable forms — `cdylib` emits `lib<name>.so` / `<name>.dll` / `lib<name>.dylib` (dynamic library with a C-compatible export table); `staticlib` emits `lib<name>.a` / `<name>.lib` (static archive). The `[lib] name = "..."` line allows decoupling the library output name from the crate name. Static archive is the form file 39 also named as *"the embedded delivery format"* for [[BareMetalProgramming|bare-metal]] firmware.
- **C is the lingua franca even when interfacing with C++.** *"Because C++ has no stable ABI for the Rust compiler to target, we use `C` for any interoperability between different languages. This is no exception when using Rust inside of C and C++ code."* Same rule as [[rust-embedded-book-interoperability-c-with-rust]] applied in the opposite direction — exported `extern "C"` signatures are the universal interop surface.
- **`#[no_mangle]` defeats Rust symbol mangling.** *"The Rust compiler mangles symbol names differently than native code linkers expect. As such, any function that Rust exports to be used outside of Rust needs to be told not to be mangled by the compiler."* — operationally, the C linker looks up a symbol literally named `rust_function`; without `#[no_mangle]` the Rust compiler emits something like `_ZN8my_crate13rust_function17h6c2e4a8b3d5f1e9aE` and the link fails.
- **`extern "C"` switches the function ABI.** *"By default, any function you write in Rust will use the Rust ABI (which is also not stabilized). Instead, when building outwards facing FFI APIs we need to tell the compiler to use the system ABI."* This is the **exported** form of [[ExternC|`extern "C"`]] (the file 39 chapter covered the imported declaration-block form; this chapter covers the function-definition form).
- **Canonical exported-function shape.** Combining the two:
  ```rust,ignore
  #[no_mangle]
  pub extern "C" fn rust_function() {

  }
  ```
  Every Rust function exposed to C must carry **both** attributes — `#[no_mangle]` (for the linker) and `extern "C"` (for the compiler's calling-convention selection). This is exactly the syntactic pair [[ExternC]] documented as form (2) — *"Function definition exported to C — defined in Rust, called from C."*
- **Platform-specific ABI variants.** *"Depending on your platform, you might want to target a specific ABI version, which are documented [here](https://doc.rust-lang.org/reference/items/external-blocks.html)."* — beyond `extern "C"`, Rust supports `extern "system"` (Win32-friendly), arch-specific strings like `extern "aapcs"` / `extern "thiscall"`, etc.
- **Data marshaling still applies.** *"Just as when using `C` code in your Rust project you now need to transform data from and to a form that the rest of the application will understand."* — the FFI **data-layout** half ([[ReprC|`#[repr(C)]`]] on shared structs, [[RawPointer|raw pointers]] in place of references, `cty::c_int` / `cty::c_char` aliases for platform-variable C primitives) carries over wholesale from [[rust-embedded-book-interoperability-c-with-rust]].
- **Linking is build-system-specific.** *"This very much depends on your project and/or build system."* Cargo produces the artifact; the host build system links it. *"`cargo` will create a `my_lib.so`/`my_lib.dll` or `my_lib.a` file, depending on your platform and settings. This library can simply be linked by your build system."* Same handwave as file 39's `Make`/`CMake` shell-out branch.
- **Every Rust-FFI function needs a matching C header declaration.** *"calling a Rust function from C requires a header file to declare the function signatures. Every function in your Rust-ffi API needs to have a corresponding header function."* Worked translation:
  ```rust,ignore
  #[no_mangle]
  pub extern "C" fn rust_function() {}
  ```
  →
  ```C
  void rust_function();
  ```
- **`cbindgen` auto-generates C headers from Rust source — the inverse of [[Bindgen]].** *"There is a tool to automate this process, called [cbindgen] which analyses your Rust code and then generates headers for your C and C++ projects from it."* The chapter cites the canonical repo as `github.com/eqrion/cbindgen`. Recall file 39 named [[Bindgen|`bindgen`]] as the Rust-side codegen that translates C `.h` → Rust; **`cbindgen` is its symmetric counterpart** going Rust → C `.h`.
- **C consumption is then trivial.** *"At this point, using the Rust functions from C is as simple as including the header and calling them!"*
  ```C
  #include "my-rust-project.h"
  rust_function();
  ```
  The C compiler now has a function declaration that resolves at link time against the Rust-produced `.so`/`.dll`/`.a`.

## Contradictions

None. The chapter is the **deliberate mirror** of [[rust-embedded-book-interoperability-c-with-rust]] — same C-ABI-as-lingua-franca rule, same build-system handwave, same data-marshaling discipline. The only thing it adds in the **opposite direction** is the export-side attribute pair (`#[no_mangle]` + `pub extern "C" fn`) and the export-side codegen tool ([[Cbindgen|`cbindgen`]]).
