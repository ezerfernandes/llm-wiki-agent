# The Embedded Rust Book — Concurrency

## Summary

File 28/44 of *[[TheEmbeddedRustBook]]* — **single-file chapter** (the *Concurrency* chapter has no sub-files). Frames embedded concurrency as the union of three sources — **[[Interrupt|interrupt handlers]]**, **multithreading** (cooperative or preemptive), and **multi-core** (SMP) — and walks a single running example (a 1 Hz rising-edge frequency counter on a shared `COUNTER`, reset each second by a timer [[Interrupt|interrupt]]) through six escalating solutions to the same [[DataRace|data race]]: (1) **no concurrency** (single main loop, no interrupts — *"sometimes this is perfectly suited"*); (2) **`static mut COUNTER: u32` + `unsafe`** — exhibits the canonical *load-increment-store* race where the interrupt fires between load and store and the reset is silently lost (*"we would count twice as many transitions for that period"*); (3) **[[CriticalSection|critical sections]]** via `cortex_m::interrupt::free` (a [[CortexMCrate|`cortex-m`]] primitive) — disables interrupts inside the closure (*"this is also the same as disabling interrupts, running some code, and then re-enabling interrupts"*), but **does not give exclusivity on multi-core** (*"the other core could be happily accessing the same memory as your core, even without interrupts"*); (4) **[[Atomic|atomic instructions]]** (`AtomicUsize::fetch_add`, `core::sync::atomic::Ordering::Relaxed`) — Cortex-M architectural split: **thumbv6** (M0 / M0+) has only atomic load/store, **thumbv7** (M3 and above) has full **Compare-and-Swap (CAS)**; *"these atomic operations are safe even across multiple cores"*; (5) **safe abstraction** wrapping an [[UnsafeCell|`UnsafeCell<u32>`]] in a `CSCounter` struct, using `unsafe impl Sync for CSCounter {}` plus a `&interrupt::CriticalSection` token parameter on every method — moves all `unsafe` *into* the abstraction so the application has none, and uses the **CriticalSection token** to **statically prove** the caller is inside a critical section with **zero runtime overhead** (one `cs` can serve many counters, no nested locks); (6) the **`cortex_m::interrupt::Mutex` + [[CellRust|`Cell`]]** generalization (the [[Mutex|`Mutex`]] applied to embedded) — `Mutex<T>` implements `Sync` for any `T: Send` (e.g. `Cell<u32>`), and the only access path is `mutex.borrow(cs)` inside `interrupt::free`, so the **CriticalSection token *is* the lock**; no separate lock-state to track, no deadlock possible. For non-`Copy` shared state (e.g. a peripheral [[Singleton|singleton]] like `stm32f405::GPIOA`), the chapter promotes the pattern to **`Mutex<RefCell<Option<T>>>`**: `Mutex` for `Sync`, [[RefCell|`RefCell`]] for **safe interior mutability via references** (the [[CellRust|`Cell`]] API only allows copy-in / copy-out, not `&T`), `Option` to allow `static` initialization to `None` and a deferred `replace(Some(periph))` move-in after the peripheral singleton has been `take()`-d at runtime. Worked example moves an `stm32f405::GPIOA` (read PA0, write PA1) and a `Timer<TIM2>` (mutable `tim.start(1.hz())` via `borrow_mut().deref_mut()`) into shared statics this way. Section explicitly names the **race-condition trap** at peripheral move-in: *"be careful to enable the interrupt only after setting MY_GPIO: otherwise the interrupt might fire while it still contains None, and as-written (with `unwrap()`), it would panic."* Closes with three named **alternatives** that sit *above* the manual `Mutex<RefCell<Option<T>>>` pattern: **[[RTIC]]** (Real-Time Interrupt-driven Concurrency — *"enforces static priorities and tracks accesses to `static mut` variables ('resources') to statically ensure that shared resources are always accessed safely, without requiring the overhead of always entering critical sections and using reference counting"*, *"guaranteeing no deadlocks and giving extremely low time and memory overhead"*, ships an `async` executor); **[[Embassy]]** (`async` / `await`-based executor ecosystem with `embassy-time`, HALs, `embassy-sync` synchronization primitives); and **RTOSs** (FreeRTOS / ChibiOS — cooperative or preemptive multitasking, mutexes + DMA interop — *"at the time of writing, there are not many Rust RTOS examples to point to"*). Final section reiterates the **multi-core caveat**: every example using `cortex_m::interrupt::Mutex` / critical sections assumes the only other execution thread is the interrupt thread; SMP requires the **[[Atomic|atomic-instruction]]** route or stronger primitives.

## Key Claims

- **Concurrency in embedded = three sources**. *"Interrupt handlers, which run whenever the associated interrupt happens; various forms of multithreading, where your microprocessor regularly swaps between parts of your program; and in some systems, multiple-core microprocessors, where each core can be independently running a different part of your program at the same time."*
- **The simplest concurrency is no concurrency** — single `loop { read → process → write }` with no interrupts. *"If you can get away with such a simple approach this can be a great solution."*
- **Embedded shared mutable state must be statically allocated**. *"Unlike non-embedded Rust, we will not usually have the luxury of creating heap allocations and passing references to that data into a newly-created thread. … At the lowest level, this means we must have *statically allocated* mutable memory, which both the interrupt handler and the main code can refer to."*
- **`static mut` is always unsafe** because *"without taking special care, you might trigger a race condition, where your access to the variable is interrupted halfway through by an interrupt which also accesses that variable."*
- **The canonical race**: increment on `COUNTER` *"is not guaranteed to be atomic — in fact, on most embedded platforms, it will be split into a load, then the increment, then a store. If the interrupt fired after the load but before the store, the reset back to 0 would be ignored after the interrupt returns — and we would count twice as many transitions for that period."*
- **[[CriticalSection]] = "a context where interrupts are disabled."** On Cortex-M, realized as `cortex_m::interrupt::free(|_cs| …)` (from the [[CortexMCrate|`cortex-m`]] crate) — *"this is also the same as disabling interrupts, running some code, and then re-enabling interrupts."* Other platforms have analogous primitives.
- **Asymmetry of who needs the critical section**: the *interrupt-side* write to `COUNTER` doesn't need one because *"writing 0 to COUNTER can't be affected by a race since we don't read it"* + *"it will never be interrupted by the main thread anyway."* The *main-side* increment does need one because it's interruptible.
- **Critical sections have a cost**: *"each critical section temporarily pauses interrupt processing, there is an associated cost of some extra code size and higher interrupt latency and jitter."*
- **Critical sections are not multi-core-safe**: *"while a critical section guarantees no interrupts will fire, it does not provide an exclusivity guarantee on multi-core systems! The other core could be happily accessing the same memory as your core, even without interrupts."*
- **Cortex-M atomic-instruction availability** is split by architecture: *"`thumbv6` (Cortex-M0, Cortex-M0+) only provide atomic load and store instructions, while `thumbv7` (Cortex-M3 and above) provide full Compare and Swap (CAS) instructions."* CAS is the basis of the *"attempt the increment, it will succeed most of the time, but if it was interrupted it will automatically retry the entire increment operation"* loop.
- **`AtomicUsize` / `fetch_add` / `Ordering::Relaxed` is the preferred solution when supported**. *"This time `COUNTER` is a safe `static` variable. Thanks to the `AtomicUsize` type `COUNTER` can be safely modified from both the interrupt handler and the main thread without disabling interrupts. When possible, this is a better solution — but it may not be supported on your platform."* Atomics are *"safe even across multiple cores."*
- **`Ordering::Relaxed` is sufficient on single-core**: *"assuming that the target is a single core platform `Relaxed` is sufficient and the most efficient choice in this particular case. Stricter ordering will cause the compiler to emit memory barriers around the atomic operations."*
- **[[Send]] and [[Sync]] are the canonical concurrency-safety traits**. *"A type is `Send` when it can safely be moved to another thread, while it is `Sync` when it can be safely shared between multiple threads. In an embedded context, we consider interrupts to be executing in a separate thread to the application code, so variables accessed by both an interrupt and the main code must be `Sync`."*
- **`static` variables *must* be `Sync`**. *"Because `CSCounter` contains an `UnsafeCell`, it is not `Sync`, and therefore we could not make a `static CSCounter`: `static` variables *must* be `Sync`, since they can be accessed by multiple threads."* The fix is `unsafe impl Sync for CSCounter {}` — *"to tell the compiler we have taken care that the `CSCounter` is in fact safe to share between threads."*
- **[[UnsafeCell]] is the bottom layer of [[InteriorMutability|interior mutability]]**. *"It allows you to obtain multiple mutable references to its value, but only with unsafe code."* By wrapping it, you can have a `static` (not `static mut`) variable that is still mutable, removing the per-access `unsafe`.
- **The `CriticalSection` token is a compile-time proof of being inside a critical section** (see [[CriticalSection]]). *"These tokens are only safely generated by `interrupt::free`, so by requiring one be passed in, we ensure we are operating inside a critical section, without having to actually do the lock ourselves. This guarantee is provided statically by the compiler: there won't be any runtime overhead associated with `cs`."* One token can serve many counters — no nested critical sections required.
- **A [[Mutex]] is *"one such synchronisation primitive"*** for *mutual exclusion*. *"A thread can attempt to *lock* (or *acquire*) the mutex, and either succeeds immediately, or blocks waiting for the lock to be acquired, or returns an error that the mutex could not be locked. … In Rust, we would usually implement the unlock using the `Drop` trait to ensure it is always released when the mutex goes out of scope."*
- **A blocking mutex with interrupt handlers is dangerous**. *"It is not normally acceptable for the interrupt handler to block, and it would be especially disastrous for it to block waiting for the main thread to release a lock, since we would then [[Deadlock|*deadlock*]] (the main thread will never release the lock because execution stays in the interrupt handler). Deadlocking is not considered unsafe: it is possible even in safe Rust."*
- **`cortex_m::interrupt::Mutex`** (from the [[CortexMCrate|`cortex-m`]] crate, the embedded realization of [[Mutex]]) sidesteps deadlock entirely: *"a mutex which requires a critical section to lock, just like our counter example. So long as the critical section must last as long as the lock, we can be sure we have exclusive access to the wrapped variable without even needing to track the lock/unlock state of the mutex."*
- **`Mutex<T>: Sync` for any `T: Send`** (such as a `Cell`). *"It can do this safely because it only gives access to its contents during a critical section."* Result: *"a safe counter with no unsafe code at all."*
- **[[CellRust|`Cell`]] vs [[RefCell|`RefCell`]] vs [[UnsafeCell]]** — the three layers of [[InteriorMutability|interior mutability]]: `UnsafeCell` (unsafe, lets you obtain multiple mutable refs), `Cell` (safe, copy-in/copy-out only, no references, not `Sync`), `RefCell` (safe, gives out references with **runtime borrow-counting**, more overhead than `Cell`, *"must be sure only one exists at a time"*).
- **The canonical embedded shared-peripheral pattern is `Mutex<RefCell<Option<T>>>`**. *"The `Mutex` ensures we only have access during a critical section, and therefore makes the variable `Sync`, even though a plain `RefCell` would not be `Sync`. The `RefCell` gives us interior mutability with references, which we'll need to use our `GPIOA`. The `Option` lets us initialise this variable to something empty, and only later actually move the variable in. We cannot access the peripheral singleton statically, only at runtime, so this is required."*
- **Init-order trap with `Mutex<RefCell<Option<T>>>`**: *"Be careful to enable the interrupt only after setting `MY_GPIO`: otherwise the interrupt might fire while it still contains `None`, and as-written (with `unwrap()`), it would panic."*
- **Mutable peripheral access** uses `borrow_mut().deref_mut()` + `if let Some(ref mut tim) = …` (worked example moves a `Timer<TIM2>` into `Mutex<RefCell<Option<Timer<stm32::TIM2>>>>` and calls `tim.start(1.hz())` from the interrupt).
- **[[RTIC]] (Real-Time Interrupt-driven Concurrency)** is the framework alternative. *"Enforces static priorities and tracks accesses to `static mut` variables ('resources') to statically ensure that shared resources are always accessed safely, without requiring the overhead of always entering critical sections and using reference counting (as in `RefCell`). This has a number of advantages such as guaranteeing no deadlocks and giving extremely low time and memory overhead."* Ships an **asynchronous executor**; tasks are `async fn`s; includes message-passing and task-scheduling. Documented at <https://rtic.rs>.
- **[[Embassy]]** is the `async` / `await` ecosystem alternative. *"The core of embassy is its asynchronous executor which supports most common MCU architectures."* Batteries-included: `embassy-time`, HAL libraries, `embassy-sync` (synchronization primitives). Documented at <https://embassy.dev/book/>.
- **Real-Time Operating Systems (RTOSs)** are the heavy alternative — cooperative or preemptive multitasking, mutexes + DMA. Open-source examples: FreeRTOS, ChibiOS. *"At the time of writing, there are not many Rust RTOS examples to point to, but it's an interesting area so watch this space!"*
- **Multi-core (SMP)** invalidates every `cortex_m::interrupt::free` / `cortex_m::interrupt::Mutex`-based example. *"All the examples using a critical section (including the `cortex_m::interrupt::Mutex`) assume the only other execution thread is the interrupt thread, but on a multi-core system that's no longer true. Instead, we'll need synchronisation primitives designed for multiple cores (also called SMP, for symmetric multi-processing). These typically use the atomic instructions we saw earlier, since the processing system will ensure that atomicity is maintained over all cores."*

## Key Quotes

> "Concurrency happens whenever different parts of your program might execute at different times or out of order. In an embedded context, this includes: interrupt handlers, which run whenever the associated interrupt happens, various forms of multithreading, where your microprocessor regularly swaps between parts of your program, and in some systems, multiple-core microprocessors." — the chapter's three-source decomposition.

> "Unlike non-embedded Rust, we will not usually have the luxury of creating heap allocations and passing references to that data into a newly-created thread. … At the lowest level, this means we must have *statically allocated* mutable memory, which both the interrupt handler and the main code can refer to." — the embedded twist that makes [[InteriorMutability|interior mutability]] central.

> "The increment on `COUNTER` is *not* guaranteed to be atomic — in fact, on most embedded platforms, it will be split into a load, then the increment, then a store. If the interrupt fired after the load but before the store, the reset back to 0 would be ignored after the interrupt returns — and we would count twice as many transitions for that period." — the canonical [[DataRace|data race]] worked example.

> "By wrapping the access to `COUNTER` in `main` in a critical section, we can be sure the timer interrupt will not fire until we're finished incrementing `COUNTER`. … This is also the same as disabling interrupts, running some code, and then re-enabling interrupts." — the [[CriticalSection]] one-paragraph definition.

> "It's worth noting that while a critical section guarantees no interrupts will fire, it does not provide an exclusivity guarantee on multi-core systems! The other core could be happily accessing the same memory as your core, even without interrupts." — the multi-core caveat that gates the entire `cortex_m::interrupt`-based stack.

> "`thumbv6` (Cortex-M0, Cortex-M0+) only provide atomic load and store instructions, while `thumbv7` (Cortex-M3 and above) provide full Compare and Swap (CAS) instructions. These CAS instructions give an alternative to the heavy-handed disabling of all interrupts. … These atomic operations are safe even across multiple cores." — the architectural split that makes [[Atomic|atomics]] portability-sensitive.

> "A type is `Send` when it can safely be moved to another thread, while it is `Sync` when it can be safely shared between multiple threads. In an embedded context, we consider interrupts to be executing in a separate thread to the application code, so variables accessed by both an interrupt and the main code must be `Sync`." — the [[Send]] / [[Sync]] definitions adapted to embedded.

> "These tokens are only safely generated by `interrupt::free`, so by requiring one be passed in, we ensure we are operating inside a critical section, without having to actually do the lock ourselves. This guarantee is provided statically by the compiler: there won't be any runtime overhead associated with `cs`." — the **`CriticalSection` token as compile-time proof** idea (see [[CriticalSection]]).

> "It is not normally acceptable for the interrupt handler to block, and it would be especially disastrous for it to block waiting for the main thread to release a lock, since we would then *deadlock* (the main thread will never release the lock because execution stays in the interrupt handler). Deadlocking is not considered unsafe: it is possible even in safe Rust." — why blocking mutexes are wrong for interrupts; introduces [[Deadlock]] as a non-`unsafe` failure mode.

> "We're now using `Cell`, which along with its sibling `RefCell` is used to provide safe interior mutability. We've already seen `UnsafeCell` which is the bottom layer of interior mutability in Rust. … A `Cell` is like an `UnsafeCell` but it provides a safe interface: it only permits taking a copy of the current value or replacing it, not taking a reference, and since it is not `Sync`, it cannot be shared between threads." — the [[InteriorMutability]] three-layer taxonomy.

> "The `Mutex` ensures we only have access during a critical section, and therefore makes the variable `Sync`, even though a plain `RefCell` would not be `Sync`. The `RefCell` gives us interior mutability with references, which we'll need to use our `GPIOA`. The `Option` lets us initialise this variable to something empty, and only later actually move the variable in." — the canonical **`Mutex<RefCell<Option<T>>>` peripheral-sharing pattern**.

> "Be careful to enable the interrupt only after setting `MY_GPIO`: otherwise the interrupt might fire while it still contains `None`, and as-written (with `unwrap()`), it would panic." — the init-order trap.

> "[RTIC] enforces static priorities and tracks accesses to `static mut` variables ('resources') to statically ensure that shared resources are always accessed safely, without requiring the overhead of always entering critical sections and using reference counting (as in `RefCell`). This has a number of advantages such as guaranteeing no deadlocks and giving extremely low time and memory overhead." — the **[[RTIC]]** pitch.

> "Embassy is an ecosystem of libraries which focus on using the `async` / `await` syntax included in Rust for concurrency. The core of embassy is its asynchronous executor which supports most common MCU architectures." — the **[[Embassy]]** pitch.

> "All the examples using a critical section (including the `cortex_m::interrupt::Mutex`) assume the only other execution thread is the interrupt thread, but on a multi-core system that's no longer true. Instead, we'll need synchronisation primitives designed for multiple cores (also called SMP, for symmetric multi-processing). These typically use the atomic instructions we saw earlier." — the closing **multi-core caveat**.

## Contradictions

None with existing wiki content. **Strictly additive**, but with one important **clarification** of the [[InterruptAttribute|`#[interrupt]`]] page's *"`static mut` inside the body is safe"* claim: that page already noted the safety rests on *"the [[NVIC]] will not concurrently re-enter the *same* handler on a single core, the `&mut` is unique by construction."* This chapter extends the picture by showing that **state shared between** `#[interrupt]` and `main` (the running `COUNTER` example) is the case `#[interrupt]`'s body-level `static mut` rewrite does **not** handle — and develops the [[CriticalSection]] / [[Atomic]] / [[Mutex]] / `Mutex<RefCell<Option<T>>>` toolchain explicitly to address it. The two claims are complementary, not contradictory.

Also worth noting: the [[Interrupt]] concept page lists *programmable priorities*, *nesting/preemption*, and *clear-reason* as the three NVIC-level concerns. This chapter adds a **fourth**, mostly orthogonal axis — **shared mutable state between interrupt and main** — which the earlier *Interrupts* chapter ([[rust-embedded-book-start-interrupts]]) deliberately deferred. The two chapters together close the loop.
