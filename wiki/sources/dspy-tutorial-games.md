## Summary

Official [[DSPy]] tutorial at `https://dspy.ai/tutorials/games/` (`docs/docs/tutorials/games/index.ipynb`) — the **canonical end-to-end worked receipt of [[BootstrapFinetune|`dspy.BootstrapFinetune`]] applied to an agentic program**, and the **first wiki-corpus DSPy tutorial that targets the [[FineTuning|weight-tuning]] rung of [[DSPyOptimization|the three-stage workflow]] on an interactive sequential-decision task** (prior weight-space receipts — [[dspy-tutorial-rl-papillon|rl_papillon]], [[dspy-rl-multihop-tutorial|rl_multihop]] — used [[grpo|GRPO]]/[[ArborGRPO]] for online RL, not supervised fine-tuning). Trains a 50-step hand-rolled [[react|ReAct]]-style agent on the [[AlfWorld]] household-task benchmark via a two-stage **prompt-then-weights** recipe: (1) [[MIPROv2|`dspy.MIPROv2(auto="light")`]] over the GPT-4o agent (teacher), then (2) [[BootstrapFinetune|`dspy.BootstrapFinetune`]] distills the prompt-optimized teacher's trajectories into [[GPT|GPT-4o-mini]] weights via the [[OpenAI|OpenAI]] fine-tuning API. **Headline lift: 15.0% → 71.5% devset success** (+56.5 pts absolute, **~4.8× relative**) on 200 dev tasks with 200 train tasks — and the fine-tuned 4o-mini **beats its own GPT-4o teacher's 57.5% zero-shot score by +14 pts** while running on a smaller, cheaper model.

## Key Claims

- **The first wiki-corpus end-to-end runnable [[BootstrapFinetune]] receipt on an agentic program.** [[dspy-optimizers|The Optimizers page]]'s only prior worked receipt is the **Banking77 classification** example (`text, hint -> label`, [[ChainOfThought]] over a `Literal[tuple(CLASSES)]`-typed Signature, 2000 examples, 66% → 87%). This tutorial **moves the BFT envelope** from single-call classification to a **50-step interactive agent with non-trivial environment-driven trajectories**. Agent shape: one [[DSPyPredict|`dspy.Predict("task, trajectory, possible_actions: list[str] -> action")`]] sub-module called up to 50× per task inside a hand-written `forward()` loop. Each `BootstrapFinetune.compile(student, teacher=optimized_4o, trainset=trainset)` call internally rolls the teacher across the trainset, filters traces by the metric (`y.success == 1`), and emits an SFT dataset of `(task, trajectory, possible_actions) → action` records — **one fine-tuning example per agent step**, not per task — for the OpenAI fine-tuning API.

- **The two-stage prompt-then-weights composition is the canonical worked example.** The tutorial directly operationalizes [[BootstrapFinetune|the page-13 composability recipe]]: *"You can run `dspy.MIPROv2` and use the produced program ... to `dspy.BootstrapFinetune` to get better results. This is partly the essence of `dspy.BetterTogether`."* Stage 1: `dspy.MIPROv2(metric=metric, auto="light", num_threads=16, prompt_model=gpt4o).compile(agent_4o, trainset=trainset, max_bootstrapped_demos=1, max_labeled_demos=0, minibatch_size=40)` — produces `optimized_4o` (a [[MIPROv2]]-tuned GPT-4o agent). Stage 2: `student_4o_mini = optimized_4o.deepcopy(); student_4o_mini.set_lm(gpt4o_mini)` then `dspy.BootstrapFinetune(metric=metric, num_threads=16).compile(student_4o_mini, teacher=optimized_4o, trainset=trainset)`. The student **inherits the optimized prompt + (optionally) the bootstrapped demos** from the teacher; the comment `# student_4o_mini.react.demos = []  # you can optionally reset the demos` exposes the demo-retention knob as an explicit design choice. **First wiki receipt of the `teacher=...` kwarg on `dspy.BootstrapFinetune`** — prior Banking77 receipt did not use a separate teacher (it bootstrapped from the same model it fine-tuned).

- **`dspy.configure(experimental=True)` is required.** Top-of-notebook flag (`dspy.configure(experimental=True)` alongside `dspy.LM` declarations) is a **first wiki receipt of the `experimental=True` global toggle**. The tutorial does not document what it gates, but its placement before BootstrapFinetune is load-bearing — implying [[BootstrapFinetune|the BFT pipeline]]'s agent-loop trace-extraction codepath ships under the experimental flag in DSPy 2.6.0.

- **Hand-rolled ReAct beats `dspy.ReAct` here — and the tutorial is honest about it.** The intro markdown calls the agent *"a ReAct agent"* but the implementation **does not use [[react|`dspy.ReAct`]]** — it builds the [[react|*think-act-observe*]] loop by hand with a plain `dspy.Predict` and a `"think: ${...thoughts...}"` pseudo-action injected into `possible_actions`. Rationale (inferred, not stated): `dspy.ReAct`'s built-in tool-call slots and trajectory format are **not what `BootstrapFinetune` wants to fine-tune** — it wants a flat `(task, trajectory, possible_actions) → action` Signature whose SFT supervision is one action per row. **First wiki receipt of "the ReAct *pattern* without `dspy.ReAct`"** — a deliberate framework-level escape hatch for the weight-tuning regime.

- **The `"think:"` pseudo-action is the [[react|ReAct]] *Thought* primitive smuggled in as an admissible command.** `possible_actions = info["admissible_commands"][0] + ["think: ${...thoughts...}"]` — the environment's admissible-command list is **augmented with a free-form thought slot the LM can emit**. When `prediction.action.startswith("think:")`, the agent **does not call `env.step(...)`**; it appends `"OK."` to the trajectory and continues the loop without consuming an environment turn. This is the [[react|paper's]] *Thought* token reimplemented as an admissible-action sentinel — preserving the *reasoning* axis of [[react|ReAct]] inside a vanilla `dspy.Predict` whose Signature has no `reasoning` field (unlike [[chainofthought|`dspy.ChainOfThought`]]). **First wiki receipt of the "thought-as-action" pattern** — a structural alternative to CoT's `reasoning` injection.

- **The metric is `lambda x, y, trace=None: y.success`.** Reads the **prediction**'s `success` attribute (not the example's gold label) — because the *prediction* carries the agent's actual environment reward (`reward = int(info["won"][0])` returned via `dspy.Prediction(trajectory=trajectory, success=reward)`). **First wiki receipt of a metric that reads from `y` (the prediction) rather than `x` (the example)** — the prior [[BootstrapFinetune|Banking77 lambda]] was `x.label == y.label`. This shape is forced by **agent-style tasks**: the ground-truth signal is environment success, not a held-out label.

- **Trajectory as a Python-rendered string, not a structured field.** The `trajectory` input to the Signature is `"\n".join(trajectory)` where `trajectory` is a list alternating `"> {action}"` lines and observation lines (or `"OK."` after a `think:`). The [[DSPyAdapters|Adapter]] sees a single `str` input named `trajectory` — there is no `list[Turn]` or `list[dict]` structured type. **Implication for BFT**: the SFT examples encode the trajectory as **plain text the model conditions on**, identical to inference time. This is the simplest possible serialization choice that survives both prompt-optimization and weight-tuning regimes.

- **`max_iters=50` is the canonical agent-loop iteration cap.** The hand-rolled `forward()` loops up to 50 times — matching [[AlfWorld]]'s standard 50-step task budget from [[react|Yao et al. 2022]]. This is the **first wiki receipt naming `max_iters=50` for a DSPy agent** — for comparison, [[react|`dspy.ReAct`]]'s default is `max_iters=5`, an order of magnitude smaller. Long-horizon agents need a 10× iteration budget over the built-in module default.

- **The dataset is `dspy.datasets.alfworld.AlfWorld()` — a DSPy-native loader.** Mirrors [[dspy-tutorial-math|`dspy.datasets.MATH(subset='algebra')`]] as the **second wiki receipt of an in-framework dataset class** that abstracts both data and (here) **environment-pool management** (`alfworld.POOL.session()` is a context manager for the [[TextWorld]] subprocess pool). **First wiki receipt of an in-framework loader that ships *executable environment infrastructure***, not just `Example` records — `AlfWorld()` is a hybrid dataset + simulator handle.

- **Asymmetric two-model stack: `gpt-4o-mini-2024-07-18` student + `openai/gpt-4o` teacher.** Same teacher-student split [[dspy-tutorial-math|the MATH algebra tutorial]] uses (4o-mini student + 4o teacher), but here the teacher is **also the [[MIPROv2]] `prompt_model`** (the LM that proposes new instruction candidates) — explicit kwarg `prompt_model=gpt4o`. **First wiki receipt of `prompt_model` as an explicit MIPROv2 kwarg** — prior MIPROv2 receipts let it default to the program's configured LM. **Inconsistency in the tutorial source**: `gpt4o_mini = dspy.LM('gpt-4o-mini-2024-07-18')` is declared without the `openai/` prefix; `gpt4o = dspy.LM('openai/gpt-4o')` is declared with it. [[DSPyLM|`dspy.LM`]] / [[LiteLLM]] tolerates both, but the inconsistency is worth flagging.

- **Pickle save/load is the persistence surface.** `finetuned_4o_mini.save('finetuned_4o_mini_001.pkl')` then `Agent().load('finetuned_4o_mini_001.pkl', allow_pickle=True)`. The tutorial includes an inline **security warning** — *"Loading `.pkl` files can execute arbitrary code and may be dangerous. Only save and load pickle files from trusted sources in secure environments. Consider using JSON format when possible for safer serialization."* — **first wiki receipt of an in-tutorial pickle security warning**. The saved `.pkl` keeps a **reference to the fine-tuned model's provider-side identifier** — the local file is *not* a self-contained artifact; it depends on the OpenAI-side fine-tune still existing under the same ID.

- **Headline number, precisely.** GPT-4o zero-shot = **115/200 (57.5%)** in **06:14** at `num_threads=16`. GPT-4o-mini zero-shot = **30/200 (15.0%)** in **08:33**. Fine-tuned GPT-4o-mini = **143/200 (71.5%)** in **03:15** (a **2.6× wall-clock speedup** over zero-shot 4o-mini, on top of the success-rate lift — the fine-tuned model is both more accurate *and* faster, because shorter trajectories on average). The prose claim *"19% → 72% with 100 train tasks, 82% with 500 train tasks"* uses approximate / round numbers diverging from the printed exact figures — the **printed-output values are authoritative**, the prose values are illustrative. The 82% figure is **not reproduced in the notebook** — it is forward-looking extrapolation.

## Key Quotes

> *"Let's walk through a quick example of optimizing the language model weights (i.e., fine-tuning) inside a DSPy module that represents a ReAct agent playing a game with 50-step tasks."* — opening line; the **first DSPy tutorial whose opening sentence is a weight-tuning thesis**.

> *"Our goal is to allow `gpt-4o-mini` to play the AlfWorld household game proficiently, without tinkering with string prompts or example trajectories by hand."* — the **DSPy abstraction-over-prompt-engineering pitch**, re-stated for agents.

> *"Though it's not strictly necessary, we'll make our job a little easier by using the larger `gpt-4o` for prompt optimization and fine-tuning, building our small `gpt-4o-mini` agent."* — the **teacher-student split rationale**, explicit. Acknowledges it as **optional** ergonomic choice, not a structural requirement.

> *"The agent is a pretty simple `dspy.Module` with one sub-module called `self.react`."* — confirms the framing: even with `max_iters=50` and a 200-task SFT dataset, the agent *program* is minimal — one Predict, one loop.

> *"With just 100 training tasks, we'll teach 4o-mini to go from 19% (can barely play the game) to 72%. If you use 500 tasks and retain the demonstrations during fine-tuning, you can push that easily to 82%."* — the **promotional headline**, with two future-work knobs called out: (1) **train-set size** (200 → 500), and (2) **demo retention** (the `# you can optionally reset the demos` line implies the **default retains them**, which the headline endorses).

> *"In principle, you can copy a short definition of the AlfWorld task (based on Yao et al., 2022) and use that as the instruction for your agent. This is not inherently essential, but it helps illustrate the role that instructions play in DSPy: they're not for coercing the model to exhibit a certain behavior, but they're there to describe the fundamentals of the task in a straightforward, human-readable way."* — the **clearest framework-philosophy statement in the DSPy corpus on what instructions are for**: not behavioral coercion, but task description. Worth citing back in the [[DSPySignatures]] page.

> *"⚠️ Security Warning: Loading `.pkl` files can execute arbitrary code and may be dangerous. Only save and load pickle files from trusted sources in secure environments. Consider using JSON format when possible for safer serialization."* — verbatim; **first explicit security warning in the DSPy tutorial corpus**.

## Contradictions

- **Prose vs printed numbers diverge.** Tutorial prose says *"19% → 72%"* but the printed-output cells show **15.0% → 71.5%**. The 19/72 figures are approximate / illustrative; the 15.0/71.5 figures are the authoritative empirical results from this run. **Not a code/data inconsistency** — just a prose rounding choice the reader should be aware of when citing.
- **The "82% with 500 train tasks" claim is not reproduced in the notebook.** It is forward-looking extrapolation, not an empirical receipt. Citing it as a result risks over-claiming.
- **The agent is called *"a ReAct agent"* in prose but does not use `dspy.ReAct`.** Internally consistent (ReAct is a prompting pattern, not a Module choice) but worth flagging — readers grepping for `dspy.ReAct` will not find it here.
- **`gpt-4o-mini-2024-07-18` model string is declared without the `openai/` prefix** while `gpt-4o` is declared with `openai/`. Inconsistent prefix usage in the same script; [[DSPyLM|`dspy.LM`]] tolerates both, but reproducers may stumble.
- **`max_iters=50` agent-loop cap is 10× the [[react|`dspy.ReAct`]] default of `max_iters=5`.** Tutorial does not flag the difference; readers transferring this to other agentic tutorials need to set `max_iters` explicitly.
- **No cost disclosure.** Same gap as [[dspy-tutorial-gepa-aime]] / [[dspy-tutorial-gepa-papillon]] / [[dspy-tutorial-gepa-trusted-monitor]] — no $ figures for the OpenAI fine-tune call, the MIPROv2 optimization rollouts, or the three evaluation runs. Fine-tuning GPT-4o-mini on ~thousands of trajectory steps is the most material cost in this tutorial and is left implicit.
- **No `dspy.BetterTogether` head-to-head.** The tutorial **hand-rolls the BetterTogether sequence** (MIPROv2 → BFT) but never compares against `dspy.BetterTogether` itself. The [[BetterTogether]] meta-optimizer's actual API is not exercised — an unfilled receipt slot.
- **No GRPO baseline.** Same task family ([[AlfWorld]]) is also a natural [[grpo|GRPO]] target via [[ArborGRPO]] (since the metric `y.success` is a deterministic binary reward — the same shape [[dspy-rl-multihop-tutorial]]'s recall reward has). The tutorial does not run a GRPO baseline, leaving the **prompt+SFT vs online-RL head-to-head on this benchmark unfilled**. (Cross-tutorial gap: [[dspy-tutorial-rl-papillon]] explicitly disclaims weight-RL as *"typically worse on cost/quality basis than prompt optimizers"* — but this tutorial demonstrates **prompt+SFT actually beats the prompt-only teacher**, suggesting the SFT step is doing real work the online-RL receipts haven't bested.)

## Scope-Limit Gaps

- **No `max_bootstrapped_demos` sweep.** Tutorial pins `max_bootstrapped_demos=1, max_labeled_demos=0` for MIPROv2 without justification. Whether higher demo counts would have improved the teacher (and therefore the student) is left open.
- **No ablation of the `# you can optionally reset the demos` toggle.** The comment hints at a knob (reset student demos to `[]` before fine-tuning) but the tutorial picks one branch (retain) without showing the other.
- **No `auto="medium"` or `auto="heavy"` MIPROv2 budget comparison.** Tutorial uses `auto="light"` exclusively.
- **No alternative metric — e.g., trajectory length penalty.** The metric `y.success` is binary; a length-penalized metric (`success / trajectory_length`) would incentivize shorter trajectories and might further improve the fine-tune since the model's `(task, trajectory, possible_actions) → action` Signature does not currently encode "be efficient."
- **No multi-task evaluation.** [[AlfWorld]] has six task types (pick & place, examine in light, clean & place, etc.) — tutorial reports one aggregate success rate, no per-task-type breakdown. Whether the fine-tune generalizes uniformly across task types or specializes on the easy ones is unknown.
- **No held-out test split.** Trainset and devset are both 200 examples sliced from the same `AlfWorld()` loader (`trainset[:200]` vs `devset[-200:]`). No fully held-out set means the headline 71.5% may include some dev-tuning overfit via the MIPROv2 prompt-search step.
- **No instructions-string ablation.** The "Aside" shows how to pass `INSTRUCTIONS` to the Signature but doesn't run the comparison — whether human-written task instructions further improve the fine-tuned model is left open.
- **No streaming / async / observability composition.** Unlike [[dspy-async-tutorial]] and [[dspy-streaming-tutorial]], this tutorial doesn't show how the fine-tuned agent program composes with the async or streaming surfaces — relevant for serving long-horizon agents in production.
