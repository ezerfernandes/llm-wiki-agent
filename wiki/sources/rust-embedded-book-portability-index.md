# The Embedded Rust Book — Portability

## Summary

File 27/44 of *[[TheEmbeddedRustBook]]* — **opens** (and is the sole content file of) the *Portability* chapter, the chapter forward-referenced from [[rust-embedded-book-start-registers]] and from the [[EmbeddedHalCrate|`embedded-hal`]] entity page since the start of the corpus. Single-file chapter. **Names the chapter's titular concept**, [[Portability]], as the *"very important topic"* of embedded systems — *"Every vendor and even each family from a single manufacturer offers different peripherals and capabilities and similarly the ways to interact with the peripherals will vary"* — and pins its standard solution as a [[HardwareAbstractionLayer|Hardware Abstraction Layer (HAL)]], quoting the Wikipedia definition (*"sets of routines in software that emulate some platform-specific details, giving programs direct access to the hardware resources"*). Notes the **embedded-specific twist** that disqualifies the OS-syscall flavor of traditional HALs: embedded targets *"typically do not have operating systems and user installable software but firmware images which are compiled as a whole."* Then introduces the embedded-Rust answer: **[[EmbeddedHalCrate|`embedded-hal`]]** as *"a set of traits which define implementation contracts between **HAL implementations**, **drivers** and **applications (or firmwares)**."* The chapter's central argument is the **combinatorial-complexity collapse from M·N to M+N**: with **M** [[HALCrate|HAL implementations]] and **N** [[DriverCrate|driver]] crates, *"if we were to reinvent the wheel for every application then we would end up with **M·N** implementations while by using the API provided by the embedded-hal traits will make the implementation complexity approach **M+N**."* Enumerates the named [[EmbeddedHalCrate|`embedded-hal`]] traits: GPIO (input + output pins), serial, [[I2C]], [[SPI]], timers/countdowns, ADC. Carves the three-role taxonomy of `embedded-hal` users — **HAL implementation** (one-or-more hardware-specific types + factory/init functions + trait `impl`s — flavored as low-level register access, OS adapter à la Linux `sysfs`, mock adapter for unit testing, or driver-for-hardware-adapter like an I2C-multiplexer or GPIO-expander), **[[DriverCrate|driver]]** (sensors / displays / actuators, parameterized by a trait-bound generic over an `embedded-hal` trait), and **application** (the firmware binary that initializes real hardware via the HAL implementation and binds drivers together — *"the part which requires the most adaptation efforts"* when porting). The chapter that **resolves the portability promise** the whole crate-stack architecture ([[MicroArchitectureCrate]] → [[PeripheralAccessCrate|PAC]] → [[HALCrate|HAL]] → [[BoardCrate|Board]]) has been building toward since file 13.

## Key Claims

- **Portability is the "very important topic"** of embedded development. *"Every vendor and even each family from a single manufacturer offers different peripherals and capabilities and similarly the ways to interact with the peripherals will vary."* — vendor + family + peripheral-variation as the three axes of fragmentation.
- **A Hardware Abstraction Layer (HAL) is the standard equalizer**. Quotes Wikipedia: *"Hardware abstractions are sets of routines in software that emulate some platform-specific details, giving programs direct access to the hardware resources. They often allow programmers to write device-independent, high performance applications by providing standard operating system (OS) calls to hardware."*
- **The OS-syscall flavor of HALs is the wrong fit for embedded**. *"Embedded systems are a bit special in this regard since we typically do not have operating systems and user installable software but firmware images which are compiled as a whole as well as a number of other constraints. So while the traditional approach as defined by Wikipedia could potentially work it is likely not the most productive approach to ensure portability."*
- **`embedded-hal` is the embedded-Rust answer**: *"a set of traits which define implementation contracts between HAL implementations, drivers and applications (or firmwares)."* Contracts encode **capabilities** (trait-implemented ⇒ capability provided) and **methods** (trait-bounded ⇒ methods available).
- **Named `embedded-hal` traits** (the file's list): GPIO (input + output pins), serial communication, [[I2C]], [[SPI]], timers/countdowns, analog-digital conversion (ADC).
- **M·N → M+N is the central architectural payoff**. *"If M is the number of peripheral HAL implementations and N the number of drivers then if we were to reinvent the wheel for every application then we would end up with M·N implementations while by using the API provided by the embedded-hal traits will make the implementation complexity approach M+N."* The chapter names this as the reason the ecosystem was structured this way — well-defined ready-to-use APIs, less trial-and-error, **fewer total implementations** to maintain across the ecosystem.
- **Three named users of `embedded-hal`**: (1) **HAL implementation**, (2) **driver**, (3) **application** — the chapter's taxonomy.
- **HAL implementation = (hardware-specific types) + (factory/init functions) + (`embedded-hal` trait `impl`s).** *"Typical implementations consist of three parts: One or more hardware specific types; Functions to create and initialize such a type, often providing various configuration options (speed, operation mode, use pins, etc.); one or more trait impl of embedded-hal traits for that type."*
- **Four flavors of HAL implementation**: *"Via low-level hardware access, e.g. via registers; Via operating system, e.g. by using the sysfs under Linux; Via adapter, e.g. a mock of types for unit testing; Via driver for hardware adapters, e.g. I2C multiplexer or GPIO expander."* — names mock-for-testing and adapter-as-HAL as legitimate first-class implementations, not just register-level wrappers.
- **A driver is initialized with an `embedded-hal`-trait-bounded peripheral instance**. *"A driver has to be initialized with an instance of type that implements a certain trait of the embedded-hal which is ensured via trait bound and provides its own type instance with a custom set of methods allowing to interact with the driven device."* The driver crate is **chip-agnostic** — it depends on the *trait*, not on a specific HAL.
- **Driver examples**: sensors (temperature, magnetometer, accelerometer, light), display devices (LED arrays, LCD displays), actuators (motors, transmitters).
- **The application is where the porting work concentrates**. *"When porting between different systems, this is the part which requires the most adaptation efforts, since the application needs to correctly initialize the real hardware via the HAL implementation and the initialisation of different hardware differs, sometimes drastically so."* HAL implementations + drivers can be reused as-is; the wiring + init code is what changes.
- **Application-level porting trade-offs**: *"Components can be physically connected to different terminals, hardware buses sometimes need external hardware to match the configuration or there are different trade-offs to be made in the use of internal peripherals (e.g. multiple timers with different capabilities are available or peripherals conflict with others)."* — peripheral-conflict + pin-assignment + bus-config as the canonical port-time decisions.

## Key Quotes

> "In embedded environments portability is a very important topic: Every vendor and even each family from a single manufacturer offers different peripherals and capabilities and similarly the ways to interact with the peripherals will vary." — the chapter's framing of the [[Portability]] problem.

> "A common way to equalize such differences is via a layer called Hardware Abstraction layer or HAL." — names [[HardwareAbstractionLayer|HAL]] as the standard solution.

> "Embedded systems are a bit special in this regard since we typically do not have operating systems and user installable software but firmware images which are compiled as a whole as well as a number of other constraints. So while the traditional approach as defined by Wikipedia could potentially work it is likely not the most productive approach to ensure portability." — why embedded-Rust uses a trait-based HAL rather than a syscall-based HAL.

> "In a nutshell it is a set of traits which define implementation contracts between HAL implementations, drivers and applications (or firmwares). Those contracts include both capabilities (i.e. if a trait is implemented for a certain type, the HAL implementation provides a certain capability) and methods (i.e. if you can construct a type implementing a trait it is guaranteed that you have the methods specified in the trait available)." — the canonical one-paragraph definition of [[EmbeddedHalCrate|`embedded-hal`]].

> "If you consider that an application might have to implement the use of the peripheral in the hardware as well as the application and potentially drivers for additional hardware components, then it should be easy to see that the re-usability is very limited. Expressed mathematically, if M is the number of peripheral HAL implementations and N the number of drivers then if we were to reinvent the wheel for every application then we would end up with M·N implementations while by using the API provided by the embedded-hal traits will make the implementation complexity approach M+N." — the **M·N → M+N** combinatorial argument, the chapter's central architectural payoff.

> "A driver implements a set of custom functionality for an internal or external component, connected to a peripheral implementing the embedded-hal traits. Typical examples for such drivers include various sensors (temperature, magnetometer, accelerometer, light), display devices (LED arrays, LCD displays) and actuators (motors, transmitters)." — the canonical definition of a [[DriverCrate|driver crate]] and the three-category taxonomy.

> "The application binds the various parts together and ensures that the desired functionality is achieved. When porting between different systems, this is the part which requires the most adaptation efforts, since the application needs to correctly initialize the real hardware via the HAL implementation and the initialisation of different hardware differs, sometimes drastically so." — locates the **port-time effort** at the application layer, not the HAL or driver layer.
