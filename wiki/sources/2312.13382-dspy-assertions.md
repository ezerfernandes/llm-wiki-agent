# DSPy Assertions (Singhvi, Shetty, Tan, Potts, Sen, Zaharia, Khattab, 2024)

**arXiv**: 2312.13382v2 (v1 Dec 2023, v2 2 Feb 2024) · **Status**: arXiv preprint (not peer-reviewed venue listed in paper).
**Authors**: [[ArnavSinghvi]]¹ · [[ManishShetty]]¹ · [[ShangyinTan]]¹ · [[ChristopherPotts]]² · [[KoushikSen]]¹ · [[MateiZaharia]]¹ · [[OmarKhattab]]² (¹ = [[UCBerkeley]], ² = [[stanforduniversity|Stanford]]; first three authors equal contribution)
**Framework integration**: Implementation publicly merged into the [[DSPy]] framework as `dspy.Assert` / `dspy.Suggest`.

## Summary

The paper introduces **[[LMAssertions|LM Assertions]]** — first-class programming constructs that let a [[DSPy]] developer express arbitrary **computational constraints** on the outputs of LM modules. Two variants are defined: **[[DSPyAssert|`Assert`]]** (hard constraint — halts the pipeline after $R$ failed retries with `AssertionError`) and **[[DSPySuggest|`Suggest`]]** (soft constraint — logs a `SuggestionError` after $R$ retries and continues). Both raise on violation, and the failing LM module is re-invoked in a **retry state** with the prior erring output plus the user-supplied error message injected into the prompt — enabling [[AssertionDrivenBacktracking|assertion-driven backtracking]] and inference-time self-refinement.

Beyond runtime self-refinement, LM Assertions enable two novel **compile-time** optimizations on top of [[BootstrapFewShotWithRandomSearch|`BootstrapFewShotWithRandomSearch`]]: **[[AssertionDrivenExampleBootstrapping|assertion-driven example bootstrapping]]** (the teacher uses assertion-driven backtracking during demo generation so bootstrapped few-shots are guaranteed to satisfy every assertion at every intermediate module — not only the final-answer metric), and **[[CounterexampleBootstrapping|counterexample bootstrapping]]** (collect traces where the LM *failed* an assertion before fixing, then include the failure + fix pair as a demonstration — a negative example the student model learns from).

Evaluation on **four** [[hotpotqa|HotPotQA]]-derived tasks ([[MultiHopQA]], [[LongFormQA]], [[QuizGen]], [[TweetGen]]) shows: in QuizGen, valid-JSON quiz generation goes from **37.6% → 98.8%**, with overall validity (JSON + correct-answer + plausibility) reaching **87.2%** (vs 30.5% baseline); MultiHopQA suggestions-passed jumps from **66.3 → 95.7** dev; TweetGen engagement-pass-rate from **2.0% → 73.0%**. Constraints are passed up to **164% more often** and the system generates up to **37% more higher-quality responses**.

## Key Claims

- **Programming-language assertions don't transfer cleanly to LM pipelines.** Conventional Python `assert` is binary halt-on-fail. LMs can be *re-prompted* with the failure as feedback — so an assertion in an LM program should trigger a retry-with-feedback loop, not termination.
- **Two-level severity is necessary.** Some constraints are non-negotiable (the answer must be valid JSON) → `Assert` halts on persistent failure. Some are heuristic guidance (this tweet should be engaging) → `Suggest` warns and continues. The same control-flow primitive can't serve both — the paper splits them.
- **Big-step operational semantics** with retry-counted states $\sigma_r$: $\text{Assert}(e,m)$ transitions to $\sigma'_0$ if $e$ evaluates true, to $\sigma_{r+1}$ if false and $r<R$ (retry), or to $\sigma^\perp$ if $r \geq R$ (halt with `AssertionError`). `Suggest` is identical except the $r \geq R$ branch transitions to $\sigma''_0$ (log `SuggestionError`, continue, reset retry count).
- **Backtracking implementation via a meta-module `Retry`.** Wraps any DSPy module; carries prior failed predictions + user error messages; on retry, the auto-updated prompt to the failing module includes "Past Query: \<previous attempt w/ errors\>" + "Instruction: \<assertion error message\>" — the LM sees its own failure and the rule it broke.
- **Compile-time optimization 1 — assertion-driven example bootstrapping.** A naive `BootstrapFewShot` teacher might emit a final answer that's correct overall but where intermediate module outputs *violated* assertions. Applying assertion-driven backtracking *during teacher bootstrapping* guarantees every bootstrapped demonstration satisfies every assertion at every module — *"all the bootstrapped demonstrations are guaranteed to follow the intermediate constraints, too"*.
- **Compile-time optimization 2 — counterexample bootstrapping.** Backtracking traces (`failing output, error, corrected output`) are themselves valuable few-shot examples. The optimizer mixes these counterexamples into the bootstrapped demos; *"counterexample traces often come with the demonstrations of fixing particular LM Assertion failures"* — *"the program still has the ability to generate more responses that adhere to programmer-defined assertions"* even without inference-time backtracking.
- **Five-strategy evaluation matrix** (Table 1): `Vanilla` (zero-shot baseline) / `Compile` (compiled few-shot, no assertions) / `Infer w/ Assert` (inference-time backtracking only) / `Compile w/ Assert` (compile-time bootstrap + counterexample, no inference-time retry) / `C+Infer w/ Assert` (all optimizations).
- **Best overall: `C+Infer w/ Assert`.** Combining compile-time assertion-driven bootstrapping with inference-time backtracking dominates on intrinsic metrics across all four tasks: QuizGen Validity 30.5 → 87.2; MultiHopQA Suggestions Passed 66.3 → 95.7; LongFormQA Citation Faithfulness 77.3 → 92.7; TweetGen Faithful 78.3 → 76.7 (mixed but No-# 21.3 → 98.0).
- **A subtle "conflicting suggestions" failure mode.** In TweetGen with `C+Infer w/ Assert`, Engaging actually *drops* compared to `Infer w/ Assert` alone — the five suggestions (no hashtags / within 280 chars / correct answer / engaging / faithful) can override each other during sequential self-refinement. The paper presents this as evidence that LM Assertion design itself is a learnable skill.
- **Robustness to prompt quality.** With deliberately minimal *primitive instructions* ("Generate a tweet that effectively answers a question"), the baseline collapses (QuizGen 2.8% Correct JSON vs 41.7% with complete instructions), but assertion-driven strategies remain comparable to their complete-instruction performance — *"model pipelines with LM Assertions and assertion-driven optimizations are less sensitive to instructions, requiring less effort on manual prompt tuning"*.

## Key Quotes

> "[...] researchers have explored various techniques, including applying constrained decoding, exploring approaches for self-reflection and tree search, building domain-specific languages [...] or monitoring models with assertions and guardrails [...] to steer LMs towards more controllable outputs."

> "We propose two types of LM Assertions: (hard) Assertions and (soft) Suggestions, denoted by `Assert` and `Suggest`, respectively. Hard assertions represent critical conditions that, when violated after a maximum number of retries, cause the LM pipeline to halt, signaling a non-negotiable breach of requirements."

> "On retrying, the LM prompt also contains its past attempts and suggestion messages, enabling constraint-guided self-refinement."

> "We apply assertion-driven backtracking to the teacher model in the `BootstrapFewShot` optimizer. In this way, all the bootstrapped demonstrations are guaranteed to follow the intermediate constraints, too. In this way, although the prompt optimizer only has the metric for the final answer, the examples selected will have higher qualities for all intermediate modules thanks to LM Assertions."

> "With LM Assertions and all assertion-driven optimizations, we see a maximum gain from 30.5% to 87.2% in generating valid quiz questions."

## Implementation

### API

```python
dspy.Assert(constraint: bool, msg: Optional[str], backtrack: Optional[module])
dspy.Suggest(constraint: bool, msg: Optional[str], backtrack: Optional[module])
```

`constraint` is a boolean — can itself invoke other DSPy modules (so the check can be an LM call); `msg` is the natural-language feedback injected into the retry prompt; `backtrack` is the target module to retry (defaults to the most recent module).

### Error handling

The framework wraps any DSPy module with a primitive `constraint_transform`. False `Assert` → raises `AssertionError`; false `Suggest` → raises `SuggestionError`. Default handler retries $R$ times via the `Retry` meta-module; after $R$ retries, `AssertionError` halts execution while `SuggestionError` is logged silently and execution continues. Handlers are composable — alternatives include disabling assertions, suppressing errors with logging, etc.

### The `Retry` meta-module

Auxiliary lightweight wrapper around any DSPy module. Tracks all previously-unsuccessful predictions. On invocation, automatically adds the failed predictions + user error messages to the failing module's prompt. *"the original module to refine is self-aware and informed of past attempts and errors on them. Consequently, this empowers the LM to develop more informed and error-avoiding generations in subsequent iterations of self-refinement."*

## Evaluation setup

- **Dataset**: [[hotpotqa|HotPotQA]] (Yang et al. 2018) open-domain "fullwiki" setting, hard-label subset; 70/30 train/val split; 300 train + 300 dev + 500 test sampled per task.
- **Retriever**: [[ColBERTv2]] (Santhanam et al. 2021) over the official 2017 Wikipedia abstracts dump.
- **Model**: OpenAI `gpt-3.5-turbo` (Brown et al. 2020), `max_tokens=500`, `temperature=0.7`.
- **Tasks**: four (described below), each with intrinsic + extrinsic metrics.

### Task suite

| Task | Pipeline | Intrinsic metrics | Extrinsic metrics |
|---|---|---|---|
| [[MultiHopQA]] | 2-hop CoT generate-query → retrieve → answer | Suggestions Passed | Retrieval Recall, Answer Correctness |
| [[LongFormQA]] | 2-hop CoT + cited-paragraph generation | Citation Faithfulness, Citation Recall, Citation Precision | Has Answer |
| [[QuizGen]] | ChainOfThought question + answer-choices generator | Correct JSON, Has Answer, Citation Precision | Validity (composite) |
| [[TweetGen]] | 2-hop retrieve + tweet generator | No "#", Has Answer, Concise (≤280), Engaging (LM-judged), Faithful (LM-judged) | Quality (composite) |

## Connections

- [[DSPy]] — the host framework; LM Assertions integrate as first-class primitives. Predates [[2406.11695-mipro|MIPRO]], [[2407.10930-better-together|BetterTogether]], and [[2507.19457-gepa|GEPA]] in the DSPy-adjacent research arc and supplies the *self-refinement* control-flow primitive that those later optimizers' demonstration-quality assumptions tacitly rely on.
- [[BootstrapFewShot]] / [[BootstrapFewShotWithRandomSearch]] — `Compile w/ Assert` and `C+Infer w/ Assert` are instantiations of `BootstrapFewShotWithRandomSearch` extended with assertion-driven backtracking on the teacher.
- [[chainofthought|ChainOfThought]] — every task pipeline uses `dspy.ChainOfThought` as its prompting module.
- [[ColBERTv2]] — retrieval backend across all four tasks.
- [[hotpotqa|HotPotQA]] — source dataset for all four tasks.
- [[OmarKhattab]] / [[MateiZaharia]] / [[ChristopherPotts]] — senior co-authors; same DSPy-adjacent author cluster as [[2406.11695-mipro|MIPRO]] / [[2407.10930-better-together|BetterTogether]] / [[2507.19457-gepa|GEPA]].
- [[KoushikSen]] — Berkeley PL perspective; same co-author as [[2507.19457-gepa|GEPA]].
- [[ArrangeActAssert]] — Python-side assertion idiom; the LM Assertion construct generalizes it to the LM-pipeline regime.
- [[SelfVerification]] — the broader claim Kambhampati et al. ([[2402.01817-llm-modulo]]) argue LLMs *cannot* perform autonomously. LM Assertions deliberately do **not** rely on the LM to verify itself — the check is a Python boolean (possibly invoking a DSPy program). This sidesteps the LLM-Modulo critique: the *critic* is external code, the LM is only the *generator* + *refiner* given the critic's failure signal.

## Contradictions

- **vs [[2402.01817-llm-modulo|LLM-Modulo (Kambhampati et al., ICML 2024)]].** Not a direct contradiction but a sharp framing difference: LLM-Modulo argues LMs cannot self-verify, so external sound critics are mandatory. DSPy Assertions agree the *check* must be external Python — but show that once the check is external, the *self-refinement* loop on top of it produces large measurable gains, including for soft constraints LLM-Modulo would not address (engagement, plausibility, faithfulness).
- **vs [[2507.19457-gepa|GEPA]] / reflective prompt mutation.** GEPA proposes reflective mutation of the *whole prompt* as the optimization primitive. This paper proposes reflective mutation of the *output* (the LM module's last response) with the prompt held fixed apart from injected feedback. The two are compatible — GEPA-optimized prompts could host LM Assertions — but they target different layers of the compound-AI-system stack ($\Pi$-update vs runtime control-flow). GEPA's "feedback function $\mu_f$" is the natural-language descendant of this paper's `msg: Optional[str]` argument.
- **vs the *prompt-engineering-only* family.** The paper explicitly diagnoses prompt engineering as *"labor-intensive and conflate the high-level design of new AI systems with the low-level exploration of teaching LMs how to follow constraints"*. LM Assertions move constraint enforcement from the prompt body into a separable program construct.
